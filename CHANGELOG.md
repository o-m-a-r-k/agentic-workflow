# Changelog

Release notes, newest first, then every fix that came from a failure in the workflow itself. Generated by `node scripts/changelog.mjs` from `docs/releases/` and `improvements/`.

## 0.7.32 - No more stuck tickets that only your override could free

- **A problem only the test run can show no longer waits for a code review that cannot see it (I-222, D69).** Named failure:
  the final review of a ticket found two problems that only the test run's output shows (a report header drawn over the first
  row in the screenshots, and a required check that never ran). After the fix, every code review honestly said it could not
  confirm them, because a code review is never handed the screenshots or the test output. The workflow then refused to start
  the test run until a review confirmed them, and the only way out was asking you to override the order: that ticket is still
  waiting on the question. In one project's records, 25 code reviews on 9 tickets kept such a problem open, and at 4 of them the
  test run was refused for it. Now:
  - a problem the final review raised that a later code review keeps open with what it checked does not hold the test run back,
    whatever it is about and whether or not a new check was added for it; the next step names those problems and says the test
    run proves them, and the final review after it confirms them; the ticket is still not accepted until that review does;
  - a problem a code review raised and keeps open still holds the test run, and so does one the final review found still broken
    in the test run's own output;
  - when a check is added after the final review, its definition still gets a code review first (that is real review work), and
    the problems that review cannot see no longer hold the test run after it;
  - replayed on the stuck ticket's own records, the next step at the point where you were asked is now the test run.
- **A fix of what the final review found goes straight to the test run again (I-222, D70).** Named failure: the shortcut that
  sends such a fix directly to the test run (the final review after it checks the fix) was switched off by bookkeeping: a plan
  update that only regrouped the same problems into one fix, or corrected an estimate, sent the finished fix to a code review that
  could not check it, which then ran into the problem above. Only 5 of 16 such fixes in one project's records took the shortcut.
  Now the shortcut looks at the work, not the bookkeeping: every implementer handed after the final review is finished (one that
  was stopped counts only when a later one finished its work), the code is what the last of them left, and nothing new was added
  (no requirement added, changed or removed, no repository added, no new check). It also applies when the final review found an
  earlier problem still there. When a check was added after the final review, the next step now says the code review it needs,
  as the test run itself does: in two tickets the next step had named the test run and the test run refused to start.
- **When you settle a disputed premise, your answer settles it (I-222, D71).** Named failure: when a reviewer and an
  implementer disagreed on whether a problem is real in production, the workflow said you decide, and then nothing read your
  answer: the item stayed out of every fix, and a review problem had no way to be closed as "not a problem" at all. Now:
  - "it is not a problem" closes the item as not a defect, through one question you answer, for a review problem
    (`wf scope not-a-defect`) as it already did for an issue found during the work; it stays in the record with the reason, and
    the delivery note does not list it;
  - "it is a real problem" sends it back to be fixed, with your words handed to the implementer; your answer can come from that
    question or from your own words, recorded with `wf decide`, which now names the item;
  - your answer stands: if an implementer reports the same doubt again, the agent is told to bring you what changed, never to
    decide it itself; and while you have not answered, the next step is your question, not another reviewer who is never shown it.
- **A change pushed outside the workflow has a way on (I-222, D72).** Named failure: when a commit made after the acceptance
  was pushed by hand, the next step said "deliver", the delivery refused and pointed at reopening the ticket, and reopening
  refused because the ticket was never delivered. Now the refusal names what works: the pushed code is reviewed, tested and
  accepted in the same attempt (the next step names each), after which the delivery records it as delivered without pushing
  again; or you decide it shipped as it is. The next step says the same, also when a commit was made after the acceptance and not
  pushed.
- **Review of this release: the pushed code is now really reviewed and tested (D69, D70, D72).** A review of this release found
  that the route above reviewed and tested nothing: once the main branch held the pushed commit, the change looked empty, so the
  test run skipped every check and the reviewer was shown the pushed code as someone else's. The pushed code is now read as the
  ticket's own until it is accepted, so its checks run and the reviewer reviews it. A ticket whose code was reset to the main branch
  is no longer mistaken for one pushed by hand: the delivery says to put the accepted code back. Also: new work added to a ticket
  after the final review (a new piece of work in the plan, even with the same requirements) goes through a code review again before
  the test run, as it did before this release; a code review that sees a problem from the final review still in the code raises it
  as its own problem, which holds the test run; and a planned batch of small fixes built while such a problem waits for the test run
  goes to the test run, as other batches do.

- **A ticket may register the proof it needs, and is told how (I-220, D73).** Named failure: `wf validation add` refused "supplemental
  step X is not committed in the attempt adapter" and said nothing more, while the rules every agent reads said "never change the
  workflow from a ticket". A finding that asked for proof on the final tree stayed open 37 minutes, a strategist escalated it to you,
  and you had to answer before the check was registered. Now the refusal names the route (commit the step in the attempt's own
  worktree of the repo that holds the project's adapter, then register it), and the session rules, the work skill and the
  implementer's instructions tell the two apart: the workflow (the plugin) is never changed from a ticket; the project's adapter is
  where a ticket adds its own checks, by design. Adding a check loosens nothing: the ticket is still judged by the adapter on its base
  branch, never by its own adapter change, and only the checks it registers run from its commit.
- **A step with no way to prepare its dependencies says what to do meanwhile (I-219, D74).** Named failure: `wf run --step` was
  refused three times for a step whose plugin cannot install its dependencies before the first commit, and the refusal told the
  implementer to add that to the plugin, which a ticket cannot do. Now it says what to do meanwhile (the package's own install and
  test commands, or commit and run `wf check`), that the implementer says so in its report, and that only the project adds a
  preparation route, in its adapter on the base branch, which the ticket then follows by itself.
- **`wf check` says which untracked files stop it, and why (D74).** Named failure: 17 refusals for a folder an IDE writes by itself
  said only "commit changes before the check". Untracked files still stop a check or a gate: the run reads the folder as it is, so a
  file no commit holds would be part of it (in the same records an untracked new source file was part of the change). The refusal now
  names each one, says why, and gives the three ways on: commit it, delete a tool's output, or have the repo ignore it.
- **A passing rerun keeps the screenshots of the tests it carried (I-221, D75).** Named failure: a gate passed by rerunning only the
  2 test files that failed in the run before it and keeping 1251 tests from that run, but none of that run's 170 screenshots, so the
  end-to-end step looked as if it had collected nothing and the reviewer opened the earlier run's files by hand. Now those screenshots
  come with the tests: each is checked against what was recorded, names the run that took it, and is handed to the evidence review
  and exported as this gate's evidence.
- **Evidence a gate failed to collect can be collected again without a dummy change (D75).** Named failure: nothing could re-run a
  step on a tree that had not changed: a gate reuses what already passed, a rerun of failed steps is refused after a passing gate, and
  the open finding held the gate back, so the only ways on were a commit made for nothing or asking you to override. Now an evidence
  reviewer can say a finding is cured only by running a step again (its screenshots were never taken, nothing in the code is wrong);
  the next step is then one gate on the same tree, which runs that step again in full, and the evidence review after it checks the
  finding. This is offered once for each version of the project's checks: if the new run does not cure it either, the next step no
  longer hands an implementer something with nothing to build; it says the cure is in the check itself (for example which
  screenshots it collects), fixed in the project's own setup on its main branch, which the ticket then follows by itself, and the
  run is offered again after that. A finding in the code is raised as an ordinary finding and fixed like any other. A reviewer that
  names a step the run does not have, or asks for a run again without naming the step, is told so while it can still correct it.
- **A divided review that can never finish says so (D76).** Named failure: the reviewer that combines a divided review asked for its
  parts 169 times over 89 minutes and then waited six hours, because one of the reviewers it waited for had ended without recording
  its part. Now that reviewer is told no part will come and to stop, and the next step stops it and starts a fresh divided review.
- **Reviewers can name evidence files the way the project names them (D77).** Named failure: 78 refusals for paths written from the
  project's top folder, which were read as relative to the ticket's evidence. Both forms now work; a read still never leaves the
  ticket's own evidence.

## 0.7.31 - A full investigation before any recommendation or fix

- **A fix is built only on a premise someone traced (I-217, D64).** Named failure: a reviewer noted a small display problem, a
  due date shown with a clock time on one page and as a date on another. You were asked to decide before anyone researched it,
  the research that followed said nothing in the product actually writes that date, and that was read as "so no wrong data
  exists, the change is safe". The small item became a change to four of the API's data shapes and a new way for a request to
  fail, built in a fix round with no plan, and it was reverted after you asked whether anyone had done a proper analysis. The
  same shape was in the records five more times. Now:
  - every role is told, and the session rules say, that before anything is recommended to you or a fix is built for a finding,
    it knows who writes the data in production, who reads it, which business process and outside systems depend on it, and what
    happens when it is absent, and says what it did not check; a fact that contradicts the premise ("nothing writes it") is a
    stop and a question, never a reason the change is safe;
  - an implementer says, for each problem it fixes, whether its premise holds and what it checked; when it does not hold, it
    builds nothing for it and says why, with the evidence. That item is not handed to another fix round; the next reviewer
    judges the premise (not a problem after all, which closes it, or a real one, which sends it back), or you are asked whether
    it is a defect at all, and it is settled before the ticket is accepted;
  - a reviewer judges the premise of a fix as well as the fix, and "the premise behind the fix does not hold" is a reason it can
    close a reported problem with, with its evidence;
  - a fix that needs a change to a contract (a data shape, a route, an error code) or a new way to fail is planned again, like a
    migration or a new endpoint already was; from a small item fixed alongside, it is never built in that pass;
  - a plan lists who writes the data beside who reads it, and a strategist grouping findings names the premise they share; one
    nobody traced is investigated before a fix round;
  - when a fix round's or a planned pass's own changes reach a contract or a migration, the strategist decides whether that
    stands before anything else is handed, and before the test run after a pass. The rule that an implementer expecting more
    than twice the reviewers' estimate goes to the strategist keeps "more than twice": the estimate in this case did not cover the
    small item at all, so the new check watches what the work did instead.
- **A product decision you make outside the workflow is recorded (I-217, D65).** Named failure: the decision above was asked
  through the question panel with no record of the question, what the recommendation rested on, or your answer. Now a
  recommendation to you says in plain words what was traced, what was not checked and the evidence, and your answer is recorded
  with `wf decide`: the question, the recommendation, what it rests on, what was not checked and your own words, which the
  workflow checks are yours as it does for any answer it reads. It is a record, never a step anything waits for. `wf resume`
  shows it, every later planner, implementer, reviewer and strategist is handed it, and when an analysis changes the picture it
  is withdrawn with what changed and you are asked again.
- **What the agent running a ticket tells an implementer is on record (I-217, D66).** Named failure: every brief in that batch
  lived only in the prompt an agent was started with, so "nothing writes it, so no wrong data exists" reached the implementer
  with no trace. What the agent carries to an implementer (your words, a decision, what research found) now goes into its record
  and its instructions, as it already did for a planner, and the implementer is told to check it rather than take it as fact. A
  reviewer still starts blind and gets none of it.

- **An analysis has a route from plan to finish (I-216, D67).** Named failure: an analysis ticket's plan was accepted with
  investigation-only steps, the next step told the agent to hand the work to an implementer, and that step was refused
  because an analysis changes nothing. Nothing recorded what the analysis found, and an analysis you did not turn into an
  implementation could only be abandoned. Now:
  - after the plan, the next step is the investigation itself, read-only, done by the agent or a read-only helper; an
    analysis is never told to hand work to an implementer;
  - the agent records what it found with `wf analysis record`: an answer for every question the plan asked, with what each
    answer rests on (the file, the query, the command and what it showed), or why it could not be answered; what else it
    found; what it traced and what it did not (where the data comes from and goes, the business process, outside systems);
    and its recommendation. A record with a gap is refused, naming each gap;
  - then the agent tells you what it found and what it did not trace, and what follows is yours: implement it in the same
    ticket (a fresh planner then plans the change, given the analysis, before anyone builds), or close the analysis
    (`wf analysis close`), whose findings stay on record and are given to the planner of the ticket's next attempt;
  - `wf analysis show` prints the analysis for you or for a ticket, also once it is closed;
  - an analysis can now be started while the ticket's implementation is in progress, to trace what a fix rests on before the
    next fix round; what it records is given to the next implementer of that ticket.
- **Your tracker's own instructions come first (I-215, D68).** Named failure: when the agent was told to post the delivered
  screenshots, the workflow said to put image links in a comment, while the project's tracker adapter said to add a native
  page section with uploaded images; the agent followed the workflow's line and the ticket got a comment without images.
  When the agent works the tracker through its connector, each tracker step it is told to do now starts with the adapter's
  own instructions for that step, word for word, followed by the workflow's wording of what the step carries (the status,
  the comment, the screenshots). An adapter that gives no instructions leaves the wording as it was; the built-in Linear
  adapter's instructions are shown too.
- **Review of 0.7.31: fewer false alarms, and the gaps a review found closed (D64, D65, D67).**
  - The check that a fix reached a contract or a migration fired too often. A review counted 35 of 155 fix rounds in one
    project's records, mostly planned work updating an API description along with an endpoint change. It now fires only on
    what nothing handed to that round explains: not on planned work being built, not where a reviewer's finding pointed at
    that file or the reviewer's suggested fix named it, and, for a round fixing only blocking problems, not on a file the
    ticket's own planned work had already changed. A round that builds planned work and also fixes problems is judged
    by the fixes, and a piece of work handed again to fix a named problem is judged as a fix of that problem, except for
    what a re-plan of that piece of work stated: the endpoints it changes, the files it names, or the planned changes it
    lists (rewording an acceptance check explains nothing). A suggested fix explains a new
    migration only when it names where it goes, never by the word "migration" alone. Measured again on the same records,
    counting only rounds that finished: 1 of 229, the due-date change that started this release, and none of the 67
    pieces of work handed again to fix a named problem. When two implementers work in one repository at once, it names
    both rather than blaming one, and a notes file or an index file in a migrations folder no longer counts as a
    migration.
  - `wf decide` records the options you were offered, and the choice has to be one of them, so a later reader sees when
    every option built the same change. A reviewer is given your decision, the options and what was not checked, never the
    agent's recommendation or its reasons.
  - What a reviewer finds about a fix's premise is kept with the problem it judged. A finding whose premise an implementer
    found false reaches the evidence review after a planned pass, with the implementer's evidence, and is marked when it is
    handed again beside other fixes. When a reviewer and an implementer disagree on whether a premise holds, you decide it,
    not a third agent.
  - An analysis run beside a ticket already being built can no longer be turned into a second implementation of the same
    ticket, and only one analysis of a ticket is open at a time.

## 0.7.30 - Live attempts follow the adapter on main; repair and review are handed every fact; fair test slots; screenshots of any run

- **Tickets in progress follow the workflow settings on main (I-151, D60).** Named failure: a ticket started before its
  project narrowed which screenshots a test step keeps went on counting 4,008 other tickets' screenshots, another project's
  ticket kept a rule about what may be left unfixed after the project had changed it, and a fixed delivery adapter reached a
  stuck ticket only through a recovery command that asked you. Each ticket read the project's workflow settings as they were
  the day it started. You had asked for the opposite: tickets in progress follow what is delivered on main. Now:
  - when the project's workflow settings change on main (pushed, not only committed), every open ticket takes them at its
    next step, by itself, and its record says what changed and which commits changed it; nobody is asked;
  - a ticket keeps what is its own: its agreed acceptance criteria, the checks it registered or corrected, the work it
    already handed out and, once its delivery has started, the kind of delivery it started with;
  - a test run that already passed is run again only where the change touches it: a test step it ran that changed, a step
    that was added, or one that may now apply. Everything else is reused, and a ticket already approved is approved again
    without a new review when the evidence comes out the same;
  - settings a ticket cannot take (they need a newer workflow version, drop one of its repositories, or are the ticket's own
    change to its rules) are not taken, and `wf status` says why once. A ticket whose own change to its rules reached main
    never takes the settings on main again while it is open, also after merging main in, and `wf status` says where main is
    now. Its own change is what it authored: main's commits that came into it by `git pull`, a fast-forward or a rebase are
    never taken for its own;
  - a ticket whose delivery has started keeps its approval when main changes a test step it ran; that step runs again
    before the rest is delivered;
  - pausing a ticket (`wf hold`) is recorded before anything else, so its settings never move under the pause;
  - a delivery adapter fixed on main reaches a stuck delivery at the next `wf deliver`; the recovery command that asked you
    (`wf deliver --repin-adapter`) is left for a delivery whose kind of adapter changed half way.
- **Doctor no longer warns about a tracker you reach through the agent's connector (D63).** Named failure: `wf doctor`
  warned that a tracker driven by the agent's connector was "agent-driven ... unverified" and offered to switch to an API
  key. For projects that chose the connector on purpose this is a standing choice, not a fault, yet sessions kept passing the
  warning on to you as something to fix after you had said to use the connector. Now doctor prints one line of information:
  the connector acts on the tracker, and its readback is recorded by the host (read from the session transcript your harness
  keeps) when wf runs from that harness. Nothing suggests another route or a key, and `wf status` points to
  `--from-transcript` for a readback that was only reported by the agent.
- **The scenario run in CI is sharded.** Named cost: the macOS scenario job grew from 23 to past 30 minutes, and its time
  limit had been raised to 45. Each operating system now runs the suite in shards, three on macOS and two on Linux, each
  with every n-th scenario file, so every file still runs on both; per-file times from the last runs put a shard at 8 to 13
  minutes, and each shard's limit is 30 minutes. The workflow's comment no longer says "half an hour" for a 45-minute limit.
- **A role whose model is at capacity is resumed, not failed (I-153, D61).** Named failure: seven role launches ended
  because the model was at capacity and were replaced by fresh starts; four had not changed anything yet, and the others'
  work had to be found again. Now, when the agent's harness reports the model at capacity, the workflow resumes the same
  session with the same instructions: at once, then after a few minutes, then every ten minutes while the model stays busy.
  If the agent's caller set a time to hand back control and the model is still busy then, the role is kept, the agent is told
  it was capacity, and running it again resumes the same session; nothing is started from scratch. Whatever the role, the
  next step the agent reads names it and the command that resumes it, so it is never replaced by a fresh one; when its work
  was finished another way, `wf handoff close` settles it.
- **A change can go to another branch, and to more than one (I-201, D62).** Named failure: a ticket was approved for
  master, and you asked for it on staging too ("commit and push straight to staging and master"). The workflow knew one
  target branch per repository, so the change was applied to staging by hand outside it; it conflicted, its checks failed,
  and it was thrown away. Now:
  - a ticket can be started on its own branch (`wf entry --target <repo>=<branch>`): it starts from that branch and is
    delivered there; the same ticket on main is a second, separate piece of work;
  - a ticket can name more branches its change goes to, when it starts (`--also-target`) or later
    (`wf target add <repo>=<branch> --reason "<why>"`, with your words when you asked). Once its own delivery is done, the
    workflow starts a port for each branch: the same change, carried over commit by commit, checked against the same
    acceptance criteria, then tested, reviewed, approved and delivered like any ticket. Once delivered, a port adds one line
    to the ticket ("ENG-1 is also delivered to staging.") and leaves its status where the first delivery put it;
  - when part of the change does not apply to the other branch, nothing is hidden: the port stops at that commit, says which
    files conflict and how much is left, and an implementer carries the rest over before the review.

- **The screenshots of any run export by its name (I-198, I-160, D55).** Named failure: a failed browser step kept four
  failed-case screenshots that `wf evidence list` showed, but `wf export screenshots --gate` said the last gate collected
  none, and roles may view images only through an exported copy: the implementer diagnosing the failure could not look at
  them. A gate stopped after its first failed case was refused the same way, and so were captures imported before any full
  gate. Now:
  - `wf export screenshots --run <run id>` copies every image recorded in that run (the run id is its folder under `gate/`
    in `wf evidence list`), whether it passed, failed, was stopped or was interrupted: the collected captures, the runner's
    failure captures in the step's scratch copy, and a reused step's captures from the run that took them;
  - `wf export screenshots --run import-<n>` copies an import's captures, before any gate and whatever the tree;
  - each copy is checked against its recorded sha256, as every export is, and says where it came from; nothing is recorded,
    and a run's outcome and the delivered set are unchanged;
  - when `--gate` finds nothing, it lists the runs and imports that hold images, and `wf evidence show` on an image names the
    export of its run;
  - the implementer handed a failed gate's repair finds that command, named with the failed run, in its `failedGate` facts.
- **A step that needs another step's output waits for it (I-163, D56).** Named failure: a full gate started browser-only
  proof steps while the Docker-leased steps that prepare their dependencies waited for capacity; a consumer failed in 0.2
  seconds because what it needed did not exist yet, and its producer later passed. A step now names the steps it consumes in
  `needs`: the gate starts it only after they finished in the same run, and one whose producer failed is recorded as not
  started, with why. A step another step needs always runs in the ticket's own worktree, never taken from another ticket's
  pass, so what it prepares is there. The adapter is refused when `needs` names an unknown step, the step itself, or a cycle.
- **A freed lease goes to the run that has waited longest, and every waiting run sees its place (I-157, D57).** Named
  failure: a small focused proof waited more than 35 minutes for the Docker lease while other live runs kept taking it,
  because whichever run asked first after a slot freed took it. Each waiting run (a gate step, `wf run --lease`, a step's
  preparation) now marks itself beside the lease's slots while it asks, and a free slot goes to the live runs in the order
  they began to wait; the gate's output, `wf status`, `wf resume` and `wf run` say `place 2 of 3 waiting`. Nothing is kept
  for a run that is gone (principle 8, reworded to say so): a mark whose process ended is removed, and one that is not
  refreshed for 20 seconds counts for nothing.
- **Delivering without the full test run is the person's one decision (I-158, D58).** Named failure: the person said "skip the
  full gate but do the review", and no recorded decision existed for it. `wf gate light-only --reason "<why>"` asks them in one
  plain question that says the answer covers the rest of this delivery, later fixes included, names the heavy steps that would
  not run on any of it, what passed on the code as it is now and what still runs. Answered
  yes, the gate runs the light steps and leaves the heavy ones out (one that failed in this attempt, or the ticket's own check,
  still runs; `wf gate --full` runs them all), the gate counts for delivery, the evidence reviewer is told what did not run,
  and the delivered comment says each step did not run by the person's decision.
- **A plugin step prepares its dependencies before the first commit (I-155, D59).** Named failure: a runtime plugin installed
  its isolated dependencies only inside a check or a gate, the step declared no `prepare` command, and `wf check` refuses
  uncommitted work, so lint before the first commit needed a contrived commit. A plugin may now give its default export
  `prepare(ctx)`: `wf run --step <id>` runs it as committed, on the worktree as it is, with the step's secrets, under the
  step's lease, its output masked, recording nothing (`prepare: false` says the step needs none). `wf doctor` warns for each
  plugin step with no preparation route.
- **A standard attempt runs only the specs its change can affect, when the step says which (I-134, D59).** Named failure: a
  one-line change reran a whole 1,200-test end-to-end step (27 to 40 minutes), and unrelated flaky specs blocked small fixes. A
  heavy step with `specs` may declare `affects: [{ paths: [<globs>], specs: [<globs>] }]`; when every changed file the step
  reads is a spec file or lies in a rule's paths, a standard attempt runs only those specs (with any suite that failed in the
  step's last run), records them as `affectedSpecs` under a key of its own, and the gate counts. A changed file under `specs`
  that a rule covers adds that rule's specs too. Any doubt (a file no rule covers, a spec-matching file no rule covers that
  other specs mention by name, as a helper, a barrel or a fixture they use would be, shared infrastructure, a changed contract, a change in another repo the step reads, an empty selection, `--full`, a
  batch) runs the whole step and says why.

- **A repair starts from what already failed (I-162, I-173, I-166, I-168, D51).** Four field cases, one shape: the workflow had
  shown a cause, and the agent sent to fix it was not told.
  - A full test run failed one step, then the owner stopped it to change the code the fix needed. Only a run that ended
    as "failed" was handed to the next implementer, and this one ended as "stopped", so it got nothing. Now a stopped run's
    failed steps are handed too, with why the run was stopped, and `wf resume` says so.
  - A quick check (`wf check`) failed on two lint lines, which the owner recorded as a bookkeeping item for that piece of
    work. The implementer handed the work again saw neither the failed check nor the item, and reran the whole check
    instead of fixing two lines. Now the last failed check is handed (`failedCheck`), each failing step with its log and,
    when it names no test, the end of its output; and open bookkeeping items reach every implementer (never a reviewer,
    and they still open no extra round).
  - A follow-up review kept a serious finding open with a new reproduction of the failure. The fix round was handed the
    finding as first written, about a case already fixed, and the implementer read it as done. Now the latest evidence
    that a finding is still open travels with it (`stillOpen`), beside its original words, to the implementer, the finding
    history and the next reviewer.
  - A review said it had not reached one check on a real device. After the base was merged, the next implementer was not
    told and reran checks that already passed. What a review did not reach now reaches implementers as well as reviewers.
- **A new criterion has someone to build it (I-165, D52).** Named failure: a change to the plan added a criterion while the

## 0.7.23 - Questions the person can read, one per finding, never asked twice

- **Why this release.**
  - **What happened.** The person answered one clear question: ship a ticket without proof that screen recording works
    on a real phone. Then they were asked seven more about the same gap:
    - six were one per review finding, each in the reviewer's own text ("waive recording_evidence_review_110:F1 (high:
      Neither candidate has ...");
    - one was about an issue that repeated them.

    They answered all seven in five seconds, "without really knowing yes to what".
  - **What 0.7.11 missed.** 0.7.11 promised plain words for every question. Only the strategist's escalations got them.
    Every question the engine asks itself still showed its own record:
    - a waiver, a gate-order override, closing as shipped, lifting a hold, adopting, a re-pin;
    - an item leaving a delivery, a rating lowered, a batch move.

    Measured on two projects: 62 of 76 questions carried no plain words. The optional plain line for an item leaving a
    delivery (`--explain`) was given 0 times in 18. No test checked that each kind of question had the plain form.
  - **Why the repeats.** Nothing let an answer decide more than its own question. The escalation's option itself said
    the owner would "present the six blocking findings ... for your explicit approvals".
- **One shape for every question (D29).**
  - **What the person decides,** in one sentence. The engine writes it from the facts it holds: "Should ENG-1 ship with
    a problem the reviewers found accepted as it is, instead of fixed?"
  - **The context, in plain words,** written by the owner agent: what happened, and what it means for the people who use
    the product.
  - **A technical line,** when one helps an engineer.
  - **A recommendation with its reason:** "Recommended: "No, fix it first", because ...". When it truly depends on
    something only the person knows, the question says what it depends on.
  - **Each choice** as a plain label, with what happens next, both written by the engine.

  The owner agent writes its part in an `--ask <file>` on the command that needs the person. Without it, nothing is asked:
  the refusal shows the question, its choices and the facts behind it, so the agent can write the words. A test reads the
  engine's source and fails if any question is created without this shape.
- **Each finding is its own question.** Several findings in one command are asked together, one question each, in the
  agent's plain line for each. The reviewer's text stays in the record, not in the question.
- **No question is asked twice.**
  - **An answer stands.** A "no", or an answer in the person's own words, is not asked again. When something changed,
    the owner withdraws the answer with what changed, and the next run asks a new question. Before, every run after a
    "no" asked it afresh. The one exception is the round-limit question, which must end in a choice: answered in the
    person's own words, it is asked again with its options. A gate-order question pending or answered before this
    release is the same question under the new key, so it is not asked a second time either.
  - **An escalation option names what it decides** (`settles: [{ ref, what }]`). Each item is listed, in plain words, in
    that option's description, and an item the project's rule fixes before shipping says so ("a medium issue, which your
    rule normally fixes before shipping"). Once the person picks it, those items are recorded under their answer with the
    usual commands, with no new question. The answer is never used up by them, so it can still be withdrawn.
  - **A finding a later review raises again about a gap the person already accepted** is recorded under that answer with
    `wf scope waive --finding <id> --same-as <their decision> --reason "<how it is the same>"`. It must block for the
    same criterion or invariant, and both must carry the same family; anything else is its own question. The delivered comment words it as the finding the person accepted.
  - **A gate-order approval holds across a base merge that leaves the ticket's own change alone (I-180).** The approval
    is keyed by the ticket's change and by what the gate order still owes, not by the whole tree. The ticket's change is
    compared without blob ids and hunk line numbers, so lines merged in above it no longer make the reviewed change look
    new. A change to the ticket's own lines, or to what is owed, is a new question.
- **Typing an answer counts as much as picking one.** The person's rule: "why are you stopping me from just typing no, why
  do i have to answer the questionnaire? both should be accepted". The person typed "ok fix all and continue" to the
  round-limit question. It was refused twice, then the session put the question panel in front of them. Two causes: a typed
  reply counted only when it began with an option, and only after a message that had quoted the question exactly; this
  session had explained it in its own words.
  - **Sessions ask in their message** (the engine's question is now written for the person), so the person can just type.
    The question panel is optional, and a typed reply and a panel answer both count.
  - **A reply chooses when it names one option anywhere** ("ok fix all and continue" is continue). It can name the
    option in several ways:
    - by its label, with or without a leading "yes, " or "no, " ("fix it first");
    - by a short name the engine gives each option ("fix it", "ship it", "run the tests", "keep it paused"), typed in
      the chat, the panel's free text or the terminal;
    - for a yes-or-no question, also "ok", "sure", "go ahead", "nope" and the like.

    What else the reply says is kept beside the choice. A reply is the person's own words, not a choice, when:
    - it asks something back;
    - it names two options;
    - it negates or conditions the option it names, before it ("don't continue", "decide whether to continue") or right
      after it ("continue is not an option");
    - it makes an exception, or a time, that could turn the answer around ("fix it here unless it is already in another
      ticket", "ship it after the fix", "lift it once the review is in"). The session then asks what they mean. A
      condition that does not move the action stays beside the choice ("yes, but keep the old button" is yes).
  - **A reply to a message that explained the question in the session's own words** binds when that message named the
    question by its id (`ENG-1.1 A2`) and no other, it is the attempt's only open question, no reply answers the quoted
    question, and the reply names an option plainly: by its label or short name, or by a choice other than yes or no when
    the message also showed an option's label. A bare "yes" there says nothing about which question it
    answers, and a message that never named the question binds no reply, so a "stop" said about something else is never
    taken as the answer.
- **The delivered comment lists what the person accepted.** A waived finding was in no line of the delivered comment. Now
  it reads "Accepted without a fix: ...", and an item an escalation answer decided names that answer.
- **Other fixes.**
  - A strategist's escalation asked again (after an answer in the person's own words, or a withdrawal) kept its plain
    words; before, it showed the strategist's rationale.
  - The round escalation (the review-round limit) carries the owner's brief and recommendation in its question.
  - A strategist's escalation names a recommendation, or says what the choice depends on.
- **Live attempts.** The question shape applies to every question asked from now on, in every attempt (D29: showing
  each question in plain words was always owed). A question already pending keeps its words; the owner may withdraw it
  and ask again with `--ask`.
- **Combined deliveries (batches).**
  - **A finding the person answered "fix now" after the parts were combined can be fixed (I-177).** Once a batch is
    assembled, its members are locked. A member's observation answered "fix now" then had no route: a move into the
    batch was refused, `wf scope fixed` needed a commit on the locked member, and the advice to eject and re-add would
    have dropped the batch's own commits. Now `wf scope move --finding <ref> --sibling <batch id> --attempt <member>`
    moves it into the batch. The batch gets it as an issue it must close before delivery; its implementer fixes it and
    `wf discovered close --fixed` closes it. The member stays locked.
  - **An eject that would drop the batch's own commits is refused.** It now goes ahead only with `--drop-own-commits`,
    which records the dropped commits. The delivery refusal no longer advises eject and re-add when it would lose work.
  - **A batch is never asked for a tracker step (I-178).** A batch has no ticket of its own. A 0.7.20 ledger could still
    ask one to move its ticket to In progress, and a numbered quick fix could be asked the same. Those old entries no
    longer count.
- **A gate that only runs a check a reviewer asked for is no longer stuck (I-179).** An evidence review found a required
  check was never run in the gate. The owner registered it, and the next code review rightly kept the finding open until
  the check runs. The gate then refused because that finding was not verified, so only the person's override let it run,
  and the override was asked again after a base merge (I-180, above). The gate order no longer waits for such a finding:
  it raised on an evidence review, a check for its criterion was registered after, and the latest review kept it open with
  evidence. Acceptance still waits for an evidence review that verifies it. `wf resume` names that evidence review.
- **Known, not fixed here (I-181).** Abandoning an assembled batch leaves its members tied to it: they can be neither
  delivered alone nor batched again. Until it is fixed, do not abandon a batch; eject its members first.

## 0.7.22 - Plans written by two planners who agree on one

- **A planning panel writes the plan.** The plan is now written by two planners instead of one. They draft blind, then
  agree on one plan before it is frozen:
  1. **Draft.** Each seat writes the whole plan blind, at the same time as the other, and neither sees the other's draft.
  2. **Merge.** Seat 1 reads both drafts and writes one plan. It lists in `disagreements` every point where the drafts
     differ in what is built or how it is proven, with what it chose and why.
  3. **Confirm.** The other seat reads the merged plan and its disagreements against its own draft. It agrees, or objects
     point by point with its reasons, and an objection sends the plan back to the merge. Its agreement freezes the merged
     plan; the freeze records the drafts, the merges and the verdicts that made it.

  Each step is a `wf handoff planner` and a `wf plan --from-agent`. `wf resume` names the next step: which seat, which
  agent type, and which agent to continue. No round count is capped; the owner judges convergence as for review rounds.
  Other cases:
  - **The merged plan is refused at the freeze** (its queries no longer match after a base merge, or it misses an
    obligation). The panel goes back to the merge, with the engine's reason as its objection.
  - **A seat's planner is gone.** It is replaced with `--seat <n>`.
  - **A dry run** (`wf plan --check --file <f> --agent <id>`) records nothing, a verdict included.
  - **A step recorded out of order** is refused as the owner's mistake and not handed to the next planner as a refused
    plan.
  - **A plan replaced whole after an upgrade** is planned by a panel too.
  - **A lane without a planner** (quick, batch) has no panel.
- **Models.**
  - The planner has its own class, `planning`: Claude `fable`, Codex `gpt-6-astra`, high effort.
  - Claude's second seat is the `review` class (Opus), so the two plans come from different models. Codex's second seat
    repeats the planner's class (Astra twice).
  - A project sets `roles.planner.panel: [<class>, ...]`; a single class plans alone, as before.
  - `wf sync` writes an agent per seat class (`wf-planner`, `wf-planner-review`).
  - `wf doctor` checks each seat's model.
- **Two engine-launched roles at once.** `wf handoff run --agent <id> --detach` returns once the role has started, so a
  Codex owner runs both drafts at the same time and follows each with `wf handoff wait`.
- **Live attempts.** Attempts admitted before 0.7.22 keep the planning they started with: one planner at the `review`
  class.
- **What it costs.** Four planner turns instead of one: two drafts at the same time, then a merge and a confirmation.
  With the default panel, two of those turns are Fable's.

## 0.7.15 - Less waiting

An audit of one project's 19 recent tickets found that most lost time was waiting, not gates or reviews. Implementer
sessions were parked idle for 3,092 of 6,787 minutes. Owner sessions sat idle for 2,542 minutes. Finished implementers
waited 5,772 minutes to be closed. One long ticket's lessons are folded in too (D25).

- **An approved correction counts once per project.** A correction of an admission check that the person approved in

  plugin code. Two checks had been corrected 7 times across 5 tickets, each time waiting 28 to 147 minutes for the same
  answer. Each ticket still gets its fresh review and gate.
  - An approval counts only while it stands. A correction the person later replaced is not taken again, and a `no` the

  - The command says when it took an earlier answer, and whose.

  - whenever a turn starts again, finished roles are acted on first.
- **A completed launched implementer is closed by the engine** when its work is committed and its report written, with
  every check `wf handoff close` makes. The ledger records that the engine closed it. Otherwise it stays open and the
  owner is told why. Finished implementers waiting
  to be closed had cost one ticket 40% of its implementer time.
- **A re-plan is measured from the re-plan.** Its expected minutes and rounds are compared with what happened since it.
  The whole attempt is compared only with an expectation the plan itself stated: a small repair's 65 minutes had been set

- **Criterion churn and repeating issues are shown.** `wf signals` and `wf resume` show plan amendments with how many
  criterion texts were rewritten (one ticket rewrote 163 while its criteria count barely moved). A discovered issue can
  name its `family` (`wf discovered add --family`, or `family` on a report's `left` item), and two or more open issues
  of one family are shown as a class to fix in one sweep.
- **Gate queue time is recorded.** A step's wait for a lease slot held by another gate is stored with its result, and
  the gate says how long steps waited. 22% of one project's gate time had no step running, with no recorded cause.
- **A gate warns about open discovered issues;** fixing them changes the tree it proves.
- **`wf status` is fast on large projects.** It runs one `git fetch` per repository per command, and reads a commit's
  lesson files once. Over 25 open tickets it took 52 seconds instead of 6 minutes.
- **`wf signals` counts an ended ticket's minutes to its delivery,** not to now.

## 0.7.14 - The person's rules reach the agents

The person's rules on test runs and gates were kept in a maintainer's notes rather than in the texts the agents read. One
implementer spent 266 minutes on a 90-minute estimate: 201 of them in sleep loops waiting for its own background runs of a
573-test end-to-end spec, run under load it added itself, after 20 and 30 targeted repeats had already proven its two fixes
(D24).

- **Implementers:**
  - Confirming a cause means the failing tests alone (repeated when intermittent). A whole spec file, a full end-to-end
    run or a repeated typecheck is the gate's run, never theirs, in every round. So is any run under load they add
    themselves.
  - A failure seen only on a loaded machine is reported as that, not chased.
  - They never wait on their own runs in sleep loops.
  - A failure in files they did not touch is reproduced on a clean base first, then fixed anyway.
  - Tests only for an invariant or a regression no existing test catches; no tests of source text.
  - No backticks or `${}` inside double-quoted shell arguments.
- **Owners:**
  - A role past its estimate is judged by what it is running, not by whether it is active.
  - Before the gate, a moved base is merged and the failures already known on it are fixed.
  - The person's scope words are taken literally.
  - Items left as follow-up work go into one ticket.
- **`wf signals`** shows, for each working role, the command it is running now and the time it spent in tool calls of
  5 minutes or more, with the longest, on both harnesses. Codex polls on a long command count toward that command. The
  owner sees "208 min in 23 commands; longest: a sleep loop" while it happens. The strategist's stored bundle leaves the
  commands out.
- **Plugin updates reach running sessions without a restart.** When a role's file changed after the owner's session
  started (a plugin update), the role's bundle points it at the current file, which it reads first. It keeps the
  session's own tools and permissions. `wf sync` no longer asks for restarts.
- **Planners:** a contract names shared test helpers and fixtures; work items that edit one hub file run in sequence.
- **Reviewers:** a skill the project requires is applied to the evidence it covers, not only named.
- **Plugin development:**
  - A rule the person gives lives in the texts agents read.
  - Experience reviews run on the strongest model, briefed with the threat model.
  - Nothing reruns that cannot add information.
  - A maintainer release goes to main after a green verify, with no pull request.
- **The scenario suite keeps only tests that catch an engine failure.** 26 tests are gone:
  - 12 only matched the wording of one role text, skill or doc. One of them failed a release verify after an intended
    wording change.
  - 14 repeated what another test asserts; each one's unique assertions were moved first.

  Generated role files are checked for structure, and long message regexes give way to the refusal ids the engine
  records. Kept: the checks that every text states the same severity scale and blocking rule, that no text repeats a
  claim the engine retired, and that agent texts name commands and links that exist.
- **An interrupt during a role's launch ends the role.** A stop that arrived after a role process started but before
  `wf handoff run` was listening killed the command and left the role running with no owner. It is now held until the
  command listens, and then the whole role tree is ended. This was found by the Linux verify under load.

## 0.7.13 - Quick fixes take minutes

- **A quick fix's gate runs the light steps only (D23).**
  - In the quick lane the gate runs lint, types, unit and build of what the fix touched, and reuses steps whose inputs did
    not change. Heavy steps, such as end-to-end suites, are recorded as skipped.
  - That gate counts for acceptance and delivery. The independent review stays, and its bundle lists the steps that did not
    run (`gate.notRun`), so the reviewer judges whether the change needed them.
  - A heavy step with an identical pass is reused, and one that failed in this attempt runs on every gate until it passes,
    whatever the fix changed: a known failure is never skipped into a pass.
  - `wf gate --full` runs the heavy steps as well. A heavy step the attempt froze as a validation of its own always runs.
  - This is the plugin's default. A project whose quick fixes should run every step sets `gate.quickLane: full` in its
    adapter.
  - Screenshots for a quick UI fix come from captures made by hand on the committed tree (`wf captures import`).
- **`npm run verify` does not run a tree again that already passed.** A clean tree that passed every leg on this machine
  (same tree, node and container image) returns at once, so the pre-push hook no longer repeats an 11-minute run that
  just passed. `WF_VERIFY_FORCE=1` runs it anyway.

## 0.7.9 - The workflow learns a project by working in it

- D19: one project had 70 lessons, all `proposed`, 16 recurred and none ever curated. Recurrences were counted only
  when a reviewer volunteered a verdict, and merging, promoting and retiring lessons waited for a person. The lessons
  were narrow (one per ticket), so a repeated mistake was spread over near-copies, and every lesson that had recurred
  once passed the bundle cap. Learning is now automatic, and it changes only what roles read and in which order.
  - **At review acceptance** a classifier labels what the attempt taught:
    - each finding any round raised: which lesson's mistake it repeats, or none;
    - each new or never-compared lesson: which other lesson describes the same mistake, or none.

    The classifier is a cheap model given fixed choices, with no tools and no reasoning: Claude `haiku` and Codex
    `gpt-6-luna` by default. A project pins its own per runtime in the adapter's `learning.classifier`, or turns it off
    with `learning: { enabled: false }`; `WF_LEARNING=off` turns it off on one machine. `wf review accept` says what it
    learned. A failed classifier is one line in `wf status` and never fails an acceptance.
  - **Recurrence and ranking.** A repeat counts as the lesson's recurrence, once per lesson per attempt. Bundles rank
    lessons by evidence: most recent repeat, then most repeats, then carried in the fewest attempts. Only enforced
    lessons pass the cap now.
  - **Merges.** `wf resume` names lessons that describe one mistake where they can be merged (an open attempt that holds
    their repos, before its review is accepted), and the owner merges them there:
    `wf lesson merge <ids> --title "<the one mistake>" --attempt <id>`. The merge is committed, reviewed and delivered
    with the attempt; the members are retired with `mergedInto`, and the merged lesson keeps their ranking evidence. A
    merge one attempt made is not proposed to another. `wf lesson distinct <ids>` (with `--attempt` for a lesson still in
    an attempt) tells the workflow the classifier was wrong: no merge of them is proposed again. A lesson recorded from a finding is never counted as that finding's repeat.
  - **What the person chose.** Items the person chose to fix when asked whether they could leave (`fix now`, or their
    own words) reach later reviewers as `severityScale.personFixed` (the 20 most recent): examples to rate by, never a
    rule.
  - **Estimates.** Each delivered attempt's prediction beside what happened reaches later planners and strategists as
    `pastEstimates`, per lane. It never reaches an implementer or a reviewer (D9).
  - **Where it lives.** The measurement is in the project's git-excluded `.workflow-maintenance/learned.jsonl`; lesson
    text stays in the repositories.
  - **Limits.** Nothing learned asks the person, stops, refuses, lowers a rating or changes who lets an item leave.
    A change from the improvement inbox now passes an experience review before it ships (CONTRIBUTING).
- I-130: a lesson recurrence found at or after acceptance wrote the lesson file in the pull-only main checkout. A
  recurrence is no longer written into any lesson file: the file keeps the count it was committed with, and
  `wf lesson list` shows the learned count beside it.
- I-131: scenario runs wrote refusals from temporary projects into the person's own refusal log (138 of 335 entries in
  one log), which `wf refusals` and plugin triage then read as real use. Every scenario process now keeps its user-level
  state (refusal log, inbox, registry, leases) in its own temporary folder.
- I-127: after an analysis attempt was upgraded to implementation, fresh planners got the analysis plan and no word of
  why it changed. They could only amend criteria, and an amendment that carried only `plan.summary` was accepted and
  then dropped.
  - Planners now see the attempt's `intent` and its `intentChanges` with the reason.
  - Until the first implementer is handed, `wf plan` replaces the analysis plan whole (`replacesPlan` tells the planner).
  - `wf handoff planner --context "<text>"` (or `--context-file`) carries the person's words to the planner, recorded
    with the handoff.
  - An amendment field no amendment applies is refused rather than silently dropped when it would be lost (a plan file
    sent again with its plan and survey as frozen is still accepted; attempts admitted from 0.7.9).
- I-129: the outside-plan list ignored anchors written `<repo>:<path>`, and the files an accepted impact amendment's
  survey brought into scope. Both now count, in the owner's warning, the reviewer's bundle, the signals and the
  strategist's plan files (the plan's own survey lists what the change reaches, so it still does not count as planned).
- I-128: `wf handoff stop` recorded a role as stopped while its native process tree kept running.
  - The stop now ends the whole tree: the role's process group, every descendant, and children that left the group.
    It escalates to SIGKILL, and records `stopped` only once every process is observed gone.
  - When something cannot be signalled, it says so, names the processes and records nothing.
  - A recorded pid the system has given to another process since (it started well after the launch) is left alone: the
    launch is recorded stopped and nothing is signalled, and `wf handoff wait` does not follow it. A pid seen in the tree
    that moved to another group is not ended either.
  - An interrupted foreground `wf handoff run` ends its tree the same way, and reports a launch it could not end as
    still running.

## 0.7.0 - Goals, not methods: agents own outcomes and predict, the engine checks facts, the owner decides

Measured on real tickets before this release: 33 attempts, 5 delivered; one ticket ran 47 review rounds over seven days
and used 59% of all tokens; reviewers found about two issues per hundred tool calls on every model, so the stop rule
"a fresh blind reviewer finds nothing" never fired on a large change; growing a ticket was free while shrinking it needed
the owner's typed phrase; agents were briefed with methods and fences ("work only in", "run only", verdict forms), so each
delivered its box and the next role discovered the rest. This release changes how agents are briefed and how the loop
stops, not the facts the engine checks.

Decisions (docs/DESIGN.md, decision register): placement is not obligation (D1); a finding blocks only for a reason the
engine can check (D2); a strategist may contract work (D3); the owner's reserved decisions are one command (D4); the
engine may launch roles (D5); agents are fallible, not adversarial (D6); releases never add obligations to attempts
admitted under an earlier version (D7); the harness is an execution detail behind one adapter per host (D8); agents
predict, the engine compares and the owner judges, so the engine judges no work against a number it picked (D9); what
may leave a delivery is decided by severity, the person's rule (D10).

- Goals, not methods. Every role (planner, implementer, reviewer, strategist) is briefed with its goal, what good looks
  like, what it decides alone, its guardrails and what the engine checks; bundle instructions are goal statements. The
  implementer owns its criteria on the whole combined tree and may fix anything its change causes or exposes without
  asking. Every role analyzes before deciding: the cause and the class of a problem, the options, the choice and its
  reason. The project's quality bar (adapter `quality:`) reaches every role as standing goals.
- Facts at the boundaries, forms gone. Reviewer verdict forms (rules, lessons, design-system hits, discovered items,
  seams, supplemental validations, files outside the plan) are context; any verdict given is still recorded. Sweep
  answers, owed impact updates and files outside the plan are information, not refusals; `doNotRun` no longer restricts;
  survey columns are context. Kept: criteria evidence, located findings, prior findings verified, anomalies and every
  screenshot inspected, the gate on the reviewed tree, the combined-tree `wf check` before a review of several work items.
- Structured implementer report: the implementer writes its report file early (approach, expected minutes) and completes
  it at the end; `wf handoff close` records what it changed and why, what it ran, its proofs and what it left, and every
  item it left becomes a discovered issue, whichever harness ran it (the old transcript scan was Claude-only and stays
  for attempts admitted before 0.7.0).
- Review rounds: a full blind audit runs at most twice per attempt, at its first review and its first evidence review;
  every other round, an evidence review after a fix included, is a delta review of the diff since the last reviewed tree,
  handed the open findings (and, for an evidence review, the new gate evidence). A finding blocks only when it cites a
  frozen criterion the change fails, regresses a line the attempt changed (in a delta: since the last reviewed tree),
  breaks a critical invariant, or (full rounds) cites nothing checkable, and is rated medium, high or not at all; a
  finding rated low never opens a round. Everything else is an observation that delivery waits for: fixed (verified by
  the next reviewer, or `wf scope fixed` with a commit made after the finding), moved to a sibling attempt, ticketed or
  left for later as a known issue. In a batch, a line a member's accepted commits wrote is that member's: only lines the batch wrote
  open a batch round. Findings carry a `family`, each fixed at its cause with one proof (`--sweep` is optional);
  implementers' own lint and fixture fixes are `--kind bookkeeping` and never reach a reviewer. Reviewers have no effort
  budget; delta scope bounds a review.
- What leaves a delivery (D10, the person's rule): a review finding or discovered issue rated high (or unrated, or citing
  a criterion or invariant) is fixed in this delivery, here or in a sibling attempt of the batch, and leaves only with
  the person's `wf approve`; medium is the owner agent's or strategist's judgement with its reason recorded; low may be
  ticketed, or left for later as a known issue listed in the delivered comment (`wf scope defer`). `wf scope ticket
  --finding a,b` files several under one ticket; every reviewer sees what left (`followUps`). A blocking finding is set
  aside only by the person, whatever its severity: waiving, ticketing and deferring it are all `wf approve`. A finding on a line the attempt changed is fixed in that
  attempt (a sibling starts from the base and has no such line), so `wf split` and `wf scope move` keep it.
- One severity scale for every reviewer and implementer, in their templates, the work skill and the AGENTS block: high =
  a user, a tenant or the business is harmed or blocked (wrong or lost data, a broken flow, security, money, a visible
  defect on a primary screen); medium = degraded but usable (a secondary flow, an edge case, a confusing state); low =
  polish (wording, spacing, naming, style); a tenant-isolation, authorization or money defect is always high. A later
  independent reviewer verifying a finding still open may re-rate it in `priorFindings` (`severity`); the latest rating
  decides where it may go. A discovered issue is rated with `wf discovered add --severity`, made high by `--invariant
  "<which>"` (or `invariant` on an implementer's `left` item), re-rated with `wf discovered rate <id> --severity <s>
  --reason "..."` (raising is free, lowering records its reason and, out of high, needs the person's `wf approve`), and several close under one decision (`wf discovered close
  D1,D2 --deferred`).
- What the second final review changed: an evidence review inspects only the screenshots whose sha256 is new since the
  last recorded inspection (`gate.screenshots` marks each `inspectedBefore`; `screenshotsInspected` lists the ones it
  viewed); `wf scope fixed` needs a commit made after the finding was raised, a later reviewer's `open` verdict undoes it,
  and a high observation settled with it still needs a reviewer's `fixed` before delivery; the person's `deliver-core`
  answer covers only the findings and discovered issues recorded before it; a delta round counts only the attempt's own
  lines (what a base merge brought in is not its change); before the gate `wf resume` names the open observations to
  place now; after an evidence review's blocking findings are fixed by the implementers handed after it (each
  closed, the tree what they left, no scope added since), `wf gate` runs without the person's approval (every other out-of-order gate still needs `wf gate --reason` and
  `wf approve`); an implementer's goal includes reviewing its own diff against the criteria, the quality bar and the
  invariants before it reports; anomaly `assertions` (a test that pins a value) are optional context.
- Predictions instead of limits: the plan states what it expects (`plan.expect`: files, review rounds, minutes), an
  implementer its approach and expected minutes, a reviewer its scope and expected minutes. `wf resume`, `wf status` and
  `wf signals` show each beside what happened, with no threshold and no refusal. The owner agent compares them at each
  round boundary and hands the strategist (`wf handoff strategist --reason`) or re-plans when the course diverges; the
  strategist chooses continue, consolidate, cluster, delta-review, split, ticket, model or escalate, each with its own
  prediction, and two missed predictions in a row make its next decision an escalation. The plan must state its
  prediction; when an actual passes its own role's estimate, the `next:` line of `wf resume` says so first and asks for
  a judgement. The engine stops only at the person's escalation after 10 handed review rounds (recorded or not; batches
  included; continue for another 10, split, deliver the core, stop) and a strategist's escalation, both answered with
  `wf approve`. Every course line separates work from waiting: a finished role shows the minute it was last active, the
  attempt its longest stretch with nothing recorded. `wf report` adds, across tickets, the median of actual over
  predicted for files, rounds, minutes and implementer minutes, so predictions can be calibrated.
- A role the engine launched never traps the owner: `wf handoff run` returns when the role ends, or once it passes the
  estimate it stated itself while it keeps running in its own process; a role that states none (the planner, the
  strategist) is given the owner's own at launch (`wf handoff run --minutes N`). The owner then judges it (`wf handoff
  wait [--minutes N]` with its own new expectation, or `wf handoff stop` and a fresh handoff).
- `wf split` moves work items, criteria, observations or discovered issues into sibling attempts of one delivery batch; a
  moved finding becomes the sibling's discovered issue, and the sibling states its own expectation when it re-plans.
  Split is a planning tool: built code stays with its attempt. A strategist `model` decision runs a role's next handoffs
  at another work class of the adapter (with the models that class pins).
- Harnesses are an execution detail: everything specific to Claude Code or Codex sits behind `engine/hosts/` (one adapter
  per harness, the same capabilities); the workflow logic names no harness, and a new harness is one adapter file.
- Review groups (a large full audit divided by recorded flows) keep their facts (every part recorded on the current
  snapshot, parts immutable, the integration closure after them, the criteria evidence) and drop their forms: no
  per-file `filesReviewed`, per-interface `interfacesReviewed` or per-part `partReviews` lists are required.
- Deferrals are listed automatically at delivery and in the delivered comment (severity, reason, who decided);
  `--acknowledge-deferrals` is gone.
- Owner authority: `wf approve <id>` at the person's own terminal replaces the owner-phrase grammar and the owner-session
  command matcher; approvals are used once. Reserved: waiving a blocking finding, overriding a failed gate, moving a
  caused or critical-boundary defect out of the batch, lifting a hold, adopting from a live owner, escalations. The guard

- Dead ends: orphaned attempts (worktree gone) show in `wf status` and abandon cleanly; a dead process's evidence lock is

- Quality bar in every project: `wf init` drafts `quality:` from what the project documents (its design system, the

## v0.5.0

0.5.0 changes the order of work, adds impact analysis before planning, measures every review round and gate stop, and closes the delivery-adapter fault cases. Several commands that used to pass now refuse; read **Breaking behaviour** before upgrading a project with open attempts.

### Breaking behaviour

- **Reviewer closures need `anomalies` when screenshots are handed (I-12).** When the bundle hands screenshots (`gate.passedOnThisTree`), the closure needs `anomalies`: `"none seen"`, or per anomaly the screenshots, the observation and either a finding id or the investigated `cause`, its `evidence` and the test `assertions` that pin the value. `wf review` refuses a closure without it.
- **`wf stop` needs `--class` and `--reason` (I-23).** `--class major-finding|tree-change|owner-decision` is required; a stop without it, with another class or without a reason is refused.
- **`wf gate` follows the order of work (I-27).** It refuses while the latest review round has open or unverified findings, while no review round covers the current tree, and while a reviewer is still at work. `wf gate --reason "<why>"` runs it anyway and records `gate.override` in the ledger.
- **No review round starts while an implementer handoff is open (I-23).** `wf handoff reviewer` refuses until every implementer handoff of the attempt is closed with `wf handoff close --agent <id>` (`--outcome stopped` for one you stopped); `--reason "<why>"` hands the tree anyway and records `review.override`. `wf handoff close` with the default outcome `done` refuses uncommitted work. Attempts admitted before 0.5.0 have no implementer events and are not blocked.
- **Impact survey and impact map are required for full-class work (I-26).** A plan for an attempt with any `full` work item (the adapter's `impact.requiredFor`) needs a `survey` before the design and an `impact` map after it, every list backed by a structured query whose hit count `wf plan` re-runs and checks. An amendment that adds scope owes an impact update before the next implementer handoff; the reviewer closure needs `impactChecked` when the bundle has an impact map; a fix handoff while review findings are open needs `--sweep` (I-25).
- **The delivery adapter's `observe` (and `readback`) are called on every retry (I-20).** A retry of `wf deliver` asks the adapter again even when the change is already on the target branch; a post-merge state other than `integrated` or a pending one refuses until the owner runs `wf deliver --acknowledge-adapter-state <repo>:<state>`. An adapter whose `observe` is not safe to call again must be made so.
- **Agent-reported attachments need `assetUrl` (I-11).** `wf tracker record --agent-reported` counts a delivered screenshot only by the `assetUrl` (https) reported for its upload, embedded as `![<title>](<assetUrl>)` in the comment; a report without it, a leftover `{assetUrl:...}` placeholder or a link instead of an image is refused.
- **`wf report --json` is a versioned document (I-24).** It prints `{ "schema": "agentic-workflow/report@1", "generatedAt", "attempts": [...] }` instead of a bare array; `findings` counts every finding of every recorded round, and `repairRounds` counts rounds that raised findings (failed gates are `gateFailures`).
- **`wf doctor` fails without an explicit planner and reviewer model (I-25).** The planner and the reviewer run at the `review` class, which pins the strongest Claude model; a project whose planner or reviewer resolves to a class that pins no Claude model fails doctor until it sets one.
- **Delivery needs the owner's summary when there are screenshots, even with no template (I-11).** With no delivered comment template, a delivery with screenshots posts the built-in delivered comment that embeds them, so `wf deliver` asks for the owner's summary first (`wf deliver --summary-file <f>` or `wf summary --file <f>`).
- **Owner-only decisions take the owner's own word, never a flag.** `wf gate --reason`, `wf handoff reviewer --reason`, `wf handoff close`, `wf deliver --acknowledge-adapter-state`, `wf deliver --repin-adapter`, `wf deliver --acknowledge-deferrals`, `wf deliver`/`wf reopen --no-lesson`, `wf shown`, `wf abandon --acknowledge-integration`, `wf release` and `wf adopt` now refuse unless the owner gave the decision: for an attempt owned by a Claude Code or Codex session, an owner message in that session starting with the decision's phrase (`override <attempt>:gate`, `override <attempt>:review`, `close <attempt>:<agent>`, `acknowledge <attempt>:<repo>:<state>`, `repin <attempt>:<tip>`, `acknowledge-deferral <attempt>:<id>`, `waive-lesson <attempt>`, `shown <attempt>`, `abandon <attempt>:<repo>:<state>`, `release <attempt>`, `adopt <attempt>`), each message counted once across the project and spent before the action; `wf handoff close` also when the owner session itself ran exactly that command. For an attempt owned by a person's name, the phrase is typed back at a real terminal outside any agent runtime (`interactive-terminal (unverified)`). See docs/trust-model.md, "Owner-only decisions".
- **Impact queries fail closed.** A text file over `impact.maxFileBytes`, an unreadable object, a missing worktree or any git failure refuses the query instead of counting it as no hit; `impactChecked.unlisted` is needed when the bundle lists only the first 100 outside callers.
- **`wf abandon` refuses a change that landed or may land.** It refuses while a repo's change is on its target branch, and while the delivery adapter last reported an integration as anything but `rejected`, until the owner acknowledges it with `--acknowledge-integration <repo>:<state>`.

### The order of work (I-27, I-23)

- Code-review rounds run to clean with no gate; then one `wf gate` on the reviewed tree; then the evidence review of the gated tree (logs and screenshots). Review and gate never run side by side: `wf handoff reviewer` refuses while a gate runs or starts (the two share the gate lock), and `wf gate` refuses while a reviewer is at work. Bundles mark the round as `code-review` or `evidence-review`.
- `wf stop` records the class, the reason, the interrupted step minutes (`discardedMinutes`), the wall-clock minutes (`wallMinutes`) and the steps finished. A gate stopped for a finding or a tree change goes back to the implementer and a code-review round; one stopped on the owner's decision resumes with `wf gate`.
- A closure refused because the tree changed during the round leaves `review.refused` and ends the round.
- An implementer handoff now stays open until `wf handoff close`. The handoff output, `wf resume` and the work and quick-fix skills say to close it; the reviewer handoff refuses while one is open.

### Impact analysis and pattern sweeps (I-26, I-25)

- The planner surveys what exists (components with their behaviours, consumers, flows with failure paths, defect patterns) before the design and maps the impact of the chosen design after it. Queries are data (`pattern`, `kind: literal|regex`, `repo`, `paths`, `exclude`), run by the engine over committed trees, never a shell. `wf impact run` re-runs them.
- The reviewer bundle carries the impact map, an inventory to sample and the callers of changed symbols the map does not list; the closure's `impactChecked` answers each, and findings outside the map carry `category: impact-gap` (counted as `impactGaps` in `wf report`).
- A fix handoff names a pattern sweep per open finding; the implementer answers each in a `Sweep <id>: fixed|clean - ...` trailer before the next review.
- `wf handoff` and `wf criteria amend` warn when a plan `doNotRun` or `externalServices` entry names a repo or step the diff now touches.

### Telemetry (I-24)

- New ledger events: `review.round`, `gate.stopped` (class, interrupted steps, discarded and wall minutes, whether a reviewer was open), `implementer.opened` and `implementer.closed`, `subagents.attributed`, `scope.changed`, and failing test names on every failed gate step.
- `wf report` shows phases, idle gaps, gate and round counts, findings by severity, scope growth, tokens and cost per model and handoff (from `engine/prices.yaml`, with user and project overrides). Every field: docs/telemetry.md.

### Delivery adapter faults and visible screenshots (I-20, I-21, I-22, I-11, I-12)

- The last state an adapter reported is recorded (`repo.integrating`) and every retry asks the adapter again; post-merge states need the owner's acknowledgement of that repo and state.
- `wf deliver --repin-adapter <tip> --reason "<why>"` re-reads the delivery adapter from the pushed tip of its base branch for an attempt that has not delivered everything, only forward, only when the adapter files changed, after showing the owner both pins, the changed files, the remote and what is left. The gate, review and tracker stay on the admission pin.
- Screenshots are embedded in the delivered comment, never only attached; reviewers account for anomalies in what they see.

### Security review of the 0.5.0 changes

An adversarial pass over every change to `engine/attempt.mjs` and `engine/lifecycle.mjs` on the four branches, with scenarios in `scenarios/security-0.5.test.mjs`:

- `wf abandon` no longer abandons an attempt whose change is on, or can still reach, its target branch.
- A delivery adapter's results can no longer overwrite the engine's `repo`, `commit`, `target` or `skipped` in the delivery record, or the worktree the adapter is called with.
- Adapter code (delivery, tracker and step plugins) is materialised from a commit id, inside the adapter folder, without following a planted link or a linked folder. The re-pin reads where the adapter lives from the adapter at the current pin, never the working tree's copy.
- Impact queries take their repos and read limits from the adapter at the attempt's base; a regex query runs in a child process stopped after `impact.regexTimeoutMs` (20 s by default), so a backtracking pattern cannot hang the engine.
- Agent-reported upload urls are recorded without their signed query string; sub-agent metadata entering the ledger is bounded.
- Owner-only decisions (above) are taken from the host-recorded owner message; the owner session's own command counts only for `wf handoff close`, exactly matched, fresh and once; a person-named owner confirms at a real terminal with no agent runtime among its ancestor processes. This is best effort against a same-user forger, stated plainly in docs/trust-model.md.
- Impact queries refuse every partial read (oversized text, missing object, missing worktree, truncated `git cat-file` answers) and the reviewer's bundle is read strictly.

### Adversarial review of the integrated branch

A second adversarial pass over the integrated 0.5.0 branch, with scenarios in `scenarios/security-adversarial.test.mjs`:

- **Trust decisions never fall back to the working copy (high).** Impact queries and `wf plan`/`wf criteria amend` caught a failure to read the adapter at base and went on with the working tree's `.workflow/project.yaml`. An uncommitted `adapterRepo` edit made that read fail, so a query could read any checkout the working copy named (a count oracle over its secrets), and `impact.requiredFor: []`, `roles.planner: false` or an invented class skipped the impact analysis or the planner. Admission now records where the adapter lives; every decision that judges the attempt (planner, impact, classes, roles, repos, query repos and limits, rules, lessons, gate steps, evidence steps, delivery targets, delivery and tracker adapters, abandon's target check) reads the adapter at base from that record and refuses when it cannot be read or no base is recorded.
- **`wf adopt` needs the current owner, and the new owner must be a person's session (high).** Adoption asked only the new owner's transcript, so an agent made itself the owner from its own `codex exec "adopt <id>"` run (a Codex rollout records the exec prompt as a user message), and the admission bound was dropped for that session. Now the current owner hands the attempt over (`adopt <attempt>:<new owner>` in the owner session, or typed at the owner's terminal for a person-named owner), and the new owner confirms from a plain interactive session: Codex rollouts from `codex exec` or a sub-agent, Claude Code `sdk-*` runs and turns without origin fields are refused. Owner turns are now an allow-list of known shapes whose text opens as typed words, so Codex `<user_action>` review results and other markup never count.
- **An owner message counts once, wherever its transcript is copied (medium).** The owner's transcript was the newest `<session>.jsonl` across project folders and a spend was keyed on that file's path and the line's offset, so a copy of the transcript made every spent message fresh (one override message ran three gates). A spend is now keyed on the runtime, session id and the line's own id (`uuid`, else its sha256); two transcripts for one session are refused; every decision reads the spends recorded in every attempt's ledger and refuses while one has lost its marker under `authorities/`; a reopen's waiver is recorded on the delivered attempt too.
- **A linked `.workflow` cannot retarget the adapter at base (medium).** The adapter's folder was the real path of `<root>/.workflow`, so replacing it with a link to another folder committed at the same base (an example adapter with a weaker gate) made that folder "the adapter committed at base". A link is now followed only to the top-level `.workflow/` of a listed repo (refused anywhere else), and an attempt refuses once `.workflow` resolves anywhere but the folder recorded at its admission.
- **The owner session's `wf handoff close` is matched as documented (low).** The command match accepted `node` followed by any script named `wf`; it now takes `wf` itself (its last path part exactly `wf`) or `node` with this engine's own absolute `bin/wf`.
- **Globs cannot hang the engine (low-medium).** An unclosed `{` in a glob made the matcher loop for ever, and stacked `**` (`**a**a…b`) backtracked exponentially in the engine's own process, so one `wf impact run --query` hung the engine. Globs are now matched by a state-set simulation (no backtracking), an unclosed `{` is a literal, and a query glob whose alternatives expand past 256 is refused before any tree is read.
- **`git replace` cannot rewrite the base (medium).** Engine git calls inherited the environment and the repo's replace refs, so `git replace <committed adapter blob> <weaker blob>` changed what the adapter at base said with no commit. Every engine git call now sets `GIT_NO_REPLACE_OBJECTS` and an empty graft file, and the engine refuses a repo with `refs/replace/*` or `info/grafts`.

- `npm run verify` works from a linked git worktree: the Linux legs mount and relink the worktree's git directories.
- `npm run verify` runs its three legs in parallel and prints each leg's time; `--host-only`, `--linux-only` and `--serial` run part of it or the old order. The suite needs about a third less CPU (CONTRIBUTING.md, "Running the suite").

## v0.4.5

- **Security fix: only the owner defers a discovered issue, as the host recorded it.** In 0.4.4, `wf discovered close --deferred` refused a deferral only when the caller-typed `--by` named a role agent. An agent that left `--by` out could defer with words it made up.
  - **A fixed phrase, host-recorded.** The owner starts a message in the owner session with `defer <attempt id>:<issue id>` (for example `defer ENG-1.1:D3`), optionally `: <reason>`; `wf discovered list` prints the phrase. Then `wf discovered close D3 --deferred` takes the decision from exactly one owner turn that starts with it. The turn must lie after an anchor recorded when the entry was added (the transcript's size and the sha256 of its bytes, which must be unchanged). The whole turn is recorded with its file, line, offset and anchor. An owner message with an image or any other non-text block never counts (it fails safe). No natural-language intent is judged: "D3 can't wait" or "Don't defer D3" are refused because they do not start with the phrase. `--decision` and `--quote` are refused, and `--by` is attribution only.
  - **At an interactive terminal.** `wf discovered defer <id> --reason "..."` runs only at an interactive terminal and asks for the id to be typed. Ending the input (Ctrl-D) or typing anything else refuses, and nothing is recorded. It is recorded `interactive-terminal (unverified)`: the Bash tool of an agent runtime has no terminal, but a pseudo-terminal wrapper gives it one. No guard rule tries to stop a wrapper around it: a deny-list of pseudo-terminal and interpreter tools cannot be complete, so none is attempted.
  - **Acknowledged at delivery.** `wf deliver` refuses while a deferral is unacknowledged. It lists each one with its id, summary, the owner's recorded words, the channel and its verification level. `wf deliver --acknowledge-deferrals D2,D3` (batch members' as `<attempt>:D2`) delivers. The acknowledgement is recorded after the pre-push checks; a refusal before that records no acknowledgement. After it, an id already acknowledged is accepted again, so the same command is run again after a push conflict, after an adapter that is still waiting for merge (that is not a refusal: `wf deliver` exits 0 and says it is waiting) and after a failed adapter readback. In that last case, when the accepted commit is already on the target branch, the retry records the delivery as recovered from the remote and does not call the adapter's readback again: the engine's own git check (the accepted, gated commit is an ancestor of the target branch) is the proof it relies on, so an adapter whose readback proves more than branch ancestry is not re-checked on a recovered retry. The delivery output (every batch member's too) and the delivered comment's known limits list each deferral with its attempt-qualified id, the owner's words, the channel and its acknowledgement.
  - These never count: tool results; meta lines; compaction summaries; lines the host marks as not from the person (`origin.kind` or `turnOrigin` other than `human`: task notifications, messages relayed from other agents, scheduled prompts); turns that are a host or runtime wrapper (`<scheduled-task>`, which this host records with origin human, `<task-notification>`, `<system-reminder>`, relayed and cross-session messages, hook and command output, Slack wake-ups, Codex environment, AGENTS.md, subagent-notification, heartbeat and shell-command blocks); assistant text; and subagent transcripts. Anything else written into the transcript as a plain user turn counts. Two turns with the phrase are refused as ambiguous. `wf discovered add` says at once when an entry gets no transcript anchor.
  - `wf deliver` prints every deferral verbatim with its source. The reviewer bundle carries the same text.
  - **Limits, plainly.** The plugin does not defend against an adversarial agent with your user's tools. Such an agent can edit the transcript after the anchor, answer the terminal prompt through a pseudo-terminal, and acknowledge at delivery. A deny-list of wrapper tools is deliberately not attempted. These controls are speed bumps plus audit visibility: every deferral is recorded, shown at delivery and in the delivered comment, and named with its channel.
- **The evidence guard says what matched and how to avoid it (I-16).**
  - The refusal names the token that matched, or the working directory for a command run inside the evidence. It says how to avoid the refusal: write "the evidence folder" in commit messages, echo text and grep patterns; read evidence with the Read tool or `wf evidence`; copy screenshots out with `wf export screenshots`; run each `wf` command as one plain invocation.
  - Nothing that was refused before passes now. The guard still decides on the raw text and never parses shell.
  - **Security fix.** `wf run --lease X -- <command>` executes its command but was treated as a plain `wf` invocation. A command on the evidence wrapped in it went through. It is now judged like any other command.
- **Delivery adapters: a rejected or failed integration refuses.** When a delivery adapter reports `rejected` or `ci-failed`, `wf deliver` now exits non-zero. The message names the state, the integration url and what to do. Before, it took the same path as a pending merge and exited 0, so a rejected delivery read as success. `awaiting-merge` and `ci-running` still wait with exit 0. Any other value refuses too, including a typo or no state at all; the message names what was received and the valid states. The adapter is pinned at the attempt's admission, so the message says that a fix on the base branch does not change the attempt, and that the owner decides the recovery. docs/lifecycle.md, "Recovering from an adapter fault", gives the proven single-repo, standard-lane steps, which apply only while no repo is recorded as delivered or skipped, and the cases they do not cover.
- **Test fix (Linux as root, under full-suite load).** The gate creates its lock with O_EXCL and writes the JSON in a second call, and the `wf stop` scenario parsed the lock without a guard. It could read the lock empty and fail; it now treats an unreadable lock as not ready yet, as the engine's own reader does.
- **`wf evidence list [--kind K]` and `wf evidence show <path>`.**
  - `list` gives an attempt's evidence files by kind (gate logs, records, plans, handoffs, reviews, tracker, delivery, screenshots), with relative and full paths. `show` prints a text file.
  - Both write nothing of their own; opening the attempt runs the usual verification. A link at the attempt folder or at a file is refused. `show` reads at most 4 MiB and refuses paths outside the attempt, binaries and images; for images it points to `wf export screenshots`.
  - The reviewer, implementer and work-skill texts use them, so no shell command needs the folder's name.
