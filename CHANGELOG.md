# Changelog

Release notes, newest first, then every fix that came from a failure in the workflow itself. Generated by `node scripts/changelog.mjs` from `docs/releases/` and `improvements/`.

## v0.4.5

- **Security fix: only the owner defers a discovered issue, as the host recorded it.** In 0.4.4, `wf discovered close --deferred` refused a deferral only when the caller-typed `--by` named a role agent. An agent that left `--by` out could defer with words it made up.
  - **A fixed phrase, host-recorded.** The owner starts a message in the owner session with `defer <attempt id>:<issue id>` (for example `defer ENG-1.1:D3`), optionally `: <reason>`; `wf discovered list` prints the phrase. Then `wf discovered close D3 --deferred` takes the decision from exactly one owner turn that starts with it. The turn must lie after an anchor recorded when the entry was added (the transcript's size and the sha256 of its bytes, which must be unchanged). The whole turn is recorded with its file, line, offset and anchor. An owner message with an image or any other non-text block never counts (it fails safe). No natural-language intent is judged: "D3 can't wait" or "Don't defer D3" are refused because they do not start with the phrase. `--decision` and `--quote` are refused, and `--by` is attribution only.
  - **At an interactive terminal.** `wf discovered defer <id> --reason "..."` runs only at an interactive terminal and asks for the id to be typed. Ending the input (Ctrl-D) or typing anything else refuses, and nothing is recorded. It is recorded `interactive-terminal (unverified)`: the Bash tool of an agent runtime has no terminal, but a pseudo-terminal wrapper gives it one. No guard rule tries to stop a wrapper around it: a deny-list of pseudo-terminal and interpreter tools cannot be complete, so none is attempted.
  - **Acknowledged at delivery.** `wf deliver` refuses while a deferral is unacknowledged. It lists each one with its id, summary, the owner's recorded words, the channel and its verification level. `wf deliver --acknowledge-deferrals D2,D3` (batch members' as `<attempt>:D2`) delivers. The acknowledgement is recorded after the pre-push checks; a refusal before that records no acknowledgement. After it, an id already acknowledged is accepted again, so the same command is run again after a push conflict, after an adapter that is still waiting for merge (that is not a refusal: `wf deliver` exits 0 and says it is waiting) and after a failed adapter readback. In that last case, when the accepted commit is already on the target branch, the retry records the delivery as recovered from the remote and does not call the adapter's readback again: the engine's own git check (the accepted, gated commit is an ancestor of the target branch) is the proof it relies on, so an adapter whose readback proves more than branch ancestry is not re-checked on a recovered retry. The delivery output (every batch member's too) and the delivered comment's known limits list each deferral with its attempt-qualified id, the owner's words, the channel and its acknowledgement.
  - These never count: tool results; meta lines; compaction summaries; lines the host marks as not from the person (`origin.kind` or `turnOrigin` other than `human`: task notifications, messages relayed from other agents, scheduled prompts); turns that are a host or runtime wrapper (`<scheduled-task>`, which this host records with origin human, `<task-notification>`, `<system-reminder>`, relayed and cross-session messages, hook and command output, Slack wake-ups, Codex environment, AGENTS.md, subagent-notification, heartbeat and shell-command blocks); assistant text; and subagent transcripts. Anything else written into the transcript as a plain user turn counts. Two turns with the phrase are refused as ambiguous. `wf discovered add` says at once when an entry gets no transcript anchor.
  - `wf deliver` prints every deferral verbatim with its source. The reviewer bundle carries the same text.
  - **Limits, plainly.** The plugin does not defend against an adversarial agent with your user's tools. Such an agent can edit the transcript after the anchor, answer the terminal prompt through a pseudo-terminal, and acknowledge at delivery. A deny-list of wrapper tools is deliberately not attempted. These controls are speed bumps plus audit visibility: every deferral is recorded, shown at delivery and in the delivered comment, and named with its channel.
- **The evidence guard says what matched and how to avoid it (I-16).**
  - The refusal names the token that matched, or the working directory for a command run inside the evidence. It says how to avoid the refusal: write "the evidence folder" in commit messages, echo text and grep patterns; read evidence with the Read tool or `wf evidence`; copy screenshots out with `wf export screenshots`; run each `wf` command as one plain invocation.
  - Nothing that was refused before passes now. The guard still decides on the raw text and never parses shell.
  - **Security fix.** `wf run --lease X -- <command>` executes its command but was treated as a plain `wf` invocation. A command on the evidence wrapped in it went through. It is now judged like any other command.
- **Delivery adapters: a rejected or failed integration refuses.** When a delivery adapter reports `rejected` or `ci-failed`, `wf deliver` now exits non-zero. The message names the state, the integration url and what to do. Before, it took the same path as a pending merge and exited 0, so a rejected delivery read as success. `awaiting-merge` and `ci-running` still wait with exit 0. Any other value refuses too, including a typo or no state at all; the message names what was received and the valid states. The adapter is pinned at the attempt's admission, so the message says that a fix on the base branch reaches only new attempts. It points to docs/lifecycle.md, "Recovering from an adapter fault": the proven single-repo, standard-lane steps (abandon, re-enter, `git merge --squash` the old branch, then gate, review and deliver) and the cases they do not cover.
- **Test fix (Linux as root, under full-suite load).** The gate creates its lock with O_EXCL and writes the JSON in a second call, and the `wf stop` scenario parsed the lock without a guard. It could read the lock empty and fail; it now treats an unreadable lock as not ready yet, as the engine's own reader does.
- **`wf evidence list [--kind K]` and `wf evidence show <path>`.**
  - `list` gives an attempt's evidence files by kind (gate logs, records, plans, handoffs, reviews, tracker, delivery, screenshots), with relative and full paths. `show` prints a text file.
  - Both write nothing of their own; opening the attempt runs the usual verification. A link at the attempt folder or at a file is refused. `show` reads at most 4 MiB and refuses paths outside the attempt, binaries and images; for images it points to `wf export screenshots`.
  - The reviewer, implementer and work-skill texts use them, so no shell command needs the folder's name.

## v0.4.4

- **Every issue found during a ticket is fixed in it (I-18).**
  - `wf discovered add --summary "..." [--where file:line] [--found-by ID]` records an issue any role finds, inside or outside the criteria. `wf discovered list` shows them; status and resume count the open ones.
  - `wf discovered close D1 --fixed <commit>` needs a commit of this ticket (on the attempt's branch, after its base). `--deferred --decision "<the owner's own words>"` records the owner's decision verbatim; no words, or a role agent named in `--by`, is refused.
  - `wf deliver` refuses while one is open. Deferred entries reach the delivered comment's known limits and the attempt page.
  - The implementer and reviewer bundles list every entry. The closure gives each a verdict (`discovered: [{ id, verdict: fixed|deferred|open, evidence }]`); `wf review` refuses one missing, `wf accept` refuses an `open` verdict and an entry recorded after the round was handed.
  - The implementer, reviewer, planner, work and quick-fix texts say: record every issue, never defer it yourself or call it harmless, and amend the criteria when they block the fix.
  - **The role that found it fixes it.** An implementer fixes what it finds in this attempt, in whatever file it lives in; the work-item brief is never a reason to leave it, and the owner sends it back instead of fixing or relaying it. The one exception, a file another work item is editing at that moment, is recorded with `wf discovered add ... --blocked-by <work item>`; the next step routes it to that work item's implementer.
  - **`wf handoff reviewer` refuses an implementer report that leaves an issue unfixed** ("not fixed", "outside the brief", "out of scope", "follow-up" ...) without naming its discovered entry. The report is read from the implementer's Claude Code transcript; elsewhere nothing is checked.
- **Scope fences never block a fix (I-19).**
  - The planner template no longer writes blanket "no change in X" criteria or plans fixes as follow-ups. It states the invariant instead: the contract seam stays matched; existing fields, permissions and tenant isolation are unchanged.
  - `wf criteria amend --file f --reason "why" --add-repo R` adds a repo to the running attempt in one owner step: its worktree on the attempt's branch from the current base, provisioned as at admission, with the amendment's work item for it. Gate and delivery then cover it like any other repo.
  - The reviewer bundle lists added repos under `addedRepos`. The closure judges each seam on both sides (`seams: [{ repo, verdict: matched|finding, evidence, finding }]`, `matched` citing the producer's and the consumer's file:line). The reviewer and lifecycle docs treat a fence that blocks a fix as a criteria defect, never a reason to defer or to ship a cosmetic workaround.

## v0.4.3

- **Every handoff names the agent to start (I-14).** `wf handoff reviewer` now prints `Start agent type wf-reviewer (name it <id>; do not pass a model)` on stderr; stdout is still only the one start line. Before, a reviewer started without a name did the whole review and then had its closure refused. `wf review` and `wf plan --from-agent` now accept an unnamed agent when its identity is unambiguous: exactly one unnamed transcript of the handed agent type began with this handoff's own line, after the handoff. It is recorded `identity: unnamed`. Zero matches, several matches or another agent type are refused, and the refusal says how to start the agent: its type, its name and only the printed line.
- **Role changes and running sessions (I-15).**
  - `wf sync` rewrites a role file only when its content changed. It lists the changed role files and says that a session already running keeps the roles it loaded.
  - `wf handoff` warns when the agent type's role file changed after the owning Claude Code session started. The start is the later of the transcript's first entry and the process start, so a resumed session is not flagged.
- **Lessons match the change's declared scope.**
  - A lesson declares `repo`, `components`, `paths` and `kinds` (ui, test, migration, docs, script, config, source). It reaches a bundle only when a changed or planned file satisfies all of them, or when the ticket mentions one of its tags.
  - A lesson whose repo was admitted to the attempt but not changed is no longer handed to the reviewer. A project lesson with no scope no longer applies to every change; `paths: ["**"]` says so explicitly, and `wf lesson list` warns about lessons without a scope.
  - Handoffs print the filtered ids, and the ledger records them. `wf lesson preview` gives the reason for each filtered lesson. Filtered lessons never enter a bundle, so they owe no verdict and no trailer.

## v0.4.2

- **Connector handoffs reach verified evidence.** `wf tracker record --event E --from-transcript` reads the attempt owner's Claude Code or Codex transcript, which the host writes. It takes the tracker's own get-issue and list-comments results recorded after the event and runs the raw-capture checks on them. It also records what the session posted. It is recorded `host-recorded`, distinct from `engine-read` (api, cli, files) and `agent-reported`. Limit: a same-user process could edit the transcript.
- **Agent-reported fallback.** `--agent-reported --file reported.json --comment-file posted.md` is for connector mode where no host record exists. The engine checks the item, the status, the comment text (its sha256, the fixed lines, the summary, an image per screenshot, no internals), the captions and a fresh read time. It is recorded `agent-reported, unverified` and shown so in status, export and the closing message.
- **Security fix from review (credential exfiltration).**
  - Tracker error notes are scrubbed of the key and of anything token-shaped (Authorization or Bearer values, known token prefixes, signed-URL signatures); a fetch error's request is never shown.
  - `gh` runs with a minimal environment, so no other service key of the owner reaches it.
  - Exports (HTML and JSON) mask signed-URL signatures and tokens on top of the catalogued secrets.
  - From a transcript, only the matched tool results are kept: no other line reaches the evidence, and the scratch copies are removed.
  - Owner-added comment lines are recorded masked.
- **Owner additions to the delivered comment are allowed** when every rendered line is still there, in order. The added lines are listed in the record.
- **Wording.** `wf doctor` prints the readback level the current host reaches, the onboard skill states it, and the next step after delivery names `--from-transcript`.
- **Demo assets.**
  - The social preview shows whole lines of the real run: the gate refusal, the refused self-review, the delivery and the readback.
  - The demo SVG wraps long lines instead of cutting them off.
  - The generator refuses any line that would overflow.

## v0.4.1

- **Public screenshots on GitHub.** When the issues live in a public repository (or GitHub does not report its visibility), `wf doctor` prints `NOTICE: screenshots will be publicly downloadable`. `wf deliver` refuses to deliver a change with screenshots there until the owner chooses:
  - keep it, with `tracker.publicAssets: acknowledged` committed on the base branch;
  - switch to the files tracker;
  - keep the issues in a private repository.

  The adapter checks again before each upload. The onboard skill asks this question.
- **Docs.** The README is a short landing page. The reference moved to `docs/`: concepts, lifecycle, gate, delivery and tracker, onboarding, adapter schema, lessons, trust model and telemetry. A scenario checks that every relative link and heading resolves.
- **Corrections.** The docs no longer claim resource-peak sampling, which is not built. The tracker docs no longer describe a Linear-only setup.
- **Presentation.** This changelog, release notes per version, issue templates for bugs and plugin improvements, and a 1280×640 social preview in `docs/assets/`.

## v0.4.0

**Trackers.** `tracker.kind` (linear, github, files, none) and `tracker.via` (api, cli, files, connector) are chosen at onboarding and validated together; `wf doctor` states what is verifiable for the combination.
- GitHub Issues through your `gh` login (`via: cli`) or a `GITHUB_TOKEN` from `wf secrets` (`via: api`): status labels, the rendered comment, screenshots as release assets, read back by the engine.
- Tickets as markdown files in the repo (`kind: files`): the engine sets the status, appends the comment, copies captioned screenshots with their sha256 and reads it all back.
- `wf init` drafts the files tracker from a `tickets/` folder and names a GitHub origin.

**Security fixes from review.**
- Tracker tokens go only to endpoints committed in the adapter at the attempt's base, over https, never through a redirect; non-default hosts are named by `wf doctor`.
- One safe reader for every screenshot that is uploaded, copied or exported: no symlink, hard link, FIFO or path outside the evidence; the sha256 is checked on the bytes read.
- Files-tracker ticket ids and attachment names are validated before any file is touched.
- Input files that are symlinks (`--summary-file`, `--file`) are refused.

**Workflow.** The reviewer role gets the Write tool its instructions require, and `wf review` refuses a closure when the worktree changed during the round (I-13).

**Demo and CI.**
- `bash examples/hello-ticket/demo.sh` runs one ticket end to end; `node scripts/record-demo.mjs` re-records `docs/assets/` from a real run.
- `npm run verify` runs the suite on the host and in Linux as non-root and root, and the pre-push hook runs it; CI runs weekly too.
