# Trust model

[Back to the README](../README.md) · [Docs map](../README.md#docs)

Native role liveness is ephemeral display from the engine's current child process handle, not additional evidence. The launcher emits compact stderr updates at most once per minute, keeps JSON stdout as one terminal result, and does not read the role transcript to generate progress. A pending process or historical started receipt never proves a completed plan, an accepted review, or current liveness after recovery. Owners wait on the original host execution handle and inspect the terminal result once; required host commentary and wait intervals remain host policy.

- **What the engine enforces:** a hash-chained ledger; gate results bound to the exact tree and to the adapter committed at base; only a gate that ran every step the tree needs (never a `--focused` one) opens acceptance and delivery; acceptance needs a clean closure written for the current tree after a passing gate on it; a step that reads another repo (`alsoInputs`) is reused only while that repo is unchanged; the reviewer is never the owner, planner, an implementer or a reviewer of an earlier round; criteria are frozen before code.
- **The adapter at base, and only it:** admission records where the adapter lives (its repo, that repo's folder and the adapter folder inside it) with the base commit. Every later decision that judges the attempt (whether a planner and the impact analysis are required, which classes, roles and repos exist, the repos and limits of impact queries, rules, skills, lessons, the gate's steps, delivery targets, the delivery and tracker adapters) reads the adapter committed at that base, located from that record only, and the committed adapter must itself name that repo at that folder. An attempt with no recorded base, or whose adapter at base cannot be read, is refused; nothing falls back to the working tree's copy. Attempts admitted before the record existed are located from the working tree once, under the same rules, and cross-checked the same way. `.workflow` at the project root is either a real folder or a link to the top-level `.workflow/` of a listed repo (the adapter repo when `adapterRepo` is set); a link anywhere else is refused at admission, and a `.workflow` that no longer resolves to the folder recorded at admission refuses every later command of the attempt. The limit: admission itself reads the working tree (which repos exist, their folders, where `.workflow` is), and the committed adapter it then reads must agree with it; an agent that rewrites the checkout before admission, and commits a matching adapter where the working tree points, chooses what is recorded.
- **Commits as committed:** every git call the engine makes ignores `git replace` refs and grafts (`GIT_NO_REPLACE_OBJECTS`, an empty graft file), and admission, every read of the adapter at base and every impact query refuse a repo that has `refs/replace/*` or `info/grafts`: neither can change what "the adapter committed at base" or a ticket's tree contains without a commit.
- **What classes change:** only how hard each agent thinks. Every guarantee above holds the same at every class.
- **Review rules:** the reviewer bundle lists the project rule documents and skills the change falls under, from the adapter at base; where transcripts exist `wf review` refuses a round that did not read each one, and `wf accept` needs a verdict per rule. A read proves the document reached the reviewer, not that it was applied.
- **Review provenance:** where Claude Code transcripts exist, `wf review` and `wf plan --from-agent` refuse a round whose transcript is missing, ran as another agent type, started before its handoff, or was started with anything but the printed line. For an engine-launched Codex role (`wf handoff run --agent <id>`), wf records the exact launch line, role instructions, model and effort in protected launch records. It binds the native runtime session id to the handoff and checks the real host transcript for that exact prompt after the handoff. A changed receipt, another session, steering, a resumed session or a failed launch refuses. Codex desktop collaboration prompts are encrypted in the local record and omitted by read-only app-server history; existing encrypted spawns remain `unverified`. Planner import never falls back to another runtime. Where native successful command-read events are available, Codex review document reads are checked too. Elsewhere the round is recorded `unverified`.
- **Commit, then reveal:** a round's own findings are recorded blind; only then does it see earlier rounds' open findings, and acceptance needs each verified by a later round. Its own findings cannot change after the reveal.
- **Discovered issues:** delivery refuses one that is open; a fix closes it only with a commit of this ticket; the reviewer gives every entry a verdict. A deferral comes from one of two channels. **Host-recorded:** exactly one owner turn in the owner session's transcript that starts with `defer <attempt>:<id>`, after an anchor taken when the entry was added (no natural-language intent is judged). **Interactive-terminal (unverified):** `wf discovered defer` at an interactive terminal with the id typed. Free text from an agent is refused. Every deferral is listed at `wf deliver` with its words and channel and counts only once the owner acknowledges it there.
- **What the deferral controls are, and are not.** They are speed bumps plus audit visibility, not a defence: the owner's exact phrase `defer <attempt>:<id>` at the start of one genuine owner turn after the entry's anchor, `wf discovered defer` labelled `interactive-terminal (unverified)`, the acknowledgement at `wf deliver`, and every deferral shown in the delivery output and the delivered comment. A deny-list of pseudo-terminal, interpreter and encoding tools in the guard is deliberately not attempted: it cannot be complete, so every rule would invite the next bypass. Nothing here defends against an adversarial agent running as your user, which can write to the owner's transcript after the anchor, answer the terminal prompt through a pseudo-terminal, and pass `--acknowledge-deferrals` itself; a Claude Code user turn without origin fields (older transcripts, some headless prompts) counts as an owner turn when it starts with the phrase (never for `wf adopt`'s new owner). What such an agent cannot do is defer without leaving a record that the export, the reviewer bundle, the delivery output and the delivered comment show.
- **Owner-only decisions (0.5.0).** Running the gate out of the order of work (`wf gate --reason`), handing a reviewer the tree while an implementer is open (`wf handoff reviewer --reason`), closing an implementer (`wf handoff close`), accepting a post-merge adapter state (`wf deliver --acknowledge-adapter-state`), re-pinning the delivery adapter (`wf deliver --repin-adapter`), abandoning past an integration (`wf abandon --acknowledge-integration`), lifting a hold (`wf release`) and adopting an attempt (`wf adopt`) are the owner's, never an agent's. A flag on the command line is never the authority. It comes from one of three channels, recorded on the decision's ledger event as `authority`:
  - **Host-recorded:** when the owner is a Claude Code or Codex session, a genuine owner turn in that session's transcript, after admission, that starts with the decision's phrase: `override <attempt>:gate`, `override <attempt>:review`, `close <attempt>:<agent>`, `acknowledge <attempt>:<repo>:<state>`, `repin <attempt>:<tip>`, `abandon <attempt>:<repo>:<state>`, `release <attempt>`, and for `wf adopt` a direct human request to adopt the ticket or attempt in the receiving chat (for example `adopt ENG-1`, `can you adopt ticket ENG-1` or `Read HANDOVER-ENG-1.md and then adopt ENG-1.1`; affirmative command clauses count, quoted examples, reports, negations and conditional requests do not). The previous session need not release it or be available. The receiving chat must be a plain interactive session: a Codex rollout whose `session_meta` records an interactive source (`cli`, `vscode`; never `codex exec` or a sub-agent), or a Claude Code turn that records a person as its origin, an interactive entry point (`cli`, `claude-desktop`; never `sdk-*`) and a typed prompt. A turn without origin fields never adopts. Adoption requests must follow admission and the most recent ownership change; the transfer records its previous owner, new owner and human receipt. Any human using this local project can authorize recovery from their own interactive chat; the previous session has no veto. Holds and existing scope stay in place, closed attempts refuse, and a repeat by the current owner is a no-op. Each message counts for one decision across the whole project, wherever its transcript is: a spend is keyed on the runtime, the session id and the line's own id (Claude Code's `uuid`, else the line's sha256), never on the transcript's path or the line's position, so a copied or moved transcript holds no fresh message. Claude Code and older Codex hosts without a thread index require one transcript: two files for one session id are refused, never chosen between. Codex hosts with an index select the active rollout from `threads.rollout_path` in their newest state database schema generation, read-only; suffixed desktop rollout names are supported. The selected file must be a regular, size-capped file inside the host transcript folders with matching `session_meta.id`. Invalid or missing indexed files and corrupt or linked indexes refuse; filesystem modification time and stale fallback files grant no authority. As with transcripts, a same-user process could forge the host index. The message is spent before the action, by creating a marker under the evidence folder's `authorities/` exclusively, so two commands racing for one message spend it once, and the spend is recorded with the decision in the attempt's hash-chained ledger (`spent`). Every decision reads the spends of every attempt's ledger, and refuses while any of them has lost its marker, so deleting a marker never frees its message. A reopen's lesson waiver, read on the delivered attempt, is recorded on the new attempt and, as `authority.spent`, on the delivered one. A decision retried as itself (the same deferral, adapter state, re-pin, close, release or abandon after a later step refused) is accepted again from its own marker; an override and a reopen's lesson waiver never are. Tool results, notifications, relayed and injected lines and sub-agent transcripts never count, as for deferrals: an owner turn is only one of the known shapes (a Claude Code `user` line with text content and, where recorded, a person as its origin; a Codex `response_item` user message of `input_text` blocks) whose text opens with a letter or digit, so a line that opens with markup or a bracket (`<user_action>`, `<recommended_plugins>`, `[12] tool exec call`) is never the owner, whatever its tag. An owner session whose transcript cannot be read is refused.
  - **Owner-session command (bookkeeping only):** for `wf handoff close` alone, the owner session's own last shell tool call is exactly `wf handoff close --agent <id> --attempt <id>` (one plain invocation: the program is `wf` (by name, or a path whose last part is exactly `wf`) or `node` followed by this engine's own absolute `bin/wf`; no shell operator, quote or redirect; every flag and value equal; after admission; within 10 minutes; each call counted once). Claude Code and Codex write a tool call before it runs, and a sub-agent's calls go to its own transcript. Codex accepts a direct `exec_command` call or exactly one literal `text(await tools.exec_command({...}));` / `await tools.exec_command({...});` wrapper; arbitrary scripts, variables, conditional or multiple calls, headless/subagent metadata, another working directory and result-only records refuse. The stable call id is spent once even if the rollout moves. Plainly: in an agent-driven session the owner session's assistant is itself an agent, so this is the orchestrating agent's own word. It is accepted only for closing an implementer, which records bookkeeping (the reviewer stays bound to the tree it is handed); every other owner-only decision needs the owner's message.
  - **Interactive-terminal (unverified):** when the owner is not a session (a person's name), the command asks at its terminal for the phrase to be typed back, and prints and records `interactive-terminal (unverified)`. It is refused when there is no interactive terminal, when the process's controlling terminal is not a real tty device, when an agent-runtime variable is set (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`, `AI_AGENT` and similar), when any ancestor process is an agent runtime (a best-effort list of executables and command lines in `engine/owner.mjs`), and when the process ancestry cannot be read. The absence of any of these never grants anything by itself.
  - **The limit, plainly:** for an attempt owned by a host session, the only authority is the owner's message in the host's record of that session. For an attempt owned by a person's name, the terminal confirmation is best effort against accidental or naive agent action, not against a deliberate forger running as the same user: such a process can allocate a pseudo-terminal, scrub its environment, detach from the agent's process tree or run under a name the list does not know. An owner who needs a firmer boundary owns the attempt from a session. A same-user process can also append a forged owner turn to the owner's transcript (or point `WF_HOME` at a folder it wrote); that is a deliberate forgery that leaves the forged turn in the ledger, as for deferrals.
- **The attempt page is a view:** `wf export` renders the ledger and evidence; it is never read back.
- **What a step sees:** an allowlisted environment, never agent session tokens unless the adapter passes them (see [Step environment](gate.md#step-environment)).
- **What it relies on you for:** agent identities are names the owner supplies (an agent started without one is matched by its start line only when that is unambiguous), and the reviewer must be a newly started agent (not an old one under a new id), started blind with only the one line `wf handoff reviewer` prints. The engine checks the exact prompt where the host record exposes it, or through the engine-controlled Codex launch above. In runtimes without readable prompt provenance it cannot prove that boundary; the report marks it unverified.
- **What it does not stop:** a determined forger with shell access on the same machine. It catches mistakes, not attacks. Details: [DESIGN.md](DESIGN.md#trust-model); the evidence layers and their accepted limits: [gate.md](gate.md#evidence-integrity); tracker credentials: [delivery-and-tracker.md](delivery-and-tracker.md#where-tasks-live-and-how-wf-reaches-them).

## Execution settings on existing attempts

`wf models refresh --attempt <id>` records the current committed tip of the admission adapter repo's configured base. Only the owner may refresh (a host-recorded exact owning-session command or a human terminal confirmation). A ticket config, uncommitted edit, arbitrary model/effort flag, unrelated commit or moved adapter location cannot provide execution settings.

Future handoffs resolve model and effort from this separate execution pin: implementers keep their frozen work class, and other roles use their class mapping at the execution pin solely to select model/effort. The admission class, its use text, role instructions and appendices, criteria, gate, tracker, review rules and skills stay frozen. Existing handoffs retain their own execution pin; refresh requires a fresh handoff for new settings. `wf doctor --runtime codex --attempt <id>` reports the attempt pin as well as the current setup. Resume distinguishes unlaunched, running, failed and completed native reviewers.

## Extra-scope decisions

Unrelated existing defects require base/current evidence and four explicit false causal checks. In-scope or uncertain findings cannot be waived by `wf scope`. After `wf scope ask`, only the direct human reply in the owning interactive session authorizes expand, ticket or ignore. The reply is spent once and the question binds the displayed finding set. Expand-all is limited to that attempt, and criteria/impact amendments still precede every added implementation. Ticket disposition stays pending until a captured raw readback exists (labelled agent-reported, not host-verified). Owner dispositions and risks remain in exports and the delivered handoff. No choice rewrites closures or bypasses required failed gates.
