# Trust model

## Threat model

Decision D6, 2026-10-13 ([decision register](DESIGN.md#decision-register)).

**Agents are fallible, not adversarial.** The engine is built for an agent that misremembers, skips a step, edits the wrong file, runs a command out of order, says it is done when it is not, or reviews work it wrote. It is not built to stop an agent, or any process running as your user, that sets out to defeat it. Everything below follows from that.

- **Checks exist to catch mistakes.** A check is kept because it stops, or would have stopped, a mistake that happened, and it is judged by its refusals: every refusal a command prints with exit code 75 (a policy refusal; a usage error such as a missing flag or a malformed file exits 1 and is not logged) is logged under its check's id (`wf refusals`), `wf report` shows them per attempt, and `wf improve review` lists the checks nobody has judged (design principle 13). A check whose refusals show no catch is deleted without an incident (`wf improve close --retire`).
- **Findings that assume an adversarial agent are closed as out of model.** An automated security review (a hook, a model scan, a scheduled audit) that reports a way a deliberate forger could defeat a check (forging a transcript, allocating a pseudo-terminal, scrubbing the environment, rewriting the ledger and its anchor together, hiding a command from the guard) is closed with that reason recorded, and is not turned into code, unless an incident shows an agent doing it. Named failure: an automated security-review hook drove nine releases in 95 minutes with no incident behind any of them; each release added a refusal, and the guard's command scanning alone refused 334 commands, 69% of them naming no evidence folder at all.
- **The person's reserved decisions are one command.** A short list of decisions is never an agent's: waiving a blocking finding, overriding a failed gate, a low finding or discovered issue leaving the delivery (medium and high never leave, D17), lowering a rating out of high, ejecting or abandoning a member of a batch a split made, lifting a hold, adopting an attempt whose owner session is alive. The person confirms each with `wf approve <id>`, typed in their own terminal, or answered in the agent session's question panel, or in its chat to a message that asked exactly that question (0.7.18), and read by `wf approve <id> --from-question` from what the harness recorded (`engine/approve.mjs`; details under *Reserved decisions* below).
- **Its stated limits.** At the terminal, a pseudo-terminal counts as a terminal: `wf approve` refuses under an agent runtime's environment and without a real terminal, so an agent's shell cannot confirm there by mistake; a process that allocates a pseudo-terminal, clears its environment and types the choice is accepted, which is deliberate forgery outside the model, and the decision records `interactive-terminal (unverified)`. In the question panel (`--from-question`, 0.7.3), the agent's shell records the confirmation, but only from the answer the harness wrote for a question bound to that decision (below): a mistaken or paraphrased question, an answer given before the decision existed, a sub-agent's or another session's panel, or typed text that is not a choice confirms nothing; a process running as you that writes a transcript line, or a harness path that answers the panel by itself, would be accepted, which is outside the model too, and the decision records `question-panel (<harness>, host-recorded)`. In the chat (0.7.18), a reply binds only to the agent's message just before it (its final text after its last tool call, with any panel question it asked) when that message carries the decision's exact question and no other decision's; every turn of the person's ends that message, and harness lines (task notices, reminders, interrupt markers, compaction summaries, context) are never the person. Stated limits: the agent writes that message, so the person read what the agent showed them, the same as the panel's text; a reply typed before the question existed but recorded after it (a queued message) cannot be told apart; a reply that is only a paste is not read; the decision records `chat (<harness>, host-recorded)`, and a reply longer than its choice is kept beside it. The channel is in the ledger and in `wf decisions --json`, and a deferral's channel is printed in the delivery output and the delivered comment.
- **What stays in the model** is everything an honest mistake can reach: a gate result bound to the exact tree, acceptance bound to a review of that tree, the reviewer never being the owner, the planner, an implementer or an earlier reviewer, criteria frozen before code, evidence files recorded and protected so a careless edit or a tool's rewrite is noticed, and agents never handling secret values.

## What is enforced, and what is not

Native role liveness is ephemeral display from the engine's current child process handle, not additional evidence. The launcher emits compact stderr updates at most once per minute, keeps JSON stdout as one terminal result, and does not read the role transcript to generate progress. A pending process or historical started receipt never proves a completed plan, an accepted review, or current liveness after recovery. Owners wait on the original host execution handle and inspect the terminal result once; required host commentary and wait intervals remain host policy.

- **What the engine enforces:** a hash-chained ledger; gate results bound to the exact tree and to the adapter committed at base; only a gate that ran every step the tree needs (never a `--focused` one) opens acceptance and delivery; acceptance needs a clean closure written for the current tree after a passing gate on it; a step that reads another repo (`alsoInputs`) is reused only while that repo is unchanged; the reviewer is never the owner, planner, an implementer or a reviewer of an earlier round; criteria are frozen before code.
- **The adapter at base, and only it:** admission records where the adapter lives (its repo, that repo's folder and the adapter folder inside it) with the base commit. Every later decision that judges the attempt (whether a planner and the impact analysis are required, which classes, roles and repos exist, the repos and limits of impact queries, rules, skills, lessons, the gate's steps, delivery targets, the delivery and tracker adapters) reads the adapter committed at that base, located from that record only, and the committed adapter must itself name that repo at that folder. An attempt with no recorded base, or whose adapter at base cannot be read, is refused; nothing falls back to the working tree's copy. Attempts admitted before the record existed are located from the working tree once, under the same rules, and cross-checked the same way. `.workflow` at the project root is either a real folder or a link to the top-level `.workflow/` of a listed repo (the adapter repo when `adapterRepo` is set); a link anywhere else is refused at admission, and a `.workflow` that no longer resolves to the folder recorded at admission refuses every later command of the attempt. The limit: admission itself reads the working tree (which repos exist, their folders, where `.workflow` is), and the committed adapter it then reads must agree with it; an agent that rewrites the checkout before admission, and commits a matching adapter where the working tree points, chooses what is recorded.
- **Commits as committed:** every git call the engine makes ignores `git replace` refs and grafts (`GIT_NO_REPLACE_OBJECTS`, an empty graft file), and admission, every read of the adapter at base and every impact query refuse a repo that has `refs/replace/*` or `info/grafts`: neither can change what "the adapter committed at base" or a ticket's tree contains without a commit.
- **What classes change:** only how hard each agent thinks. Every guarantee above holds the same at every class.
- **Review rules:** the reviewer bundle lists the project rule documents and skills the change falls under, from the adapter at base, as context for the review: a verdict the reviewer gives per rule is recorded with the acceptance, and none is required. The engine does not read the reviewer's transcript to prove it read the documents (0.7.0: that check is gone).
- **Review independence (0.7.0):** a reviewer is never the owner, the planner, an implementer or the reviewer of an earlier round (ledger names, checked by `wf handoff reviewer`), and each round uses a fresh id. The engine does not read the reviewer's transcript to prove its agent type, start time, prompt or reads (named failure: that check refused four rounds in the field, all benign, and DESIGN.md principle 1 says the engine never parses transcripts for authority). For an engine-launched role (`wf handoff run --agent <id>`), wf records the exact launch line, role instructions, model and effort in protected launch records and binds the runtime's session id to the handoff; a review round whose engine launch failed is refused. A recorded round is marked `engine-launched` or `ledger-names`. `wf plan --from-agent` still reads the planner's last YAML block from its transcript (content, not authority) and checks that the transcript is the handed agent's; Codex desktop collaboration prompts are encrypted in the local record, so a planner started there is imported with `wf plan --file`.
- **Commit, then reveal:** a round's own findings are recorded blind; only then does it see earlier rounds' open findings, and acceptance needs each verified by a later round. Its own findings cannot change after the reveal.
- **Discovered issues:** delivery refuses one that is open; a fix closes it only with a commit of this ticket, and a commit made before the entry was recorded is a claim that only an independent reviewer's `fixed` verdict closes, when its bundle showed that entry and that commit (0.7.19); the reviewer bundle lists the entries still in play as context. A deferral moves a defect out of the delivery, so it follows the person's rule (D17): medium and high are fixed in this delivery, a low one leaves only with the person's answer, one short question per item (D18; the project's `leaving:` may change who decides): `wf scope defer` (or `wf discovered close --deferred`) refuses a medium or high issue and creates one decision per low item (kind `move-out-of-batch`, key `leave:<ref>`, choices `let it leave` | `fix now`), refused until the person picks `let it leave`; an answer in their own words is recorded as `other` with the words and never acts as a choice. Every deferral is listed at `wf deliver` on its own (the delivery output with its severity, reason, who decided and channel; the delivered comment's known limits in plain words); there is nothing to acknowledge.
- **What the deferral control is, and is not.** A speed bump plus audit visibility, not a defence: the confirmation at `wf approve` (an interactive terminal with no agent-runtime variable set; a pseudo-terminal wrapper can answer it), the listing at `wf deliver`, and the deferral shown in the delivery output and listed in the delivered comment. A deny-list of pseudo-terminal, interpreter and encoding tools is deliberately not attempted: it cannot be complete. Nothing here defends against an adversarial agent running as your user (the threat model is that agents are fallible, not adversarial). What such an agent cannot do is defer without leaving a record that the export, the reviewer bundle, the delivery output and the delivered comment show.
- **Owner decisions (0.7.0).** Two classes; neither reads a transcript for authority (`engine/owner.mjs`, `engine/approve.mjs`). Named failure: the 0.5.0 owner-phrase grammar and owner-session command matcher made 46 refusals with no genuine catch, 15 of 18 phrase refusals came after the person had already said yes, and 283 of 304 recorded owner decisions were the orchestrating agent's own shell command.
  - **Bookkeeping**, recorded with the caller as actor and no authority claim: closing an implementer (`wf handoff close`), handing the tree to a reviewer while an implementer is open (`wf handoff reviewer --reason`), a runtime or model choice (`--runtime`, `wf models refresh`), adopting an attempt whose owner session is gone or idle (no transcript write in 30 minutes), listing every deferral at delivery (automatic; it was decided when it was recorded), accepting an adapter state that is not a failure (`--acknowledge-adapter-state`), a lesson waiver (`--no-lesson`), and `wf shown` (from 0.7.7 no observation leaves on the agent's word: a low one leaves only with the person's answer, one short question per item (D18; the project's `leaving:` may change who decides), D17).
  - **Reserved**, confirmed by the person with `wf approve <id>` at an interactive terminal (a real tty, no agent-runtime variable), or with their answer in the agent session's question panel (`wf approve <id> --from-question`, 0.7.3): the question names the attempt and the decision and carries its summary, offers exactly its choices, and was answered after the decision was created; an answer that is none of the choices (the panel's free text) is recorded as `other` with the person's words, which the owner follows and which never acts as a choice (0.7.8); only the answer the harness recorded for that question is read (Claude Code's `AskUserQuestion` answers, Codex's `request_user_input` reply bound to its call; a sub-agent's line, another session and a non-interactive `codex exec` run count for nothing). The decision records the channel (`question-panel (<harness>, host-recorded)`). Its limit is the tracker readback's: the host's record, not a signature; a process running as you could write a transcript line, which is deliberate forgery and outside the model (D6). The refused command creates the decision, the person confirms it, the command is run again, and an approval is used once. Kinds: `waive-finding` (`wf scope waive`); `override-gate` (skipping the gate order with `wf gate --reason`, accepting a failed adapter state, `wf deliver --repin-adapter`, `wf abandon --acknowledge-integration`, `wf close --shipped`: closing an attempt whose every change git shows on its target branch without its acceptance); `move-out-of-batch` (a low finding or discovered issue leaving the delivery, D17: medium, high, unrated and blocking ones never leave, and the person's `deliver-core` answer is the one exception; lowering a discovered issue out of high; ejecting or abandoning a member of a batch a split made); `lift-hold` (`wf release`); `adopt-live` (adopting from an owner session active in the last 30 minutes, from a person-named owner, or from a transcript that exists but cannot be read); `escalation` (the scope question). `wf decisions` lists them.
  - **The limit, plainly:** an agent's shell has no terminal, so it cannot confirm a decision by mistake; an agent that allocates a pseudo-terminal and scrubs its environment can answer one. That is the stated limit under the threat model (agents are fallible, not adversarial). Every decision records its id, kind, summary and the action that spent it.
- **The attempt page is a view:** `wf export` renders the ledger and evidence; it is never read back.
- **What a step sees:** an allowlisted environment, never agent session tokens unless the adapter passes them (see [Step environment](gate.md#step-environment)).
- **What it relies on you for:** agent identities are names the owner supplies, and the reviewer must be a newly started agent (not an old one under a new id), started blind with only the one line `wf handoff reviewer` prints. The engine checks the ledger names only (0.7.0); it does not read the prompt a runtime gave the agent, so a steered or reused reviewer under a fresh name is not detected.
- **What it does not stop:** a determined forger with shell access on the same machine. It catches mistakes, not attacks. Details: [DESIGN.md](DESIGN.md#trust-model); the evidence layers and their accepted limits: [gate.md](gate.md#evidence-integrity); tracker credentials: [delivery-and-tracker.md](delivery-and-tracker.md#where-tasks-live-and-how-wf-reaches-them).

## Execution settings on existing attempts

`wf models refresh --attempt <id>` records the current committed tip of the admission adapter repo's configured base. Refreshing is bookkeeping (the owner agent records it as itself, 0.7.0). A ticket config, uncommitted edit, arbitrary model/effort flag, unrelated commit or moved adapter location cannot provide execution settings.

Future handoffs resolve model and effort from this separate execution pin: implementers keep their frozen work class, and other roles use their class mapping at the execution pin solely to select model/effort. The admission class, its use text, role instructions and appendices, criteria, gate, tracker, review rules and skills stay frozen. Existing handoffs retain their own execution pin; refresh requires a fresh handoff for new settings. `wf doctor --runtime codex --attempt <id>` reports the attempt pin as well as the current setup. Resume distinguishes unlaunched, running, failed and completed native reviewers.

## Review findings that do not block

Since 0.7.0 a finding blocks only when it fails a frozen criterion, breaks a critical invariant or regresses a line the attempt changed (in a delta round, since the last reviewed tree), and is rated medium or high; a finding rated low never opens a round. Every other finding is an observation: it never blocks by itself and never opens a review round, and the strategist schedules it (a fix pass in the batch, a sibling attempt, or a ticket). Placement is not obligation (D1): nothing is silently dropped, but where the fix lives can change. A finding that blocks leaves the delivery (ticketed or deferred) only with the person's `wf approve`, as waiving it does (`wf scope waive`; `wf approve`, above). No reply grammar is parsed: a person's answer is the choice typed to `wf approve` in their own terminal, or the option they picked in the question panel for that decision, or their chat reply to the agent's message that asked exactly that question (0.7.18); no other chat words are read. Required gate failures stay failures whatever is decided about a finding. Dispositions and risks remain in the export and the delivered handoff. See [scope-decisions.md](scope-decisions.md).

From 0.7.0 no owner question stands in front of an unrelated defect: the engine computes whether a finding blocks (`engine/review-policy.mjs`), and an observation is placed by the person's rule (D17): fixed (verified by a later reviewer, or recorded with `wf scope fixed` for a commit made after the finding, undone if a later reviewer finds it still open), moved to a sibling attempt (`wf scope move`, which asks nobody because the obligation stays in this delivery), ticketed (`wf scope ticket`, with a raw tracker readback labelled agent-reported, not host-verified) or left for later as a known issue (`wf scope defer`). A high or unrated observation leaves the delivery only with the person's `wf approve` (kind `move-out-of-batch`), a medium one with the owner agent's recorded reason, a low one freely; the person's `deliver-core` answer to the round escalation covers only the findings and discovered issues recorded before it. `wf deliver` waits until each is placed. No choice rewrites closures or bypasses a required check.

## Owning runtime and provider selection

Fresh handoffs inherit the current recorded owner's host. Adoption into Codex or Claude selects that host without
consuming a provider-switch receipt; the admission runtime stays in the ledger as audit history. A child process's
environment cannot replace this default. Owners without a host retain the admission fallback.

An explicit switch to another provider (`--runtime`) is a recorded choice, bookkeeping since 0.7.0: the handoff records who
chose and from what, and later handoffs and recovery inherit it for the same ownership period. Switching again is another
recorded choice. Adoption clears the selection. Historical per-handoff switch receipts do not become persistent grants.
Native launch still checks each handoff against the current default or its own recorded provider choice.

## Additive required validation

`wf validation add` is an auditable addition to proof obligations, not an admission adapter re-pin. New IDs are
selected from the committed adapter in the attempt's own adapter repo, descending from admission. Existing IDs,
plugin pins, repos, rules, roles, environment policy, secret stores and delivery/tracker targets stay frozen. The
registration records exact definitions and existing catalogued key bindings; no secret values enter it. Prior
acceptance and gate proof are invalidated. A fresh code review must come before the full gate (the reviewer
judges each pinned definition and plugin as context); fresh evidence review and screenshot inspection still precede acceptance.
The ordinary evidence protection and review/gate lock paths also govern registration and execution.

`wf validation correct` is the one way a registered pin moves (0.7.0, I-102): forward only, to a commit of the same
adapter repo that descends from the previous pin, under the same obligations as a registration (closed roles, a clean
committed tree, a recorded reason, existing catalogued keys, admitted repos), with both pins kept in the ledger and a
fresh code review and full gate required before acceptance. An admission step is corrected the same way, as the person's decision (I-125); a correction that only narrows which files are kept as evidence reruns nothing (0.7.11).

## Imported captures

A project whose gate collects no screenshots brings in captures made by hand with `wf captures import` (0.7.0, I-94).
They are held to what a gate artifact is held to: read once without following a link, copied into the attempt's
evidence by `wf` (write-once, read-only, sha256 in the manifest, checked by `wf verify`), recorded with the tree of
every repo, the importer and the note, and from then on the gate's screenshots for that tree: the evidence reviewer
must inspect each one, a change to the tree leaves them behind, and one imported after the review of the tree was
accepted is refused. What `wf` cannot verify is how the pictures were made; the record says they were imported by the
owner, and the reviewer judges what they show.
