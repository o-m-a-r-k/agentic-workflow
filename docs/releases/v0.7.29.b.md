- **A batch keeps every check its members registered (I-204, D49).** Named failure: four accepted tickets, each admitted to
  share a batch's long test run, were assembled into a batch. The HTTP and browser checks the tickets had registered
  (`wf validation add`) stayed with the tickets: the batch's reviewer was handed none, and the batch's test run selected
  none of them, so it could pass on the combined code without the tickets' required proofs. Only the reviewer noticed.
  Now:
  - `wf batch create` carries every check a member registered or corrected into the batch, exactly as the member pinned it
    (its definition, its code and the screenshots it collects), and says which ones it carried;
  - the batch's reviewer is handed them with the ticket each came from, and the batch's test run counts only once each of
    them passed on the combined code;
  - a check two members registered alike is carried once; two members that registered one check differently are refused
    before the batch exists, with how to make them the same, since the batch can run only one of them;
  - a ticket taken out of the batch takes its checks with it;
  - a long check a ticket corrected with your yes now runs in that ticket's own test run, as a check it registered does.
    Found while reproducing the batch failure: a ticket waiting for a batch put the corrected check off to the batch while
    its own test run required it, so its test run could never pass.
- **Checks registered since the last review reach the next reviewer (I-206, I-205, D49).** Named failure: six checks were
  registered on a batch before its next review, and that review was handed none of them, because a follow-up review was
  only told about corrected checks; the reviewer kept a finding that the required proof was not registered until the agent
  showed it the record. A follow-up review is now handed every check registered, corrected or carried since the last
  review, and asked for its verdict on each as pinned.
- **The way into a batch is said where it matters (I-194, D49).** Named failure: `wf batch create` refused tickets that
  had not been admitted to share a batch's long test run, and said nothing about what to do; three tickets not yet
  implemented waited for a restart nobody had described. The refusal now says: a ticket already implemented is delivered
  on its own, and one not yet implemented is admitted again with `--defer-heavy` (the exact commands are printed). The
  help for `wf entry` and `wf batch create` says how a batch member is admitted.
- **A screenshot cited wrongly is caught while the reviewer can still fix it (I-154, I-175, I-197, D50).** Named failure:
  on three tickets in two days a reviewer cited several screenshots in one place (their fingerprints or paths joined by
  commas or semicolons, or a pattern); the review was recorded, acceptance refused it only after the reviewer had finished,
  and the next reviewer, told nothing, did the same: a whole review round lost each time. Now:
  - recording an evidence review runs the same check acceptance runs, and a citation that is not one screenshot the test
    run collected is refused there, saying when it names several screenshots or a pattern; the review stays open and the
    same reviewer corrects it;
  - each piece of evidence names one screenshot (or test), and a criterion several screenshots show lists each in its own
    entry; the reviewer's instructions show that shape;
  - when acceptance refuses a review, its reasons are recorded and the next evidence review is handed them.
