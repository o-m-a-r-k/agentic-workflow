## 0.6.5 - Add required sealed validation after admission

Required HTTP or browser proof discovered after admission can now join the normal full gate without replacing
the frozen adapter or merging product code first.

- `wf validation add --steps <ids> --criteria <ids> --reason "..."` registers new step IDs from the attempt's
  committed adapter. The adapter repo must belong to the attempt, and the commit must descend from admission.
- Admission checks, their plugin pins, review rules, environment policy, delivery and tracker configuration remain
  unchanged. Additions cannot replace existing IDs, add repos, alter secret stores or select unknown keys.
- Registration invalidates prior acceptance and proof. A fresh independent code review must inspect each added
  definition and its plugin at the recorded commit; the full gate then runs all required checks.
- Passing required steps produce ordinary sealed logs, reports and captures. Every screenshot remains subject
  to fresh evidence review, exact hashes, inspection and normal acceptance rules.
- Missing, failed, skipped or deferred required execution cannot count as passing proof. Review/gate locking,
  cleanup, redaction and no-follow evidence writes retain their existing paths.

I-90 regression scenarios cover additive HTTP/browser proof, frozen plugin identity, stale acceptance, replacement
refusals, step-specific secret bindings, missing review verdicts, failures, skips and screenshot inspection.
