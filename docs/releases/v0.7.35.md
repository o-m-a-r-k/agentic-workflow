## 0.7.35 - A reviewer can read the adapter snapshots its bundle hands it, and a read survives a worktree removed under it

- **The adapter snapshots a reviewer is handed can be read through `wf evidence` (I-235, D89).** Named failure (three reviews on two
  attempts): since 0.7.32 a reviewer judging a corrected admission check is handed the check's plugin at the admission original,
  the previous correction and the corrected version, each with a decoded copy. `wf evidence show` and `wf evidence inspect` refused
  every one of them as a read outside the attempt, and `wf evidence list --kind adapter` showed nothing, so reviewers rebuilt the
  files from git themselves. Now a snapshot reads when a reviewer bundle of the same attempt names it, and only then: the file must
  be where the workflow writes that plugin at that commit, and its bytes must be the committed text (expanded, for the decoded copy),
  else nothing is read and the refusal gives the `git show` command that prints it as committed. `wf evidence list --kind adapter`
  lists each handed snapshot once, with the bundle and correction that handed it, and the reviewer's instructions name both commands.
  The workflow now writes these copies read-only. Another attempt's snapshot, or any other file in
  that folder, stays refused (`evidence:adapter-not-handed`), and every other attempt's evidence stays a cross-attempt read.
- **A read no longer fails when another command removes the attempt's worktree while it reads (D90).** Named failure (CI, one
  macOS shard): a `wf status` waiting for the evidence lock while `wf deliver` wrote ran on after `wf shown` had closed the attempt
  and removed its worktree, and failed with "worktree missing". `wf status`, `wf resume` and `wf signals` now start again when a
  worktree disappears under them, and report the attempt as closed, or as orphaned when it is still open. Commands that change
  something still stop on a missing worktree.
