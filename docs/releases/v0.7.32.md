## 0.7.32 - No more stuck tickets that only your override could free

- **A problem only the test run can show no longer waits for a code review that cannot see it (I-222, D69).** Named failure:
  the final review of a ticket found two problems that only the test run's output shows (a report header drawn over the first
  row in the screenshots, and a required check that never ran). After the fix, every code review honestly said it could not
  confirm them, because a code review is never handed the screenshots or the test output. The workflow then refused to start
  the test run until a review confirmed them, and the only way out was asking you to override the order: that ticket is still
  waiting on the question. In one project's records, 25 code reviews on 9 tickets kept such a problem open, and at 4 of them the
  test run was refused for it. Now:
  - a problem the final review raised that a later code review keeps open with what it checked does not hold the test run back,
    whatever it is about and whether or not a new check was added for it; the next step names those problems and says the test
    run proves them, and the final review after it confirms them; the ticket is still not accepted until that review does;
  - a problem a code review raised and keeps open still holds the test run, and so does one the final review found still broken
    in the test run's own output;
  - when a check is added after the final review, its definition still gets a code review first (that is real review work), and
    the problems that review cannot see no longer hold the test run after it;
  - replayed on the stuck ticket's own records, the next step at the point where you were asked is now the test run.
- **A fix of what the final review found goes straight to the test run again (I-222, D70).** Named failure: the shortcut that
  sends such a fix directly to the test run (the final review after it checks the fix) was switched off by bookkeeping: a plan
  update that only regrouped the same problems into one fix, or corrected an estimate, sent the finished fix to a code review that
  could not check it, which then ran into the problem above. Only 5 of 16 such fixes in one project's records took the shortcut.
  Now the shortcut looks at the work, not the bookkeeping: every implementer handed after the final review is finished (one that
  was stopped counts only when a later one finished its work), the code is what the last of them left, and nothing new was added
  (no requirement added, changed or removed, no repository added, no new check). It also applies when the final review found an
  earlier problem still there. When a check was added after the final review, the next step now says the code review it needs,
  as the test run itself does: in two tickets the next step had named the test run and the test run refused to start.
- **When you settle a disputed premise, your answer settles it (I-222, D71).** Named failure: when a reviewer and an
  implementer disagreed on whether a problem is real in production, the workflow said you decide, and then nothing read your
  answer: the item stayed out of every fix, and a review problem had no way to be closed as "not a problem" at all. Now:
  - "it is not a problem" closes the item as not a defect, through one question you answer, for a review problem
    (`wf scope not-a-defect`) as it already did for an issue found during the work; it stays in the record with the reason, and
    the delivery note does not list it;
  - "it is a real problem" sends it back to be fixed, with your words handed to the implementer; your answer can come from that
    question or from your own words, recorded with `wf decide`, which now names the item;
  - your answer stands: if an implementer reports the same doubt again, the agent is told to bring you what changed, never to
    decide it itself; and while you have not answered, the next step is your question, not another reviewer who is never shown it.
- **A change pushed outside the workflow has a way on (I-222, D72).** Named failure: when a commit made after the acceptance
  was pushed by hand, the next step said "deliver", the delivery refused and pointed at reopening the ticket, and reopening
  refused because the ticket was never delivered. Now the refusal names what works: the pushed code is reviewed, tested and
  accepted in the same attempt (the next step names each), after which the delivery records it as delivered without pushing
  again; or you decide it shipped as it is. The next step says the same, also when a commit was made after the acceptance and not
  pushed.
- **Review of this release: the pushed code is now really reviewed and tested (D69, D70, D72).** A review of this release found
  that the route above reviewed and tested nothing: once the main branch held the pushed commit, the change looked empty, so the
  test run skipped every check and the reviewer was shown the pushed code as someone else's. The pushed code is now read as the
  ticket's own until it is accepted, so its checks run and the reviewer reviews it. A ticket whose code was reset to the main branch
  is no longer mistaken for one pushed by hand: the delivery says to put the accepted code back. Also: new work added to a ticket
  after the final review (a new piece of work in the plan, even with the same requirements) goes through a code review again before
  the test run, as it did before this release; a code review that sees a problem from the final review still in the code raises it
  as its own problem, which holds the test run; and a planned batch of small fixes built while such a problem waits for the test run
  goes to the test run, as other batches do.

- **A corrected test check is judged by the reviewer, never asked of you (D78).** In your words: "why should it come to me? we have
  an agent designed just for that in the workflow right?" Correcting a test check that was fixed when a ticket started asked you
  every time: 20 questions on 10 tickets in four days, 7 on one ticket, while an independent review and the full test run followed
  anyway. Now the review that follows judges it, and you are not asked. The reviewer is handed the check as it was when the ticket
  started, the previous correction if there was one, and the corrected version, with the embedded test code decoded so it reads
  line by line, and checks that nothing was lost: every test case and every check survives, and only what the ticket's requirements
  deliberately change is updated. A removed, skipped or loosened check, a weakened expectation or a longer timeout that hides a
  failure is a problem the ticket fixes before its test run; only you can let one stand. In the past corrections nothing frozen at the
  start was lost, but four loosened checks the same ticket had added earlier, and the summaries you approved named none of it: the
  reviewer now compares against both versions, and test code moved out of the check into another file is followed too. The original
  check and both versions stay on record; a ticket is not accepted until a reviewer has judged the correction. A question about a
  correction that is still open is withdrawn with the reason; an answer you already gave stands. When one defect in a check affects
  every ticket (seven tickets corrected the same one), the agent is told to fix it once in the project's setup on its main branch,
  which every ticket then follows.
- **A ticket may register the proof it needs, and is told how (I-220, D73).** Named failure: `wf validation add` refused "supplemental
  step X is not committed in the attempt adapter" and said nothing more, while the rules every agent reads said "never change the
  workflow from a ticket". A finding that asked for proof on the final tree stayed open 37 minutes, a strategist escalated it to you,
  and you had to answer before the check was registered. Now the refusal names the route (commit the step in the attempt's own
  worktree of the repo that holds the project's adapter, then register it), and the session rules, the work skill and the
  implementer's instructions tell the two apart: the workflow (the plugin) is never changed from a ticket; the project's adapter is
  where a ticket adds its own checks, by design. Adding a check loosens nothing: the ticket is still judged by the adapter on its base
  branch, never by its own adapter change, and only the checks it registers run from its commit.
- **A step with no way to prepare its dependencies says what to do meanwhile (I-219, D74).** Named failure: `wf run --step` was
  refused three times for a step whose plugin cannot install its dependencies before the first commit, and the refusal told the
  implementer to add that to the plugin, which a ticket cannot do. Now it says what to do meanwhile (the package's own install and
  test commands, or commit and run `wf check`), that the implementer says so in its report, and that only the project adds a
  preparation route, in its adapter on the base branch, which the ticket then follows by itself.
- **`wf check` says which untracked files stop it, and why (D74).** Named failure: 17 refusals for a folder an IDE writes by itself
  said only "commit changes before the check". Untracked files still stop a check or a gate: the run reads the folder as it is, so a
  file no commit holds would be part of it (in the same records an untracked new source file was part of the change). The refusal now
  names each one, says why, and gives the three ways on: commit it, delete a tool's output, or have the repo ignore it.
- **A passing rerun keeps the screenshots of the tests it carried (I-221, D75).** Named failure: a gate passed by rerunning only the
  2 test files that failed in the run before it and keeping 1251 tests from that run, but none of that run's 170 screenshots, so the
  end-to-end step looked as if it had collected nothing and the reviewer opened the earlier run's files by hand. Now those screenshots
  come with the tests: each is checked against what was recorded, names the run that took it, and is handed to the evidence review
  and exported as this gate's evidence.
- **Evidence a gate failed to collect can be collected again without a dummy change (D75).** Named failure: nothing could re-run a
  step on a tree that had not changed: a gate reuses what already passed, a rerun of failed steps is refused after a passing gate, and
  the open finding held the gate back, so the only ways on were a commit made for nothing or asking you to override. Now an evidence
  reviewer can say a finding is cured only by running a step again (its screenshots were never taken, nothing in the code is wrong);
  the next step is then one gate on the same tree, which runs that step again in full, and the evidence review after it checks the
  finding. This is offered once for each version of the project's checks: if the new run does not cure it either, the next step no
  longer hands an implementer something with nothing to build; it says the cure is in the check itself (for example which
  screenshots it collects), fixed in the project's own setup on its main branch, which the ticket then follows by itself, and the
  run is offered again after that. A finding in the code is raised as an ordinary finding and fixed like any other. A reviewer that
  names a step the run does not have, or asks for a run again without naming the step, is told so while it can still correct it.
- **A divided review that can never finish says so (D76).** Named failure: the reviewer that combines a divided review asked for its
  parts 169 times over 89 minutes and then waited six hours, because one of the reviewers it waited for had ended without recording
  its part. Now that reviewer is told no part will come and to stop, and the next step stops it and starts a fresh divided review.
- **Reviewers can name evidence files the way the project names them (D77).** Named failure: 78 refusals for paths written from the
  project's top folder, which were read as relative to the ticket's evidence. Both forms now work; a read still never leaves the
  ticket's own evidence.
