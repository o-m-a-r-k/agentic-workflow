## 0.7.31 - A full investigation before any recommendation or fix

- **A fix is built only on a premise someone traced (I-217, D64).** Named failure: a reviewer noted a small display problem, a
  due date shown with a clock time on one page and as a date on another. You were asked to decide before anyone researched it,
  the research that followed said nothing in the product actually writes that date, and that was read as "so no wrong data
  exists, the change is safe". The small item became a change to four of the API's data shapes and a new way for a request to
  fail, built in a fix round with no plan, and it was reverted after you asked whether anyone had done a proper analysis. The
  same shape was in the records five more times. Now:
  - every role is told, and the session rules say, that before anything is recommended to you or a fix is built for a finding,
    it knows who writes the data in production, who reads it, which business process and outside systems depend on it, and what
    happens when it is absent, and says what it did not check; a fact that contradicts the premise ("nothing writes it") is a
    stop and a question, never a reason the change is safe;
  - an implementer says, for each problem it fixes, whether its premise holds and what it checked; when it does not hold, it
    builds nothing for it and says why, with the evidence. That item is not handed to another fix round; the next reviewer
    judges the premise (not a problem after all, which closes it, or a real one, which sends it back), or you are asked whether
    it is a defect at all, and it is settled before the ticket is accepted;
  - a reviewer judges the premise of a fix as well as the fix, and "the premise behind the fix does not hold" is a reason it can
    close a reported problem with, with its evidence;
  - a fix that needs a change to a contract (a data shape, a route, an error code) or a new way to fail is planned again, like a
    migration or a new endpoint already was; from a small item fixed alongside, it is never built in that pass;
  - a plan lists who writes the data beside who reads it, and a strategist grouping findings names the premise they share; one
    nobody traced is investigated before a fix round;
  - when a fix round's or a planned pass's own changes reach a contract or a migration, the strategist decides whether that
    stands before anything else is handed, and before the test run after a pass. The rule that an implementer expecting more
    than twice the reviewers' estimate goes to the strategist keeps "more than twice": the estimate in this case did not cover the
    small item at all, so the new check watches what the work did instead.
- **A product decision you make outside the workflow is recorded (I-217, D65).** Named failure: the decision above was asked
  through the question panel with no record of the question, what the recommendation rested on, or your answer. Now a
  recommendation to you says in plain words what was traced, what was not checked and the evidence, and your answer is recorded
  with `wf decide`: the question, the recommendation, what it rests on, what was not checked and your own words, which the
  workflow checks are yours as it does for any answer it reads. It is a record, never a step anything waits for. `wf resume`
  shows it, every later planner, implementer, reviewer and strategist is handed it, and when an analysis changes the picture it
  is withdrawn with what changed and you are asked again.
- **What the agent running a ticket tells an implementer is on record (I-217, D66).** Named failure: every brief in that batch
  lived only in the prompt an agent was started with, so "nothing writes it, so no wrong data exists" reached the implementer
  with no trace. What the agent carries to an implementer (your words, a decision, what research found) now goes into its record
  and its instructions, as it already did for a planner, and the implementer is told to check it rather than take it as fact. A
  reviewer still starts blind and gets none of it.

- **An analysis has a route from plan to finish (I-216, D67).** Named failure: an analysis ticket's plan was accepted with
  investigation-only steps, the next step told the agent to hand the work to an implementer, and that step was refused
  because an analysis changes nothing. Nothing recorded what the analysis found, and an analysis you did not turn into an
  implementation could only be abandoned. Now:
  - after the plan, the next step is the investigation itself, read-only, done by the agent or a read-only helper; an
    analysis is never told to hand work to an implementer;
  - the agent records what it found with `wf analysis record`: an answer for every question the plan asked, with what each
    answer rests on (the file, the query, the command and what it showed), or why it could not be answered; what else it
    found; what it traced and what it did not (where the data comes from and goes, the business process, outside systems);
    and its recommendation. A record with a gap is refused, naming each gap;
  - then the agent tells you what it found and what it did not trace, and what follows is yours: implement it in the same
    ticket (a fresh planner then plans the change, given the analysis, before anyone builds), or close the analysis
    (`wf analysis close`), whose findings stay on record and are given to the planner of the ticket's next attempt;
  - `wf analysis show` prints the analysis for you or for a ticket, also once it is closed;
  - an analysis can now be started while the ticket's implementation is in progress, to trace what a fix rests on before the
    next fix round; what it records is given to the next implementer of that ticket.
- **Your tracker's own instructions come first (I-215, D68).** Named failure: when the agent was told to post the delivered
  screenshots, the workflow said to put image links in a comment, while the project's tracker adapter said to add a native
  page section with uploaded images; the agent followed the workflow's line and the ticket got a comment without images.
  When the agent works the tracker through its connector, each tracker step it is told to do now starts with the adapter's
  own instructions for that step, word for word, followed by the workflow's wording of what the step carries (the status,
  the comment, the screenshots). An adapter that gives no instructions leaves the wording as it was; the built-in Linear
  adapter's instructions are shown too.
- **Review of 0.7.31: fewer false alarms, and the gaps a review found closed (D64, D65, D67).**
  - The check that a fix reached a contract or a migration fired too often. A review counted 35 of 155 fix rounds in one
    project's records, mostly planned work updating an API description along with an endpoint change. It now fires only on
    what nothing handed to that round explains: not on planned work being built, not where a reviewer's finding pointed at
    that file or the reviewer's suggested fix named it, and, for a round fixing only blocking problems, not on a file the
    ticket's own planned work had already changed. Measured again on the same records: 1 of 279 rounds, and that one is
    the due-date change that started this release. When two implementers work in one repository at once, it names both
    rather than blaming one, and a notes file in a migrations folder no longer counts as a migration.
  - `wf decide` records the options you were offered, and the choice has to be one of them, so a later reader sees when
    every option built the same change. A reviewer is given your decision, the options and what was not checked, never the
    agent's recommendation or its reasons.
  - What a reviewer finds about a fix's premise is kept with the problem it judged. A finding whose premise an implementer
    found false reaches the evidence review after a planned pass, with the implementer's evidence, and is marked when it is
    handed again beside other fixes. When a reviewer and an implementer disagree on whether a premise holds, you decide it,
    not a third agent.
  - An analysis run beside a ticket already being built can no longer be turned into a second implementation of the same
    ticket, and only one analysis of a ticket is open at a time.
