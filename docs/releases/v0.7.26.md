## 0.7.26 - A moved base reaches a delivery waiting on a merge request; a ticket's handoff shows its own screenshots

- **A base that moved while a merge request waits can be brought in (I-183).** With a delivery adapter whose merge a
  person makes (a merge request), the base branch moved after the first `wf deliver`. `wf base merge` refused ("already
  being delivered"), and every later `wf deliver` only checked the merge request again, so the branch stayed behind the
  base and the merge request could not be merged as reviewed. Now:
  - `wf base merge` brings the base into every repo the ticket changes that is still to deliver. A repo already
    delivered or skipped, a repo the ticket changes nothing in (also when named with `--repo`) and a repo whose request
    was merged are left as they are, and the output says so. An adapter that cannot be read makes it refuse, naming why.
  - **One rule for adapters (D31):** a base merge on an accepted attempt whose delivery goes through an adapter
    withdraws the acceptance, whether or not a delivery has started, and also for attempts admitted before this
    release: it ends a dead end and adds no obligation. The gate runs on the combined code, then the evidence review (or
    a code review first when the base touched the ticket's own lines), then `wf accept`. The next `wf deliver` hands the
    reconciled branch to the adapter again, and the person's merge of it is recognised.
  - A base merged by hand in a worktree (or after `wf base merge` stopped on a conflict), or a commit made after the
    acceptance, moves the tree without a record: `wf deliver` now refuses to hand an adapter a tree the acceptance does
    not name, naming both, and `wf resume` and `wf advance` read that acceptance as none (gate, evidence review,
    accept). Before, the person's merge of such a tree was refused as "pushed outside wf".
  - Built-in push-main keeps its own behaviour: the acceptance stands, and once delivery started `wf deliver` merges the
    base itself.
  - A review round still covers the change when only the base moved: it is compared on the repos with a change still to
    deliver, so a repo already delivered, or whose request was merged and not recorded yet, no longer makes a base merge
    that leaves the ticket's lines alone ask a new code review (the person's rule: no rerun that adds nothing). A commit
    made in such a repo afterwards is compared again.
  - A repo recorded for the delivery is final: a commit made in a repo recorded as skipped, or after it was delivered,
    was never delivered and `wf deliver` finished without it. It now refuses, naming the repo, and `wf resume` says the
    change belongs to a new attempt.
  - `wf deliver`, while it waits, says when the base moved meanwhile, and `wf resume` names the evidence review after the
    gate on a moved tree.
- **A ticket's handoff shows its own screenshots (I-182, D32).** After a combined delivery, each ticket's handoff held
  only the screenshots tagged for every ticket, and none of its own. The cause was not a cap: a capture tagged with the
  ticket's item id was never matched, only its attempt id. Now each handoff draws from every verified capture:
  - captures a criterion of the ticket cites come first, then the ticket's own, then shared ones; captures tagged only
    for other tickets stay out. Nothing is cut at a number.
  - `wf delivery list` shows every verified capture, its place, and whether it is in the set; `wf delivery narrow` can
    add any verified capture, not only one already in the set.
