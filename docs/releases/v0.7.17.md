## 0.7.17 - Known limits a tester can read, with nothing left out

- **The delivered comment lists every known limit once, in plain words.** One delivered comment carried 53 lines of known
  limits. 25 of them were per-round reviewer notes with file paths and test counts, and the deferrals carried their ids,
  ratings, "Why it waits" and "Decided by". The comment now lists, once each:
  - every known issue left for later;
  - every part of the change a review named as not checked, from every round since the last complete full audit;
  - fixes no reviewer saw;
  - follow-ups.

  Nothing is counted away or capped. Each line is the item's first sentence. Ids, ratings, who decided and why an item
  waits stay in the `wf deliver` output and `wf export`.
- **The owner words items for the tester.** `wf summary` and `wf deliver` list each known-limit item with its ref.
  `wf summary --file <summary.md> --explain <lines.json>` (`{ "<ref>": "<one plain line>" }`) gives any item the owner's
  wording, which is kept until replaced. Items worded the same show once, so items that read alike can be joined. A ref
  that is not an item, or wording that carries file paths or hashes, is refused with the valid refs. The plain line the
  person was asked with (`wf scope defer|ticket --explain`) is kept on the decision and used as well.
- **The writers are told how to write these lines.**
  - A reviewer's finding summary and an implementer's `left` item start with one plain sentence a tester would understand,
    with file and test detail after it.
  - A reviewer's `notReached` names only scope its round did not check, as a sentence a tester could act on. The steps the
    gate runs and the criteria a delta round does not re-judge are not unreached scope. On one ticket, 50 of 80 such notes
    were of these two kinds.
- **A comment edited in place passes the readback.** When the person wants the comment worded differently, the owner
  changes the summary or the items' wording and edits the posted comment to the new rendering, so the ticket keeps one
  comment. With a connector, the host-recorded readback counts an edit made by the comment's own id when the ticket's
  comment list holds that id; before, only a comment created against the issue counted.
- **An anomaly that needs no follow-up is recorded with a `cause`.** The `wf shown` hint says so, because the tester reads
  each `followUp` in the delivered comment.
