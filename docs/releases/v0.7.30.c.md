- **A repair starts from what already failed (I-162, I-173, I-166, I-168, D51).** Four field cases, one shape: the workflow had
  shown a cause, and the agent sent to fix it was not told.
  - A full test run failed one step, then the owner stopped it to change the code the fix needed. Only a run that ended
    as "failed" was handed to the next implementer, and this one ended as "stopped", so it got nothing. Now a stopped run's
    failed steps are handed too, with why the run was stopped, and `wf resume` says so.
  - A quick check (`wf check`) failed on two lint lines, which the owner recorded as a bookkeeping item for that piece of
    work. The implementer handed the work again saw neither the failed check nor the item, and reran the whole check
    instead of fixing two lines. Now the last failed check is handed (`failedCheck`), each failing step with its log and,
    when it names no test, the end of its output; and open bookkeeping items reach every implementer (never a reviewer,
    and they still open no extra round).
  - A follow-up review kept a serious finding open with a new reproduction of the failure. The fix round was handed the
    finding as first written, about a case already fixed, and the implementer read it as done. Now the latest evidence
    that a finding is still open travels with it (`stillOpen`), beside its original words, to the implementer, the finding
    history and the next reviewer.
  - A review said it had not reached one check on a real device. After the base was merged, the next implementer was not
    told and reran checks that already passed. What a review did not reach now reaches implementers as well as reviewers.
- **A new criterion has someone to build it (I-165, D52).** Named failure: a change to the plan added a criterion while the
  piece of work that would build it kept its old list; the implementer built what it was handed, reported nothing left,
  and the owner caught the gap just before review. Now, on tickets started from this release, a plan change that adds a
  criterion no piece of work names is refused, with the fix: list it under the piece of work that builds it.
- **A follow-up review after a base merge sees which files are the ticket's (I-167, D53).** Named failure: the reviewer was
  given six changed files and a diff command that showed forty-one, because the files the base merge brought in were in
  the diff and in no list. The files only the merge brought in are now listed apart (`baseMerged`), the two lists together
  are exactly the diff, and the instructions say which is which. A file the ticket changed back to how it was before is now
  listed too (it used to drop out).
- **A plan says what it adds beyond what you asked, and why (I-159, D54).** Named failure: a hotfix asked for as "fast,
  with the existing inbox" was planned with a new ledger, a migration, retries and retention, 180 minutes nobody asked for,
  noticed only when the plan was read. The planner now lists each addition with its reason (`beyondAsked`), leaves out what
  the request does not need, and `wf plan` prints the list so the agent tells you before anything is built.
