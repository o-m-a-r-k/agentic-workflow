## 0.7.6 - A repair after a failed gate gets its facts, and Playwright steps rerun only what failed

- I-118: a gate failed with 617 end-to-end failures, all reproducing on the base branch and 603 of them one cascade. The
  owner briefed the repair to prove itself with whole-suite runs; the implementer spent 130 of its 156 minutes waiting on
  them. Every failure is still fixed in the attempt; the gate after the fix is now the repair's proof:
  - The implementer and work-skill texts say so: the brief carries what failed and the goal, the implementer's own runs
    serve finding causes, and the next gate reruns what failed (only the failed suites, where a step allows it) and reuses
    what still passes. The owner's estimate check: an estimate is judged when it is written, not only when it is passed.
  - The implementer's bundle after a failed gate carries `failedGate`: the gate's tree and whether it is the current one,
    and for each failing step the whole failure count and the names the gate kept, the failed suites, how long it last
    ran, whether it can rerun only what failed, and which failing test files the change did not touch.
  - A Playwright step's JSON report is a suite list (`report: { playwright: <file> }`, one suite per spec file; a spec that
    failed to load is a failed suite), so with `select` the gate reruns only the failed spec files, as it already did from a
    JUnit report. A step with both reports keeps one suite per id. A suite file that matches more than one input by suffix
    names none, so the step reruns whole rather than reuse another file's result. A suite with a test that did not run (the
    run stopped first, or the test was interrupted) is `not-run`: rerun, never carried as passed; where two reports or
    shards name one suite, failed wins over not-run and not-run over passed.
  - A suite that never ran is never passed over: after a run that stopped early (Jest `--bail`; a JUnit report names only
    the suites that ran), every input named like a reported suite that the run did not report is rerun with the failed
    ones; and only report files the run wrote are read, so a run that died before writing is not read as an earlier
    run's suites. A suite the gate asked to rerun that the run did not report stays
    `not-run` and the step does not pass; in a Playwright run stopped as a whole every skipped test counts as not run;
    JUnit suite files named by their extension alone (`login.ts`) rerun the step whole.
  - A failing Playwright test is counted once per project, in the log and in the JSON report (612 failures read as 448).
  - `wf doctor` names each heavy, non-plugin step that cannot rerun only its failed suites, and what it lacks (`select`, a
    suite report, `{select}` in `run`, `inputs`).
  - `wf resume <item or attempt id>` shows that attempt (the name was ignored, and the one open attempt of another item was
    shown), and `wf report --attempt <id>` reports only that attempt (it listed every attempt).
- Align the CLI package and both host plugin manifests at 0.7.6.

Regression scenarios: `scenarios/focused-repair.test.mjs` (Playwright suites rerun only the failed spec files; the
`failedGate` facts, with no prescribed method; the doctor notice; a spec that failed to load reruns; an ambiguous suite file
reruns whole; one suite per id; a spec that did not run, or was interrupted, is rerun; no merge passes a not-run suite; an early-stopped
JUnit run reruns the suites it never reported; a stale report is not read; a requested suite never reported stays
not-run; extension-only suite names rerun whole; `wf resume <item>` (and a damaged ledger of that item) and `wf report
--attempt`) and `scenarios/telemetry.test.mjs` (a test
failing in two projects is two failures); each fails on 0.7.5.
