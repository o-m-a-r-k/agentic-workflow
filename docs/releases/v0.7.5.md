## 0.7.5 - Close an attempt that shipped outside the workflow

- I-116 (D16): an attempt whose change reached its target branches by another route before its acceptance (one repo
  delivered, the others merged by hand) could be neither abandoned nor delivered, so it stayed ORPHANED in every listing.
  `wf close --shipped --reason "<why>"` closes it: for each repo the change is the attempt's own tip: its worktree's HEAD (the worktree must hold no uncommitted work), else its branch's tip, and only when both are gone the commit the workflow recorded (the delivered commit, else the head of its last passed gate, else the accepted head), named as such; the engine fetches the
  remote target branch in the repo's own checkout and refuses naming any repo whose change is not on it, any remote it
  cannot fetch (a stale ref is never taken as proof) and an attempt that changed nothing; closing without the acceptance
  is the person's decision (`wf approve`, kind `override-gate`, which also ends a hold). `wf resume`, `wf deliver`,
  `wf export` and `wf report` name the shipped close; `wf abandon` refuses an attempt that is already closed. The ledger keeps the commits, the decision and what
  was still open; the worktrees are removed; the tracker is not touched.
- `wf abandon` of an orphaned attempt now refuses when a repo's recorded change is already on its target branch, as it did
  for a worktree that exists (its branch's tip, or the recorded commit, stands for the change): a change that landed is
  never recorded as given up.
- Align the CLI package and both host plugin manifests at 0.7.5.

Regression scenarios: `scenarios/close-shipped.test.mjs` (the field case over a hold; a change not on its target branch; a
commit made after the gate, uncommitted work, an unreachable remote and an attempt that changed nothing, each refused; the
recorded commit when the worktree and branch are gone; a never-gated orphan whose change landed is not abandoned; what was
open recorded with the close).
