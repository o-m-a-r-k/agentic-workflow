# Work a ticket

Check `wf status --quiet` exits 0; otherwise this project is not onboarded (offer the onboard skill).

The user's request to implement a ticket authorizes the whole lifecycle below, including delivery, unless they say otherwise. If they say hold, local only or don't push, run `wf hold --reason "<their words>"` immediately.

Role agents are generated by `wf sync`: `wf-planner`, `wf-reviewer`, `wf-implementer` and one `wf-implementer-<class>` per other work class. Each file sets that agent's effort (and model, if the class sets one). Always start the agent type a `wf handoff` names, never `general-purpose`, and never pass `model` on the Agent call: both replace the agent file's settings. Agents written or changed by `wf sync` after this session started reach it only after a restart (`wf sync` lists changed role files; `wf handoff` warns when the role changed after the session started); if the named type is missing or the handoff warns, ask the user to restart the session instead of substituting another agent. Start every role agent, the reviewer included, under the name the handoff prints (`name it <id>`): the review is matched to its transcript by that name.

With more than one open attempt, pass `--attempt <id>` to every `wf` command; the commands `wf` prints already include it.

1. `wf entry --item <ID>` (add `--intent analysis` for investigate-only requests; analysis never delivers; with no tracker, save the request text to a file and pass `--issue-file <file>`). Perform the printed tracker actions, then record the readback from the RAW tracker response, never a hand-written one: call the tracker's read (Linear `get_issue` with the issue id), write its whole JSON response unchanged to a file, and run `wf tracker record --event admitted --capture <file>`. The admitted capture must carry the issue description; for a title-only issue add `"descriptionEmpty": true` to that file. A capture byte-identical to an earlier one is refused: read again.
2. Planner (it runs at the `review` class, the strongest model, unless the adapter changes it; `wf doctor` fails when the planner or reviewer has no model): `wf handoff planner --agent <new agent id> --session <its session id if known>`, then start the `wf-planner` agent on the bundle path. In Codex, use `wf handoff run --agent <the same id> --attempt <id>` to launch it fresh with engine-recorded exact prompt provenance; do not also spawn it through collaboration. The command waits for completion and binds its runtime session id. Configure the planner/reviewer class model and effort first (`wf doctor --runtime codex --attempt <id>`). If an existing attempt predates those settings, its owning chat runs exactly `wf models refresh --attempt <id>` to pin the committed base execution settings, then creates fresh handoffs. The admission rules stay frozen. When it reports, run `wf plan --from-agent <the same agent id>`: the engine takes the planner's last YAML block from its transcript. Never retype, summarise or reshape the planner's YAML; if `--from-agent` cannot find it (another runtime), save the planner's reply unchanged to a file and use `wf plan --file <file>`. `wf plan` lists the work items with their classes. For cross-cutting work (by default any `full` work item; the adapter's `impact.requiredFor`) the plan must carry the planner's two-stage impact analysis: a `survey` of what exists around the issue (components with their endpoint, limit, write paths, paging, empty, loading, error, permission, mobile, RTL, public-API, sorting, reorder, totals, enums and tests; consumers; flows with failure paths; defect patterns), written before the design, and an `impact` map after it (every changed symbol, endpoint, DTO, error code and migration with its consumers, flows, contracts crossed and suites that must run, citing the criteria or work items that build it, and covering or excluding every survey entry). Every list names a structured query and its hit count; `wf plan` re-runs each query and refuses a plan whose counts do not match, a survey entry left uncovered, or an impact entry that cites nothing in the design. When it refuses, send the refusal to the same planner (SendMessage) and freeze its corrected block; never fix the counts yourself. Read the impact map before you freeze: an assumption such as "no API change" stands only on a query that shows it, and `doNotRun` never bans a suite the map says must run. The survey covers every dependency of the requested change; unrelated existing defects require the scope-decision checkpoint below before becoming implementation criteria. To change criteria later, `wf criteria amend --file <f> --reason <why>` with only the changed or new criteria; the rest stay. Removing one takes `{ id, dropped: true, reason }`. An amendment that adds or changes criteria, work items or repos (a new endpoint, error code, DTO, repo) owes an impact update before the next implementer handoff: put `impact` in the same amendment file (new `queries` and `survey` entries for the added scope, and `changes` citing the new criteria or work items, with consumers, flows, contracts and suites), or `impact: { unchanged: "<why it adds no element>" }`; `wf handoff implementer` refuses until it is recorded. `wf criteria amend` and `wf handoff` warn when a plan `doNotRun` or `externalServices` restriction names a repo or suite this attempt now changes: amend the restriction, or confirm it still holds, before the implementer runs.
3. Implementers, one per work item: for each open work item `wf resume` lists, run `wf handoff implementer --work <W> --agent <new id>` and start the agent type it prints (for example `wf-implementer-light`), named with that id, on the bundle path. When the plan's `agentSplit` says the `contract` goes first, run that work item first and let it commit before starting the others; otherwise run them in parallel. Without work items, one `wf handoff implementer --agent <id>` and the `wf-implementer` agent. If an implementer reports its work touches something a stronger class covers, stop it and tell the user; do not re-classify work yourself. Make sure everything is committed in the worktrees. When an implementer reports done and its work is committed (or you stop it), close its handoff: `wf handoff close --agent <id>` (`--outcome stopped` for one you stopped). `wf handoff reviewer` refuses while any implementer handoff of the attempt is open, since the tree may still move under the reviewer; only the user may hand it anyway: they start a message with `override <attempt>:review`, then `wf handoff reviewer --agent <id> --reason "<their words>"` records the override. You run `wf handoff close` yourself, in this session (never from an implementer or any sub-agent: the engine reads who ran it); where your session is not the owner's, the owner starts a message with `close <attempt>:<agent id>` first. Closing also lets the report attribute the sub-agents it started. Telemetry, not a gate: when an amendment adds endpoints, error codes or repos, state them under `scope:` in the amendment file.
4. Before the review, read the `outside the plan` warning `wf status`, `wf gate` and `wf check` print: for every intended change no criterion covers (a capture fix, a build or `.gitignore` change), amend the criteria now (`wf criteria amend --file <f> --reason <why>`), and have an implementer revert anything unintended; the reviewer must mark each listed file covered by a criterion or a finding. Review, blind and fresh, as soon as everything is committed: `wf handoff reviewer --agent <new reviewer id>` (never the planner, an implementer, or a reviewer of an earlier round) and start the `wf-reviewer` agent with exactly the one line it printed and nothing else. No hints, focus areas, summary of what the implementers did or decided, list of what to judge, or anyone's findings or opinions, including earlier rounds': steering a reviewer boxes it in and it misses things. It writes the closure to the bundle's `reviewClosureFile` and runs `wf review --closure <its file>`, which prints only a receipt; then run `wf resume` yourself for the next step. Never resume a reviewer for another round: every round is a new agent that reviews the whole attempt against the frozen criteria.
   If the reviewer's `wf review` lists earlier-round findings to verify, let it finish that (it adds `priorFindings` and records again); never pass it findings yourself.
   **The order of work: code review to clean, then ONE gate, then the evidence review. Review and gate never run side by side.** No gate runs during the code-review rounds: any finding made while a gate runs makes that gate obsolete, and a gate on an unreviewed tree proves nothing about review. `wf gate` refuses while the latest review round has open findings or unverified earlier findings, while no review round covers the current tree, and while a reviewer is still at work; `wf handoff reviewer` refuses while a gate runs. Only the user may skip the order: they start a message with `override <attempt>:gate`, then `wf gate --reason "<their words>"` runs it and records the override in the ledger. The same holds for every owner-only decision (`acknowledge <attempt>:<repo>:<state>` before `wf deliver --acknowledge-adapter-state`, `repin <attempt>:<tip>` before `wf deliver --repin-adapter`, `abandon <attempt>:<repo>:<state>` before `wf abandon --acknowledge-integration`, `release <attempt>` before `wf release`): ask the user for the message; never type the phrase yourself or pass the flag on their behalf.
5. First use the scope-decision checkpoint below for unrelated extra findings. Fix every in-scope open finding in one cycle. A fix handoff (`wf handoff implementer` while review findings are open) needs `--sweep <file>`: one pattern sweep per open finding it covers, `sweeps: [{ finding: "<reviewer>:<id>", why: "<the defect pattern>", query: { pattern, kind: literal|regex, repo, paths, exclude } }]`, so the fix covers every instance of the pattern, not the one line the finding names. The handoff prints each sweep's hits; the implementer fixes every real instance and answers each in a commit trailer (`Sweep <id>: fixed - ...` or `Sweep <id>: clean - ...`), and `wf handoff reviewer` refuses until it has. Give one implementer a whole pattern, not one finding, sending each to the implementer of the work item it is tagged with (continue the same agent with SendMessage; a repair round is not a new handoff and is not re-classified), commit, then hand the fixed tree to a new reviewer (step 4): the next code-review round. Repeat until a round comes back with no open findings. Then run ONE `wf gate` on that tree (in the background; follow its output or `wf status`; never edit the worktrees or hand a reviewer the tree while it runs). Reuse is automatic; never rerun passing work by hand. A gate failure is fixed the same way, and the fixed tree gets a code-review round before the next gate (`wf gate --rerun-failed` and `--focused` are repair proof only and never count). Stopping a gate needs its class and reason: `wf stop --class major-finding|tree-change|owner-decision --reason "<why>"`; the ledger records the minutes of gate work discarded. Once the gate passes, hand the gated tree to a new reviewer for the evidence review: it inspects the gate logs and every screenshot the bundle's `gate.artifacts` lists for this ticket, in contact-sheet batches when there are many, and gives a `noEvidence` verdict ({ step, reason }) or a finding for every step the bundle marks `uncovered`. Every round reads every document under the bundle's `rules` and `skills` (they add to the review and never narrow it) and gives each rule a verdict with one line of evidence; the list comes from the adapter at base and the changed files, so you never pass it to the reviewer yourself. When `wf review` refuses a round for documents its transcript shows were not read, or `wf accept` for a rule without a verdict, hand a fresh reviewer the tree (its globs matched nothing although the ticket changed its package). When `wf accept` reports a step without a verdict, hand a fresh reviewer the tree; never write the verdict yourself. When `wf accept` reports screenshots not inspected, hand a fresh reviewer the tree; never narrow the globs mid-attempt (the adapter is read at the attempt's base). `wf accept` needs, on the current tree, a passing full gate and a clean closure written after that gate passed (the evidence review); its refusal names what is missing and the command to run. A review round refused because the tree changed during it is recorded in the ledger and is over: commit through the implementer, then hand the tree to a new reviewer.
6. `wf deliver --summary-file <summary.md>`: write the summary first, a few plain-language lines on what changed for the person who tests it (never the criteria pasted; `wf` adds the user-visible UAT scope, the screenshots and the known limits, and refuses a summary that repeats a criterion or says "not user visible"). It exports the delivered screenshots (the engine copies them out of the evidence, named by title and sha256-checked) and prints a **SHOW TO OWNER** block: every delivered screenshot (the copy's path, attachment title, sha256, proposed caption), or `no screenshots for <item>: <reason>`, the exact `wf export screenshots ... --to <dir>` command, and the rendered comment file. The attempt stays open until both of these are done:
   - **Reading evidence.** `wf evidence list --attempt <id>` lists the attempt's evidence files by kind with their full paths and `wf evidence show <path> --attempt <id>` prints a text file (or use the Read tool on the path). Never name the evidence folder in a shell command, also not in a commit message, echo text or grep pattern: write "the evidence folder" there instead. The guard's refusal names the token that matched.
   - **Show them in the chat.** View screenshots only through `wf export screenshots` then the Read tool: the copies are listed in the SHOW block (`wf export screenshots --attempt <id> [--to <dir>]` makes a fresh copy any time, also after close; `wf resume` names the latest). The evidence guard refuses every shell command that names `.wf-evidence/` except one plain `wf` invocation (no `;`, `&&`, pipes, `$(...)`, redirections or quotes), so never `cp`, `cat` or `curl` an evidence path: read evidence files with the Read tool. Open each copy yourself with the Read tool, then display it to the user with a caption saying which screen and which state it shows (refine the proposed caption; an unchanged proposal is refused). Claude Code: send each file to the user with the runtime's file/image tool so it renders in the chat, and publish the attempt page (below), which embeds them; Codex: put each as a markdown image `![caption](<absolute path>)` in your message and open or attach the file. If the set holds files that are not this ticket's (an over-broad glob), first keep only the ticket's, once, with the owner's reason: `wf delivery narrow --keep <sha256,...> --reason "<why>"` (`--dry-run` first to check); it rewrites the draft. An attempt delivered before 0.1.11 has only the pending attach list: the same command narrows it. With no screenshots, tell the user the printed reason; nothing to record.
   - **Investigate anomalies before the handoff.** While viewing, compare captures of the same state with each other and with the criteria: any value that differs (counts, dates, names) or contradicts a criterion is investigated to a cause (check the test data, fixtures, timing; "cosmetic" needs evidence of what you checked) or recorded as a follow-up. Never dismiss one unchecked. Record it: edit the draft file `wf deliver` names (it is outside the evidence, next to the copies) with your captions and `anomalies` (`"none seen"`, or `[{ "screenshots": [titles], "observation", "cause" | "followUp", "evidence" }]`), and run `wf shown --file <that file>`. Follow-ups go into the comment's known limits.
   - **Attach them to the ticket as files and embed them in the comment**, never links: with an engine route (`tracker.via: api`, `cli` or `files`; prefer it), `wf shown` uploads them, posts the comment with each image inline and records its own readback. Otherwise, per file, one at a time: Linear `prepare_attachment_upload` (filename and title = the "attach as" name, subtitle = its caption, exact size), `PUT` the raw bytes of the exported copy (never the evidence path) to the returned url with every returned header (`curl -X PUT --data-binary @<copy path> ...`, within 60 s), then `create_attachment_from_upload` (same title and subtitle); keep each `assetUrl`. Attachments alone show in Linear only as "added N links": post the rendered comment file (`delivery/delivered-comment.md`) unchanged except each `{assetUrl:<title>}` replaced by that upload's `assetUrl`, so every screenshot is an inline `![title](assetUrl)` under its caption; a ticket that shows the uploads only as link rows, or a comment with a placeholder left in, is refused at the readback. Never post the comment before the uploads it embeds. Set the status as printed. Save the readback RAW, never rebuilt, abridged or reformatted: run `get_issue` and `list_comments` and keep each result exactly as returned (when the runtime saved a long result to a file, copy that file; otherwise write the printed JSON unchanged), combine with `jq -s '{issue: .[0], comments: .[1]}' issue.json comments.json > capture.json`, and run `wf tracker record --event delivered --capture capture.json`. In Claude Code and Codex, after the connector actions read the issue and its comments back with the connector and run `wf tracker record --event <e> --from-transcript`: the engine takes the tracker's answer from your session transcript (host-recorded). Only when that is not possible, never retype tool results: write what the tracker showed to `reported.json` (`{ "issue", "status", "comment": { "id", "bodySha256", "createdAt" }, "attachments": [{ "title", "subtitle", "assetUrl" }], "readAt" }`, plus `title` and `description` for `admitted`), save the comment text exactly as posted to a file, and run `wf tracker record --event <e> --agent-reported --file reported.json --comment-file <posted.md>` (connector mode only; recorded agent-reported, unverified; sections the owner added to the comment are allowed and listed). It refuses a capture missing raw fields or signatures, a comment that differs from the rendered one, a screenshot not embedded by its asset, and any file not uploaded with its title and caption.
7. Report with a short summary: what changed, the proof, what's pending, and the delivered screenshots, each shown with its caption (or the no-screenshots reason).

**Scope decision before unrelated repairs.** Classify every defect from the frozen request/criteria and the actual change, including affected consumers and required validation, not from filenames or whether the impact map lists it. In-scope defects, introduced regressions and consumers missed by the plan remain mandatory repair findings. Uncertain causality remains blocking until investigated. Extra scope means an existing independent defect whose fix is not required by the request, not caused by this change, not needed to preserve a changed contract, and not needed to make required validation execute correctly. Compare base and current behavior; a warning in a passing broad suite alone is not a product dependency.

For a review finding attach `scope: { kind: in|extra|uncertain, issue: "stable defect key", reason, baseEvidence, currentEvidence, requiredByRequest, causedByChange, affectsChangedContract, requiredValidation }`. Extra scope requires all four causal checks explicitly false and concrete base/current evidence. Missing metadata stays in scope for compatibility. Keep an extra finding open until the owner chooses; classification never supplies permission. Implementer/planner discoveries use `wf discovered add --scope-file <JSON with the same scope object>` and stop before unrelated repairs.

The owning chat runs `wf scope ask`, explains the finding, its impact and why fixing it is a scope increase unrelated to the changes, and asks once for the displayed group: **increase scope and fix**, **create tickets for later**, or **ignore for this attempt**. Wait for the direct human reply; silence and agent text do not count. Record it with `wf scope decide --choice expand|ticket|ignore`. A direct "continue fixing all" uses `expand-all` and covers extra scope only within this attempt. In-scope and uncertain findings always continue repair rounds regardless of any ticket/ignore decision.

Expansion requires a criteria/impact amendment with `scopeFindings: [the approved keys from wf scope list]` before implementation. Pattern sweeps do not authorize repairing unrelated defects. Ticket choice authorizes creating follow-ups with the configured tracker; use its connected tools/API, then save each actual raw readback and run `wf scope ticket --finding <reviewer:F1 or discovered:D1> --capture <raw.json>`. Failed creation or unavailable tracking stays pending. Captures are labelled agent-reported raw readbacks, not host-verified receipts. Ignore keeps an auditable owner waiver and the risk in the final handoff. Neither disposition claims a fix, suppresses a failed required check, changes immutable evidence, or removes change-related repair obligations.

**Keep a view of the attempt.** At each milestone (plan frozen, each review closure, each gate result, delivery, `wf shown`) run `wf export --attempt <id>`. When an Artifact tool is available, publish that HTML file as a private Artifact, one per attempt, updated in place at every milestone (same artifact, not a new one); otherwise just tell the user the file path. The page is a VIEW of the ledger and evidence, never the source of truth: decisions are taken from `wf` output, and the raw plan, amendments and closures stay under `.wf-evidence/` (`wf resume` prints the export path). The export masks catalogued secrets and embeds the delivered screenshots with their captions (click to enlarge, no external requests); never add anything to the page by hand.

Agents you start must not leave background waiters, Monitors or `sleep` loops running when they report; if one does, stop it (TaskStop) before continuing. `wf status` shows when a base moved and whether it overlaps the ticket; `wf base merge` merges it in (the gate and the review then need to run again on the merged tree).

**Learn from corrections.** When the user corrects you, a ticket is reopened, a review finding has a `category`, or a delivered screenshot shows an anomaly with a follow-up, first decide: is it about the **project** (its code, repos, design system, tests, planning) or the **workflow itself** (wf, its templates, skills, guard, tracker handling, onboarding, docs)?
- Project: record a lesson in the repository it concerns: `wf lesson add --attempt <id> --repo <name> --title "..." --what "..." --cause <process|tooling|criteria|review|test|design-system|other> --mechanism <review-rule|designSystem-rule|planner-criterion-template|reviewer-checklist|gate-check|engine-change|doc> --quote "<their words, verbatim>"` (`--project` when it spans repos). During an open attempt it is committed in that attempt's worktree and delivered with the ticket; a reopened attempt records it before the review (or `wf lesson waive --reason "<why none>"`). `wf lesson apply <id>` prints the change that enforces it: propose it to the user and commit it only with their approval; never edit instructions or the adapter on your own.
- Workflow: record a plugin improvement, never a lesson in a project repo: `wf improve add --title "..." --what "..." --observed-in <attempt or step> --quote "<their words>" --class <engine|template|skill|guard|tracker|onboarding|docs|other>`. It goes to the user's own inbox outside every repo. In a plugin maintainer session, fix it in the plugin repo with a scenario test that reproduces the failure and fails without the fix, then `wf improve close <id> --version X --test scenarios/<file>.test.mjs --fix "..."`.

**Use the lessons you are handed.** Every bundle lists the lessons that apply, with why they matched. Implementers acknowledge each in a commit trailer (`Lesson <id>: applied - <how>` or `Lesson <id>: not-applicable - <why>`); reviewers give each a verdict. `wf lesson preview --attempt <id> --role <role>` shows what a role will get.

**Prior decisions are inputs, not authority.** An earlier merge, existing tests, a prior verdict or an invariant cited elsewhere say what was decided, not what should be. Re-derive each kept behaviour from who uses the surface and what they need, check the invariant applies to this subject, and rewrite a test that asserts a wrong behaviour.

`wf resume` tells you the next step at any point, including after an interruption.

Evidence is write-protected and verified at every use. If a command refuses with "the evidence of <attempt> does not match what wf recorded", stop: run `wf verify --attempt <id>`, find what changed the listed files (a tool, a gate step, a person) and tell the user. Never edit, restore or lift the protection of evidence files yourself. Only the user decides to accept a change (`wf verify --accept-changes --reason "<their words>"`, recorded and shown to the reviewer) or to delete closed attempts' evidence (`wf evidence release`).

## Codex host integration

- If native launch reports an app-server initialization permission failure before a session starts, its failed receipt is preserved. Create a fresh handoff and use the host tool's approved execution path with access to the native runtime and session store. Keep the child `workspace-write` sandbox. Never retry the same handoff, automatically escalate, or bypass a rejected approval.
- A Node reader can satisfy required document reads with leading `nodeRepl.write(await fs.readFile("<absolute path>", "utf8"));` calls (import `node:fs/promises` as `fs` first). Handed references `bundle.skills[n].file` and `bundle.invariants` also work. Keep the literal Node tool call and its output unchanged; full file content must appear in successful host output. Absent, failed, truncated or changed content does not count. Other arbitrary Node programs earn no read credit.
- After each Codex planner or reviewer handoff, use `wf handoff run --agent <id> --attempt <id>` for verified prompt provenance. It launches the frozen role with only the start line, configured model and effort, and no inherited conversation. It records the native session id and verifies the actual prompt. A running command is pending; report completion only on its successful result. Never start the same handoff twice. A failed or stopped run needs a fresh handoff. Existing encrypted desktop spawns remain unverified.
- Wait economically on the original execution-session handle. Keep unchanged checks silent; after ten unchanged checks, one short liveness heartbeat is enough. Report starts, meaningful progress, terminal results, failures and required actions promptly. Do not repeat the unchanged worktree, model, pending verdict or next-step plan. If higher-priority host instructions require updates within 60 seconds, use bounded waits of about 50 seconds and only the minimum factual liveness update; otherwise use the host's supported cadence. The launch command emits an immediate start line and one liveness line per ten eligible minute checks on stderr; these describe this live process, never review progress. Do not scan an in-flight role transcript, poll its closure file, repeat interim findings, or duplicate its analysis merely to fill waiting time. Inspect intermediate logs only for a concrete failure, suspected stall, or explicit user request. Once the command finishes, import the unchanged plan or verify the reviewer-recorded closure and its receipt, then run `wf resume`. A missing closure needs diagnosis, never owner submission. Process completion and an accepted closure are separate facts. Keep the turn active until completion or a supported durable continuation; never leave a process unmonitored merely to save tokens.
- Close completed implementers from the owning chat with one exact `wf handoff close --agent <id> --attempt <id>` call. A direct shell tool or one literal `text(await tools.exec_command({...}));` wrapper counts; unrelated scripts and child calls do not. Other owner-only decisions still need the human message.
- For host-recorded connector receipts through functions-exec, call one MCP tool directly as `text(await tools.mcp__codex_apps__linear_get_issue({id:"ENG-1"}));` (and likewise for comments/writes). Keep each invocation separate and its result unchanged.

## Optional foreground runner

After implementation is committed, the owning chat closes every implementer through the existing owner-authorized command. It may then run `wf advance --once --runtime claude|codex --attempt <id>` for one permitted operation, or `wf advance --until-owner --runtime claude|codex --attempt <id>` for up to four operations (at most eight with `--max-steps`). This is opt-in and keeps the original host execution handle. It launches fresh native reviewers with frozen role/model/effort settings, runs the normal gate only after valid code review, obtains fresh evidence review, and accepts only through the existing checks. It stops for findings, failures, missing closures, holds, scope/authority needs, or uncertain runtime liveness. Do not create a second runner or reviewer while that handle is pending.

Keep the owning chat as the user's interface: show starts, meaningful phase results, failures and required decisions; retain host-mandated commentary rules. Process completion is separate from workflow validity. The terminal result contains both plus the next decision. Route repairs through the existing implementer; the runner never retries, amends criteria, closes implementers, lifts holds, adopts, changes models, overrides checks or delivers. A lost handle is not proof of a dead reviewer. Diagnose or recover it before manually creating a fresh handoff. Claude native launch uses the runtime's normal permission checks and uses the frozen role tool set and permits plain `wf` commands; commands needing additional permissions remain refused. No background daemon, wake-up guarantee or silent-chat claim is provided.

The owning chat routes in-scope repair findings to their implementer; never fix them yourself. A scope choice never authorizes leaving an in-scope defect. If another work item owns the file, record the discovered issue with `--blocked-by <work item>` and route it to that implementer. Existing owner-only `wf discovered close --deferred` decisions remain supported; Never defer one yourself. Amend the criteria when a related consumer is missing; do not ship a cosmetic workaround.
