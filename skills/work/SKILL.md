# Work a ticket

Check `wf status --quiet` exits 0; otherwise this project is not onboarded (offer the onboard skill).

The user's request to implement a ticket authorizes the whole lifecycle below, including delivery, unless they say otherwise. If they say hold, local only or don't push, run `wf hold --reason "<their words>"` immediately.

Role agents (`wf-planner`, `wf-implementer`, `wf-reviewer`) are generated by `wf sync`. A session that was running when they were generated may not have them registered until it restarts; then start a general-purpose agent and tell it to follow the role file (`.claude/agents/wf-<role>.md`, or the runtime's equivalent) as its instructions.

1. `wf entry --item <ID>` (add `--intent analysis` for investigate-only requests; analysis never delivers; with no tracker, save the request text to a file and pass `--issue-file <file>`). Perform the printed tracker actions, save the raw responses, run `wf tracker record --event admitted --capture <file>`.
2. Planner: `wf handoff planner --agent <new agent id> --session <its session id if known>`, then start the `wf-planner` agent on the bundle path. Save its YAML and run `wf plan --file <yaml>`.
3. Implementers: when the plan's `agentSplit` allows parallel work, have one implementer commit the `contract` first, then hand off one implementer per repo or area (`wf handoff implementer --agent <id>` for each; several are allowed) and run them in parallel. Otherwise one `wf handoff implementer --agent <id>` and the `wf-implementer` agent on the bundle. Make sure everything is committed in the worktrees.
4. `wf gate` (run it in the background and follow its output or `wf status`). Never edit the worktrees while a gate runs. On failure, read the step logs, fix the root cause (through the implementer), commit, rerun. Reuse is automatic; never rerun passing work by hand. `--focused` is for repair rounds only: review and delivery need a gate without it.
5. Reviewer, blind: its prompt carries no hints, focus areas, summary of what the implementers did or decided, list of what to judge, or anyone's findings or opinions; steering a reviewer boxes it in and it misses things. While the gate runs, start the `wf-reviewer` agent with a reviewer id (not the planner or any implementer) and only this line: `Review the committed diff of attempt <id> in <worktree paths> against its base; the bundle follows.` After the gate passes, `wf handoff reviewer --agent <that same id>` and resume that agent with exactly the one line it printed (the bundle path; the bundle holds the criteria, amendments with reasons, plan, diff locations, gate evidence and screenshots) so it checks the gate evidence and screenshots; it writes the closure to the bundle's `reviewClosureFile`. Then `wf review --closure <its file>`. Fix every open finding and any gate failure in one implementer cycle, gate again, and hand to the reviewer again until all findings are fixed or verified non-issues. `wf accept`.
6. `wf deliver`. Then do the printed tracker actions (comment, screenshots, status), save the readback, and `wf tracker record --event delivered --capture <file>`. Show the user every delivered screenshot with a caption.
7. Report with a short summary: what changed, the proof, what's pending.

`wf resume` tells you the next step at any point, including after an interruption.
