# Work a ticket

Check `wf status --quiet` exits 0; otherwise this project is not onboarded (offer the onboard skill).

The user's request to implement a ticket authorizes the whole lifecycle below, delivery included, unless they say otherwise. If they say hold, local only or don't push, run `wf hold --reason "<their words>"` at once.

`wf resume` always names the next step. With more than one open attempt, pass `--attempt <id>`; the commands `wf` prints already include it.

## The goal: finish, not just keep going

The plan predicts how long the ticket takes, and you judge whether it is on course, not the engine. Agents predict: the planner's plan states what it expects (`plan.expect`: files, review rounds, minutes to delivery), each implementer its approach and expected minutes in its report file (written early, completed at the end), each reviewer its scope and expected minutes in its closure, and the strategist its own prediction. `wf resume`, `wf status` and `wf signals --attempt <id>` show every one beside what happened (changed files, rounds, minutes since admission, each running role's elapsed time and last activity against its own estimate). No number in the engine stops a handoff or a role; reading the comparison is your job, and when an actual passes its own role's estimate the `next:` line of `wf resume` says so first. An estimate is a prediction to judge when it is written, not only when it is passed: one far from the size of the work handed (a long estimate for small fixes) is a question about the role's approach, asked then.

**At each round boundary** (a review round recorded, an implementer closed, before every repair round) look at plan against actual and analyze: what explains the difference (the cause and the class of the problem, not the one instance), and is the approach converging? Signs it is not: the blocking findings did not go down since the last round, each fix widens the diff, implementers keep discovering consumers one at a time, a role is far past its own estimate with no recent activity (look at it; a stalled one is stopped and re-handed, never polled). When the course diverged and you cannot explain it away, change the approach instead of repeating it: hand the strategist (below) with what you saw as its `--reason`, or re-plan (`wf criteria amend`, whose file may carry the new `expect`, and whose `--reason` is the record). A difference you can explain, in a ticket that is still converging, needs neither; say it in your next report to the user.

What stays a hard stop: at 10 review rounds the decision is the user's: bring them the brief from `wf signals` (the numbers, what keeps coming back, 2-3 options and your recommendation); the next handoff opens the decision they answer with `wf approve` (continue for another 10; split: unstarted work items, observations and discovered issues move to a sibling attempt with `wf split`, code already built stays; deliver-core: what the criteria need and what blocks stays, and every other finding or discovered issue recorded before the answer may be ticketed under that one decision, never one raised after it (the one way a medium or high item leaves); or stop). Handed rounds count, recorded or not. A strategist's escalation awaits `wf approve` too, and two missed strategist predictions in a row make its next decision an escalation.

## Give every agent a goal, not a method

Each role gets the goal of its step and what good looks like; the engine checks the facts at the boundaries. Never brief an agent with how to do its work, which files to stay in, or which tests to skip, and never steer a reviewer. What you add to a role's printed start line, if anything, is context it lacks (for a fix round: the cause you found), never instructions.

| Step | The role's goal | Checked by |
| --- | --- | --- |
| Plan | targets an implementer can build and a person can check, with the quality bar turned into targets for this ticket | the engine re-runs the planner's queries |
| Implement | its criteria hold on the whole combined tree and nothing it touched regresses; it has reviewed its own diff against the criteria, the quality bar and the invariants before it reports | `wf check` on the combined tree, the implementer's report, the review |
| Review | the truth about whether the change meets its goals and what it broke | the engine decides what blocks |
| Strategy | the attempt finishes at the lowest cost that keeps its guarantees | its prediction, shown against what happens |

## Analyze before deciding

When the user, a finding, a failing gate or a discovery would change scope or approach, stop before acting: find the cause and the class of the problem (not the one instance), state the options with their cost and risk, pick one with a reason, and record it (the amendment's `--reason`, or a strategy decision). An aside from the user is a direction to analyze, not a command to apply within seconds; when it widens scope, tell them what it costs (rounds, time, a sibling attempt) before you act on it.

## Roles

Role agents come from `wf sync`: `wf-planner`, `wf-implementer` (and `wf-implementer-<class>`), `wf-reviewer`, `wf-strategist`. Start the agent type a handoff names, under the name it prints (`name it <id>`), on the bundle path it prints, and nothing else: never `general-purpose`, never a `model` override when you start it. If your harness cannot start an agent type by name, launch every role with `wf handoff run --agent <id> --attempt <id>` (native launches load fresh engine instructions, the frozen model and effort, and record the session id); a failed or finished launch is never reused: create a fresh handoff. A role file changed by `wf sync` after this session started reaches it only after a restart; if a handoff warns, ask the user to restart.

**Never poll.** Run a role in the foreground (`wf handoff run` waits for it, and hands control back once the role passes its own estimate while it keeps running: then judge it, `wf handoff wait --agent <id> [--minutes N]` to follow it again with your own new expectation, or `wf handoff stop --agent <id>` and a fresh handoff; a role that states no estimate of its own, such as the planner or the strategist, gets yours at launch: `wf handoff run --agent <id> --minutes N`) or wait for the host's completion notification. No `sleep` loops, Monitors or repeated `wf status` while a role works. `wf signals` shows each working role's last transcript activity beside its own estimate; look at that once at a round boundary, not in a loop.

## The loop

1. **Admit.** `wf entry --item <ID>` (`<ID>` is the tracker's ticket id such as `ENG-12`, never a page or database UUID; a project with another id shape sets `tracker.itemPattern`; `--intent analysis` for investigate-only; an analysis attempt can later become an implementation with `wf intent implementation --attempt <id> --reason "<the user's request>"`, then hand a fresh planner, whose plan replaces the analysis one with `wf plan` until the first implementer; with no tracker, save the request to a file and pass `--issue-file <file>`). Perform the printed tracker actions, then record the RAW tracker response (Linear `get_issue`, whole JSON unchanged) with `wf tracker record --event admitted --capture <file>`.
2. **Plan.** `wf handoff planner --agent <id>` (`--context "<what the user asked>"` carries the user's words or a decision to the planner); start `wf-planner` on the bundle. When it reports, `wf plan --from-agent <id>` (never retype its YAML; on another runtime save its reply unchanged and use `wf plan --file`). For cross-cutting work the plan carries the survey and impact map with queries; `wf plan` re-runs the queries and refuses mismatched counts: send the refusal back to the same planner (a fresh handoff for an engine-launched planner), never fix counts yourself (a refused or unreadable plan is kept and handed to the next planner in `priorPlanRefusals`). Read the impact map before freezing. A ticket that sweeps many modules (for example "every table") is planned as module batches: separate work items, or sibling attempts in one batch (`wf split`), not one giant diff. In an investigation, query the read-only sources (logs, database, cluster, tracker) before asking the user for a fact. A criterion that needs screenshots needs a route to them: a gate step that collects captures, or, where the project has none, captures taken on the reviewed tree and brought in with `wf captures import` (`wf plan` warns when neither exists).
3. **Implement.** `wf handoff implementer --agent <id>`: an implementer handed without `--work` covers every work item no implementer has started, so no plan amendment is needed for one implementer to build several; `--work <W>` hands one item, for items built apart or in parallel. Start the agent type it prints. A `contract` work item goes first when the plan says so. When an implementer reports done and committed, close it: `wf handoff close --agent <id>` (`--outcome stopped` for one you stopped; it spends no sweep, so its replacement is handed a corrected `--sweep`). Its report (`implementerReportFile` in its bundle) is recorded at close; every item it says it left becomes a discovered issue, so nothing it saw is dropped. Implementers record their own lint or fixture fixes as `wf discovered add --kind bookkeeping`; real defects they find are `--kind defect` (default), rated on the severity scale below (`--severity`; `--invariant "<which>"` when it breaks a critical invariant, which makes it high), and go to the strategist or the next repair, not into a silent fix outside the plan. `wf discovered rate <id> --severity <s> --reason "..."` re-rates one (raising is free, lowering records its reason and, out of high, needs the person's `wf approve`). To install dependencies that need a step's secret before the first commit, `wf run --step <step id>` runs the step's declared `prepare` command (the adapter declares it; never pass your own command).
4. **Check the parts together.** With more than one work item, run `wf check` on the combined tree once the implementers are closed and fix what it finds through them; `wf handoff reviewer` refuses until the combined tree has a passing check. Review is never the first place the parts meet.
5. **Review round 1 (full, blind).** `wf handoff reviewer --agent <new id>`; launch it with exactly the line it prints. No hints, summaries or anyone's findings: a steered reviewer misses things. The reviewer writes its closure and runs `wf review --closure <file>` itself. The reviewer states its scope and expected minutes in its closure file and `wf resume` shows them while it works; a delta round is bounded by its scope (the diff since the last reviewed tree and the open findings), not by a clock.
6. **Repair by family.** A finding blocks a round only if it cites a frozen criterion the change fails, breaks a critical invariant, or is a regression on lines this attempt changed (in a delta round: since the last reviewed tree), and is rated medium or high (or unrated); a finding rated low never opens a round, in any round, and a full-round finding that cites nothing checkable blocks until a later round locates or verifies it. Everything else is an **observation**: it is not dropped (delivery waits until each is fixed or moved to a sibling attempt; by default only a low one may leave, with the user's answer to its own short question) but it never opens another review round by itself. Fix an observation as an observation: amend the criteria only when the ticket's goal changes, because a criterion added for one defect makes every later finding that cites it a blocker. Group the blocking findings and observations you will fix by `family`; hand them to the implementer that did that work as a fix round (`wf handoff implementer --agent <its id>`; `--sweep <file>` is optional, for a pattern you already know), so its report and the defect history are recorded; it fixes each family at its cause with one mechanical proof (a query, lint rule or test and its expected result) instead of answering every match. You route every repair to an implementer and never write the product repair yourself. Then a fresh reviewer for the next round: from round 2 on it is a **delta review** (the diff since the last reviewed tree plus the open findings, which it verifies). Repeat until no blocking finding is open.
7. **Gate once.** Before it, `wf resume` names the open observations to place now: fix them in this pass (the implementer's next commit), so they do not wait for delivery; by default only a low one may leave, with the user's answer: one short question per item, asked together. Then `wf gate` on the reviewed tree (background is fine; never edit the worktrees or hand a reviewer the tree while it runs). Reuse is automatic. A failure is fixed through the implementer, then a delta review, then the gate again; that gate is the repair's proof (it reruns what failed, only the failed suites where a step allows it, and reuses what still passes), so the brief names what failed and the goal, never the runs that prove it, and the implementer's own runs serve finding causes. After an evidence review's blocking findings are fixed by the implementers handed after it (each closed, the tree is what they left, and no scope was added since), `wf gate` runs without the user's approval (the evidence review after it verifies the fix); every other out-of-order gate needs `wf gate --reason` and the user's `wf approve`. Stopping a gate or check: `wf stop --class major-finding|tree-change|owner-decision --reason "<why>"`; a check stopped for a tree change or finding is not rerun until a new commit.
8. **Evidence review.** A fresh reviewer inspects the gate logs and the screenshots of this ticket it has not seen before (`gate.screenshots` marks each `inspectedBefore`; a screenshot with the same sha256 as one an earlier review inspected is not opened again, and the reviewer may look at any) and maps every criterion to the evidence. The first evidence review is a full blind audit; one after a fix is a delta (what changed since, the open findings, the new gate evidence), so a fix never restarts an audit of the whole change. Then `wf accept`; its refusal names what is missing and the command to run.
9. **Deliver.** Write a few plain-language lines for the tester, then `wf deliver --summary-file <summary.md>` (every deferral is listed in its output and in the delivered comment's known limits on its own; there is nothing to acknowledge). Show every delivered screenshot in the chat (below), record captions and anomalies with `wf shown --file <draft>`, attach and embed them in the tracker comment, set the status, and record the RAW readback.
10. **Report** in a short summary: what changed, the proof, what is pending, each delivered screenshot with its caption (or the no-screenshots reason).

## The strategist

When you judge the course diverged from what was predicted (the section above), run `wf handoff strategist --agent <new id> --reason "<what you saw diverge, and your analysis>"` and start `wf-strategist` on its bundle (or `wf handoff run` where your harness cannot start it by name). It reads the expectations beside what happened and the signals, and returns one decision with a prediction; record it with `wf strategy record --closure <its file>`. While it works, `wf resume` says `strategy`: wait for its completion notification. Actions: continue, consolidate (one amendment for the whole dependency map), cluster (families and their proofs), delta-review, split (sibling attempts in the same delivery batch: `wf split --items <ids> --reason "..."`), ticket (low observations and discovered issues only, each then the user's decision), model (change model or effort), escalate (a decision the user confirms with `wf approve`). Two missed predictions in a row make the next decision an escalation. Apply the decision before the next handoff, and never hand a second strategist while one is outstanding. After a `ticket` decision you file the tracker tickets (`wf signals` lists them under `toTicket`). After a `split`, each sibling is a normal attempt (`wf handoff implementer --attempt <sibling> --agent <id>`); once every member is accepted, `wf batch create --members <parent>,<siblings>`, then gate, review, accept and deliver the batch. Never deliver a member alone.

## Scope

Nothing broken is silently dropped, and where a fix lives can change.

**Severity** is one scale for every reviewer and implementer, and it decides where an unfixed finding or discovered issue may go: **high** = a user, a tenant or the business is harmed or blocked (wrong or lost data, a broken flow, security, money, a visible defect on a primary screen); **medium** = degraded but usable (a secondary flow, an edge case, a confusing state); **low** = polish (wording, spacing, naming, style). A tenant-isolation, authorization or money defect is always high.

- Defects caused or exposed by this change, and defects on a critical boundary (tenant isolation, money, authorization), are fixed in this delivery: in this attempt, or in a sibling attempt of the same batch (`wf split`, `wf scope move`), which asks nobody because the obligation stays in this delivery. A finding on a line this attempt changed is fixed in this attempt: a sibling starts from the base and has no such line.
- Other existing defects you find are observations. What may leave the delivery is the user's rule (D17, D18), for observations and discovered issues alike: medium and high (or unrated, or one that breaks a critical invariant) are fixed in this delivery, here or in a sibling attempt of the batch; a low one leaves only with the user's answer, one short question per item (`wf scope defer --finding <ref>[,<D-id>...]` for known issues, `wf scope ticket` for a follow-up ticket; give a plain line per item with `--explain <file.json>`), and they may fix one and let another go, or answer in their own words, which you then follow; the project's adapter may change who decides each level (`leaving:`); a fix that needs a product decision is a question for the user, not a deferral; a finding the user judges wrong is waived by them (`wf scope waive`). The default is to fix: propose a low item for leaving only when fixing it now costs more than it is worth, and put every such item to the user at once (the engine prints one short question per item, to ask together in one panel; a ticket needs the tracker's raw readback, `--capture <raw.json>`). A severity is the reviewer's or implementer's claim: a defect touching money, authorization, data shown to another party or legal output is never low. An observation an implementer fixed is verified by the next reviewer, or recorded with `wf scope fixed --finding <id> --commit <sha>` (a commit made after the finding was raised; a later reviewer who finds it still open undoes the record, and a high one still needs a reviewer's `fixed` before delivery). Every reviewer sees what left the delivery (`followUps`) and can raise any of it again.
- Amend criteria with `wf criteria amend --file <f> --reason <why>` (only the changed or new criteria; `{ id, dropped: true, reason }` removes one). An amendment that adds scope carries its `impact` update in the same file. Prefer one consolidated amendment per strategy decision over one per discovery. On an accepted attempt an amendment that adds or re-words a criterion withdraws the acceptance (on every attempt, from 0.7.4; an amendment an earlier engine recorded kept the acceptance, and `wf resume` warns for it): hand a fresh reviewer, which maps every criterion to the gate evidence, then `wf accept` again; never deliver on the earlier acceptance.

## The user's reserved decisions

Only these need the user: waiving a blocking finding (`wf scope waive --finding <id>`), overriding a failed gate or the gate order, a low finding or discovered issue leaving the delivery (one question per item; medium and high never leave unless the project's `leaving:` says otherwise), lowering a rating out of high, ejecting or abandoning a member of a batch a split made, lifting a hold, adopting an attempt whose owner session is still active, and escalations. The engine creates the decision and prints its id, the question and its options. First say in your reply, in plain words, what it decides, why, and what each choice leads to (a question panel may not show; a tool that says "accepted" proves nothing). Then ask the user in your question panel with exactly that question and those options, each option by the label the engine printed with what follows it as its description and the recommended one marked "(Recommended)" (they can answer from anywhere, the phone included) and run `wf approve <id> --from-question --attempt <attempt>`: the engine reads the answer the harness recorded. When the panel shows nothing for them, give them `wf approve <id> --attempt <attempt>` to run in their own terminal. `wf decisions` lists them. Never ask the user to type an approval in the chat for these (their chat words are not read; the explanation in your reply is for them to decide, not the approval), and never try to approve one yourself. Everything else (closing implementers, choosing runtime or model, adopting an abandoned attempt, moving work to a sibling of the batch) you decide and the engine records.

## Evidence and screenshots

- Read evidence with `wf evidence list --attempt <id>` and `wf evidence show <path> --attempt <id>`, or the host's file reader and image viewer. Write "the evidence folder" in commit messages and notes instead of its path. Never write, move or restore evidence files; if a command says the evidence does not match what wf recorded, stop, run `wf verify --attempt <id>` and tell the user.
- View screenshots only through `wf export screenshots [--gate] --attempt <id>` and the host image viewer. Show each in the chat with a caption saying which screen and state it shows (the way your chat displays an image). Compare captures of the same state: any differing value is investigated to a cause or recorded as a follow-up in `anomalies`. If the set holds files that are not this ticket's, `wf delivery narrow --keep <sha256,...> --reason "<why>"`.
- Attach and embed: with an engine route (`tracker.via: api|cli|files`), `wf shown` uploads, posts and reads back. With a connector: per file `prepare_attachment_upload` (filename and title = the "attach as" name, subtitle = caption), `PUT` the exported copy's bytes with every returned header, `create_attachment_from_upload`; then post the rendered comment file unchanged except each `{assetUrl:<title>}` replaced by its asset URL; set the status; read the issue and comments back and run `wf tracker record --event delivered --from-transcript` (or save the RAW `get_issue` and `list_comments` results and `--capture` them). Never post the comment before its uploads; never rebuild a readback by hand.
- At each milestone (plan, review closure, gate, delivery) `wf export --attempt <id>` writes a page of the attempt; publish it as one private Artifact updated in place when the host has one.

## Proof belongs in evidence, not in the repository

When a reviewer asks for missing proof, route it to a gate step that collects `artifacts`, to `wf export screenshots`, or to a tracker attachment. Never amend criteria to publish captures, logs or reports in a repository folder, and never commit disposable run outputs. A step plugin writes its captures into its scratch folder (`ctx.evidenceDir`) or its package folder and returns them as `artifacts`; the engine records the sealed copies. If outputs were committed, remove them in a new commit.

## Recovery

- `wf resume` after any interruption or compaction. An attempt whose worktree is gone shows as ORPHANED: restore the folder from its branch with the git command `wf resume` prints (committed work only), or `wf abandon --reason "..."` (branches are kept); an attempt whose change already landed on its target branches outside the workflow is closed with `wf close --shipped --reason "..."` (the user's decision; the tracker is not touched).
- A stale evidence lock left by a dead process clears itself; `wf unlock --attempt <id>` removes one explicitly and refuses while its owner is alive. Never delete the lock file by hand.
- `wf status` shows when a base moved; `wf base merge` merges it (the review and gate then run on the merged tree).

## Learn from corrections

When the user corrects you, a ticket is reopened, or a delivered screenshot shows an anomaly with a follow-up, decide first: project or workflow?
- Project: `wf lesson add --attempt <id> --repo <name> --title "..." --what "..." --cause <class> --mechanism <kind> --quote "<their words>"` (`--project` when it spans repos). `wf lesson apply <id>` prints the change that enforces it; commit it only with the user's approval.
- Learning is automatic: at acceptance the classifier counts which lessons the findings repeat, and bundles rank lessons by it. When `wf resume` names lessons that describe one mistake, merge them in the open attempt (`wf lesson merge <ids> --title "<the one mistake>" --attempt <id>`); it is reviewed and delivered with the attempt. If they are different mistakes, `wf lesson distinct <ids>`.
- A standing rule for every ticket (what the user holds every change to, not a fix for this one) also belongs in the project's quality bar: propose the sentence to the user and, with their go, add it under `quality:` in the adapter and commit it on the adapter base branch (then `wf sync`). The quality bar grows from corrections the way lessons do.
- Workflow: `wf improve add --title "..." --what "..." --observed-in <attempt> --quote "<their words>" --class <engine|template|skill|guard|tracker|onboarding|docs|other>` (the user's inbox, outside every repo). Prefer removing a check that keeps misfiring to adding a new one: `wf refusals` shows which checks refuse most, `wf improve review` which of them no improvement cites, and a check that caught nothing is retired with `wf improve close <id> --retire --version X --reason "..."`.

Prior decisions are inputs, not authority: an earlier merge, a test or a cited invariant says what was decided, not what should be.

## Native launches

- If a native launch fails before a session starts (initialization permission), create a fresh handoff and launch it through the host's approved execution path; never retry the same handoff or bypass a rejected approval.
- Close completed implementers from the owning chat with `wf handoff close --agent <id> --attempt <id>`.
- For connector receipts, call one MCP tool per invocation and keep each result unchanged.
- Use the owning thread's runtime for every role unless the user asks for another provider.
