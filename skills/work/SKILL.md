# Work a ticket

Check `wf status --quiet` exits 0; otherwise this project is not onboarded (offer the onboard skill).

The user's request to implement a ticket authorizes the whole lifecycle below, including delivery, unless they say otherwise. If they say hold, local only or don't push, run `wf hold --reason "<their words>"` immediately.

Role agents are generated by `wf sync`: `wf-planner`, `wf-reviewer`, `wf-implementer` and one `wf-implementer-<class>` per other work class. Each file sets that agent's effort (and model, if the class sets one). Always start the agent type a `wf handoff` names, never `general-purpose`, and never pass `model` on the Agent call: both replace the agent file's settings. Agents written by `wf sync` after this session started are registered only after a restart; if the named type is missing, ask the user to restart the session instead of substituting another agent.

1. `wf entry --item <ID>` (add `--intent analysis` for investigate-only requests; analysis never delivers; with no tracker, save the request text to a file and pass `--issue-file <file>`). Perform the printed tracker actions, save the raw responses, run `wf tracker record --event admitted --capture <file>`.
2. Planner: `wf handoff planner --agent <new agent id> --session <its session id if known>`, then start the `wf-planner` agent on the bundle path. Save its YAML and run `wf plan --file <yaml>`. `wf plan` lists the work items with their classes. To change criteria later, `wf criteria amend --file <f> --reason <why>` with only the changed or new criteria; the rest stay. Removing one takes `{ id, dropped: true, reason }`.
3. Implementers, one per work item: for each open work item `wf resume` lists, run `wf handoff implementer --work <W> --agent <new id>` and start the agent type it prints (for example `wf-implementer-light`), named with that id, on the bundle path. When the plan's `agentSplit` says the `contract` goes first, run that work item first and let it commit before starting the others; otherwise run them in parallel. Without work items, one `wf handoff implementer --agent <id>` and the `wf-implementer` agent. If an implementer reports its work touches something a stronger class covers, stop it and tell the user; do not re-classify work yourself. Make sure everything is committed in the worktrees.
4. `wf gate` (run it in the background and follow its output or `wf status`). Never edit the worktrees while a gate runs. On failure, read the step logs, fix the root cause through the implementer that did that work (continue the same agent with SendMessage; a repair round is not a new handoff and is not re-classified), commit, rerun. Reuse is automatic; never rerun passing work by hand. `--focused` is for repair rounds only: review and delivery need a gate without it.
5. Reviewer, blind: its prompt carries no hints, focus areas, summary of what the implementers did or decided, list of what to judge, or anyone's findings or opinions; steering a reviewer boxes it in and it misses things. While the gate runs, start the `wf-reviewer` agent with a reviewer id (not the planner or any implementer) and only this line: `Review the committed diff of attempt <id> in <worktree paths> against its base; the bundle follows.` After the gate passes, `wf handoff reviewer --agent <that same id>` and resume that agent with exactly the one line it printed (the bundle path; the bundle holds the criteria, amendments with reasons, plan, diff locations, gate evidence and screenshots) so it checks the gate evidence and screenshots; it writes the closure to the bundle's `reviewClosureFile`. Then `wf review --closure <its file>`. Fix every open finding and any gate failure in one cycle, sending each finding to the implementer of the work item it is tagged with (SendMessage to the same agent), gate again, and hand to the reviewer again until all findings are fixed or verified non-issues. `wf accept`.
6. `wf deliver`. Then do the printed tracker actions (comment, screenshots, status), save the readback, and `wf tracker record --event delivered --capture <file>`. Show the user every delivered screenshot with a caption.
7. Report with a short summary: what changed, the proof, what's pending.

`wf resume` tells you the next step at any point, including after an interruption.
