# Resume

1. `wf status` lists open attempts in this project (`wf status --all` across projects). An attempt whose worktree is gone shows as orphaned; `wf abandon --reason "..."` closes it and keeps its branches. When its change is already on its target branches (merged outside the workflow, or one repo delivered and the rest merged by hand), `wf close --shipped --reason "..."` closes it as shipped: the engine checks the commits are there and the user confirms the decision.
2. `wf resume --attempt <id>` prints the next action and how far each base moved. With several open attempts always pass `--attempt`. Before anything else the user asked, act on every role that finished while you were away: read its report and close it (`wf handoff close`), then continue; a role still running is waited on in your turn, not left to wake you.
3. To take over an attempt from another session: `wf adopt --attempt <id>` (or `--item <ticket>`). If the previous owner session is gone or idle, adoption is recorded at once; if it is still active, the engine creates a decision the user confirms: ask them in your message (the question quoted exactly, its options, nothing else asked; the question panel too, if you like: both count), then `wf approve <id> --from-question --attempt <attempt>` after their reply (adding `--choice <choice> --quote "<their words>"` when you read an answer in more words than an option's name); or they type `wf approve <id> --attempt <attempt>` in their own terminal. Adoption keeps holds and existing work; it never lifts a hold or widens scope.
4. Every question `wf status` or `wf resume` lists under "waiting on the person" is still open. When your reply mentions it (a status, what remains), ask it there as it is printed, quoted exactly with its options; one described in your own words is not asked. You read their answer: one that is exactly an option is recorded by `wf approve <id> --from-question`; for one in more words ("ok we can close this then"), judge whether it chooses an option and record it with `--choice <choice> --quote "<their exact words>"`. Either way, tell them in that reply what you recorded (for a reading, from which words), and honour their correction. Words that choose nothing (a condition, a hedge, a later sentence that takes it back, someone else's words reported, words about something else, the action meant for another ticket) are no answer: ask the question in that same reply. Never end the turn on a refusal.
5. An attempt whose delivery waits for the deployment (`wf resume` names the deployment step after the delivered handoff) stays open until the merged change is confirmed running where it deploys and the fix is tested there: the deployment may have finished, failed or still be rolling out while you were away, so check it again (read-only: `wf deployment check`, or look and `wf deployment record`) before anything else on it, and follow the work skill's delivery step.
6. A gate whose runner died, or that the owner stopped, continues with `wf gate`; finished steps are carried. A gate stopped for a finding or a tree change is not resumed: the fixed tree gets a delta review first.
7. A role launch recorded as running after a restart is not proof of a live process. `wf signals --attempt <id>` (and `wf resume`) shows each working role's elapsed time and last transcript activity beside its own estimate; a role far past it with no recent activity is yours to judge (look at it, then stop and re-hand it). Never launch a duplicate of a running handoff; a failed or stopped one needs a fresh handoff.
8. A stale evidence lock left by a dead process: `wf unlock --attempt <id>`.
9. Read the `course` lines of `wf resume`: the plan's, each implementer's and each reviewer's expectation beside what happened. After an interruption this is where you judge whether the ticket is still converging (the work skill's section on round boundaries). If `wf resume` says `strategy`, the course signals it names make the strategist the next step (hand it; that is not a judgement call), a strategist you handed has not decided, or an escalation awaits the user's `wf approve`: follow the work skill's strategist section before any other handoff. If it says `pass`, the items that do not block are planned as one pass (the work skill's step 7), never a round each.

If a command refuses because the evidence does not match what wf recorded, run `wf verify --attempt <id>` and report the listed files to the user; never repair evidence yourself.

Use the owning thread's runtime for every role (an owner on one harness uses that harness) unless the user asks for another provider. If your harness cannot start an agent type by name, launch each handed role with `wf handoff run --agent <id> --attempt <id>`; native launches load fresh engine instructions, so no session restart is needed.

If `wf status` lists open plugin improvements and this is a session in the plugin's own repo, `wf improve next` names the one to fix; `wf refusals` shows which checks refuse most.
